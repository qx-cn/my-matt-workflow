# my-matt-workflow v2

本工作流在多个宿主共用 4 个手动触发的 Skill、1 份个人通用规则和 1 个软链同步脚本。小改动直接编码，或用宿主内置 Plan Mode。跨模块或需团队评审的需求，设计期默认维护一份技术方案（本地 `design.md` 与对应飞书文档），供评审、编码和验收共用。大型项目若涉及多个独立子系统或不同评审团队，按评审边界拆分。

| Skill | 干什么用 | 调用方式 |
| --- | --- | --- |
| `my-grill` | 先查代码再逐轮提问，把需求边界、对外契约和方案取舍问透 | 手动 |
| `my-tech-design` | 写出契约清晰的纯 Markdown 定稿（技术方案 / 发布文档 / 测试报告），可一步发布飞书或 HTML | 手动 |
| `my-doc-publish` | 把定稿 Markdown 排成留白清晰、带原生画板的飞书云文档或本地交互式 HTML，并跑脚本校验 | 手动 |
| `my-review` | 派新子 Agent 独立审查代码或文档，按“必须修”和“建议”分级报告 | 手动 |

## 日常使用流程

Cursor、Claude Code 和 WorkBuddy 里敲 `/my-grill`，Codex 里敲 `$my-grill`。

任务本地文件统一放在业务仓库 `.agent/work/<主题>/` 下：外部参考放 `refs/`，测试原始证据放 `evidence/`，方案定稿放 `design.md`（上线期按需生成 `release.md`、`test-report.md`），飞书与本地排版产物放对应的 `.xml` / `board*.json` / `.html`（不再额外维护重叠的 `spec.md` 与 `decided.md`）。含内部信息的文件只留本地，不提交仓库（本仓库已将 `.agent/work/` 加入 `.gitignore`；在业务仓库使用时，如未忽略请先加入 `.gitignore` 或 `.git/info/exclude`）。

- **极小改动 / 修简单 Bug**：
  - **0 份文档**，不调自定义 Skill，也不用开详细计划，直接让 Agent 改代码跑单测。
- **无需拉会评审的单人中等改动 / 局部重构**：
  - **0 份外部协作文档**，直接用宿主内置 **Plan Mode**（如 Cursor `Shift+Tab`）先对齐几步修改计划，确认后实施。
- **跨模块或需拉会评审的中大型需求**：
  1. **问清边界（可选）**：需求还有模糊点时运行 `/my-grill`，查清代码现状、追问边界与取舍，最后在对话中得到结构化定稿摘要。
  2. **起草并发布方案**：运行 `/my-tech-design 发到飞书`（不发飞书就说“只留本地 md”或“出本地 HTML”）。Agent 先写出干净的 `design.md`（包含背景目标、状态矩阵、老接口切换表、时序图、DB/Proto 契约、方案取舍表与验收场景表，不塞源码行号与锁拼接细节），再自动调 `my-doc-publish` 排成飞书文档并画好画板。
  3. **看着飞书直接改定**：评审时只盯这一份飞书文档；要改哪里直接运行 `/my-doc-publish <飞书链接> <修改意见>`，局部更新飞书（保留原有画板和评论）、跑通脚本校验并同步回本地 `design.md`。
  4. **按定稿实施并独立审查**：让 Agent 对照源码和 `.agent/work/<主题>/design.md` 核实现状，先列修改文件，再实施并补齐验收表对应的测试。涉及存量数据、并发锁、对外契约或回滚风险时，可运行 `/my-review` 对照方案审查代码改动，只修确认成立的“必须修”，“建议”由作者决定。
- **上线变更单与测试留证**：按需运行 `/my-tech-design` 生成《发布文档》或引用 `evidence/` 真实报文的《测试报告》，一键发飞书。
- **已有 Markdown 单独发布**：手头已有现成 `.md` 文稿时，直接调 `/my-doc-publish @xxx.md` 发飞书或出 HTML。

## 官方建议与本仓用法

下表区分厂商建议和本仓选用的流程。原文与适用范围见[编写与审核参考](docs/authoring-guidance.md)。

| 场景 | 官方推荐做法 | 落地方式 |
| --- | --- | --- |
| **极小改动 / 简单修 Bug** | 不必先写计划，直接让 Agent 动手改代码并跑测试验证 | 0 份文档，不调自定义 Skill |
| **单人中等改动（不拉会）** | Cursor 的 Plan Mode 支持先查代码、讨论计划，再按计划实施 | 直接用宿主内置计划，省去外部协作文档 |
| **排查与修复 Bug** | Claude Code 指南用失败测试复现故障，再修复并运行测试 | 给出症状、相关目录与测试命令 |
| **跨模块 / 需评审需求** | OpenAI 的工程实践用可检查的不变量约束实现 | 边界不清时先用 `/my-grill` 澄清，再用 `/my-tech-design` 写评审与验收共用的方案 |
| **长任务编码与审查** | Claude Code 指南建议让独立审查者检查实现是否符合方案 | 对照 `design.md` 实施并补测试，按需调用只读的 `/my-review` |

使用时按任务情况处理上下文和规则。

1. **按任务相关性切换会话**：Claude Code 建议在无关任务之间运行 `/clear`。同一需求从设计转入编码时，仍要用前面的决策就继续当前会话。若大量排障日志已妨碍实施，可在新会话中依据定稿和源码继续。
2. **连续两次纠正仍未解决同一问题时停下来**：Claude Code 建议清空会话并重写提示词，Cursor 建议实现跑偏时回退改动、细化计划再试。本仓先说明卡点，由作者决定是否回退。
3. **用测试和脚本守住边界**：OpenAI 的工程实践把不变量写进检查，并在报错中说明修法。本仓用技术方案约定业务规则、对外契约和验收场景，内部实现由 Agent 对照源码确定。
4. **按实际问题补规则**：Cursor 建议观察到重复错误后再加规则。若已经写明的硬要求仍被漏掉，Claude Code 建议用 Hook 执行，本仓也用校验脚本检查客观要求。

## 常见写作毛病与对策

AI 写中文技术文档最容易犯下面 6 个毛病（已在全局规则、模板构件和校验脚本里设防）：

1. **乱翻英文原词、照搬源码黑话、名词化堆叠或砍宾语变半截话**：机翻团队英文动作词（如 Approve、Reject），原样照抄代码注释里的生硬英译词，把动词压在句尾堆成偏正名词词组与四字口号，或为省字数砍掉主宾语写成半截话。
2. **把实施难点塞进现网故障、切流改造缺前后对比**：把新方案开发期参数适配或预发测试难点冒充成现网已有故障，接口切换或重构只平铺直叙写新代码而不对比新旧机制差异，或拿通用发版套话代替具体配置和权限依赖。
3. **小兼容点满篇刷屏，或后半程跳节漏表**：把只占 5% 的边角兼容写进主干标题反复念叨，写到后半程却把关键的《方案取舍》整节漏掉。
4. **窄列表格挤成文字砖、配图画成高瘦电线杆**：把多个枚举用斜杠塞在一格，把带前提的长条件全塞进 4 列窄表（应表内只放 1 至 2 行简明结论，复杂前提移至表下分点），或跳过作图策划直接画出无改造边界、高瘦单列的流程图。
5. **业务映射配置截断成两行示例、动态文件不查真实格式**：路由或市场字典配置只贴 2 行样例配 JSON 语法废话表而漏掉全量业务映射表，或贴报表样例时没去源码核实真实拼接格式。
6. **标题报菜名、一节塞两件事、视觉后半程掉队**：标题用顿号堆砌，把触发规则与文件格式揉进同一小节，或前半篇卡片颜色丰富、后半篇退化成纯黑白无表头底色文本。

平时按这三步应对最省心（不需要另建写作检查 Skill，统一用 `my-review` 检查，避免脱离源码事实瞎润色把意思改反）：

1. **根据已有上下文选起草方式**：干净会话中直接运行 `/my-tech-design 发到飞书`。当前会话若已积累大量排障日志，由新子 Agent 根据需求、决策摘要和必要材料起草。
2. **重要评审方案跑一次独立 `my-review`**：同会话自检受模型固有思维定势限制，关键方案按待审文件区分审查重点。先审本地 `design.md`，对照真实源码核查方案设计，发布后再拿核查过的 `design.md` 当基线，审飞书或 HTML 成稿的阅读体验、视觉层次和图表效果。
3. **自己扫读发现小问题按“1 分钟原则”处理**：
   - **顺眼度小调整**（挪一下画板框间距、多标一处高亮、顺手改两字语气）：直接在飞书网页上动手改，1 分钟搞定，不用管本地文件。
   - **段落看不懂、缺例子或要改规则**：运行 `/my-doc-publish <飞书链接>` 用大白话直说修改意见（比如“2.3 节这段看不懂，画个时序图讲清楚”），Agent 局部改飞书、跑脚本校验并同步更新本地 `design.md`。同类毛病要是犯了第二次，让 Agent 补个通用正反例记进本仓规则。

## 三层分工边界

文档和画板按下面三层分工，不把主观审美硬写成死配额：

| 层次 | 谁来管 | 管哪些事 | 为什么这么分 |
| --- | --- | --- | --- |
| **1. 版式与画板校验** | **脚本门禁与提醒**（`check_feishu.py` / `check_html.py` / `sync.sh`） | 用 `ERROR` 拦住非法嵌套、标题跳级等客观错误（`check_html.py` 只报结构 `ERROR`），`check_feishu.py` 另用 `WARN` 提醒作者核查偏长段落、窄表格与高瘦构图 | 脚本给出可复查的位置，作者判断如何改善可读性 |
| **2. 内容结构与代码一致** | **4 个 Skill 分工处理** | 写方案时先写结论图注，再选算例、标明改造边界，最后选图型。发布时渲染并导出画板预览图复核。`my-review` 对照原始规范独立审查 | 方案交代读者要看懂什么，发布时才能检查实际画面 |
| **3. 会议侧重与像素微调** | **自己在飞书页面微调** | 画板局部框体的像素对齐与折线弧度；针对某位参会人临时多标黄强调的一句话；某处用双栏卡还是三列表的个人喜好 | 因人和会议场景而异，在飞书页面拖两下比让 AI 盲猜坐标快得多 |

画板连线按端点检查。若一端引用节点却缺锚点，`polyline` 和 `rightAngle` 报 `WARN`，直线及其余线型（含默认直线）报 `ERROR`。若一端直接给坐标，该端无需锚点。

## 安装与同步

同步脚本依赖 Bash 和 Python 3：

- **新机器首次安装**：克隆仓库后在根目录运行 `./scripts/sync.sh`，再跑 `./scripts/sync.sh --check` 检查。
- **装过旧版的机器同步更新**：增删或重命名 Skill 后运行 `./scripts/sync.sh`（脚本会自动清理退役 Skill 的残留软链；若机器上保留着 v1 旧版 `install-state.json`，首次升级运行 `./scripts/sync.sh --migrate-v1`），再跑 `./scripts/sync.sh --check`。

生成本地 HTML 只需 Python 3；发布飞书云文档和画板还需本机装好飞书工具链并完成登录：

- **外部 Skill**：`lark-doc`、`lark-whiteboard`、`lark-wiki`、`lark-shared`
- **外部 CLI**：`lark-cli`（已执行 `lark-cli auth login`）与 Node.js `@larksuite/whiteboard-cli`

日常同步说明：

- **软链位置与范围**：默认把 Skill 软链到本机 `~/.agents/skills/` 和 `~/.claude/skills/`，把 `rules/global.md` 软链到 `~/.claude/CLAUDE.md` 和 `${CODEX_HOME:-~/.codex}/AGENTS.md`。注意本方案面向本机 IDE 与 CLI 会话：Claude Desktop 的 Cowork 模式会跳过软链 `CLAUDE.md`，Cursor Cloud Agents 只同步 `~/.cursor/skills/` 而不同步 `~/.agents/skills/`。
- **WorkBuddy 按需启用**：在 `~/.zshrc` 等配置里加上 `export WORKBUDDY_CONFIG_DIR="<绝对路径>"` 后跑 `./scripts/sync.sh`，就会额外软链 `$WORKBUDDY_CONFIG_DIR/skills/` 和 `MEMORY.md`（未配环境变量时自动跳过）。WorkBuddy 会把 `MEMORY.md` 截断在 4000 字符，`./scripts/sync.sh --check` 会自动检查 `rules/global.md` 没超限。
- **Cursor 用户规则**：本机 Cursor 从设置读取 User Rules。改完 `rules/global.md` 后，用 `cursor_dialog` 更新名为“个人通用规则”的 User Rule，或手动粘贴。前述 Skill 目录软链另按 Cursor 的 Skill 发现规则加载。

常用本地检查命令：

```bash
# 检查软链状态与 rules/global.md 4000 字符上限
./scripts/sync.sh --check

# 运行文档校验与同步脚本的单元测试
python3 -m unittest discover -s tests -p 'test_*.py'

# 检查飞书 XML 留白、重点格式、单元格长度与画板防撞框（局部块更新加 --fragment）
python3 skills/my-doc-publish/scripts/check_feishu.py <design.xml> [board1.json board2.json ...]

# 检查本地 HTML 导航完整性与窄栏防截断
python3 skills/my-doc-publish/scripts/check_html.py <design.html>
```
