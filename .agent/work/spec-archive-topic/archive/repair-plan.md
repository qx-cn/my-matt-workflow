# 归档功能系统性修复方案

## 背景与根因

连续独立审查发现预览字段、首次发布参数、引用扫描边界、符号链接、文件类型、当前长期 Spec 引用和大文件读取等问题。这些问题分属同一条发布与搬移链路，并非重复审查同一个 Spec。主要根因是：

1. 当前 Spec 的验收句子未被展开成逐入口、逐字段、逐状态的实现清单，预览与应用参数因此出现不一致。
2. “搬移前检查失效引用”没有先定义完整的活动引用范围和路径表示，扫描器最初只覆盖常见文本扩展名及带尾斜杠的路径。
3. 文件读取策略分散，外部引用扫描采用分块读取后，Topic 清单仍曾整文件读取。
4. 前几轮复审侧重上一轮补丁，没有先做全链路盘点，所以问题按场景逐次暴露。

## 契约矩阵与修复顺序

| 边界 | 必须核对的条件 | 修复动作 |
| --- | --- | --- |
| 长期 Spec 预览与发布 | 来源、候选、旧版哈希；首次发布标记；审查收据；预览值可直接用于应用 | 对齐 `previous_sha256` 表示和应用比较；复查发布中与已发布恢复路径 |
| Topic 预览与搬移 | 完成依据、已发布版本、目标、完整文件清单及摘要；应用重验这些条件 | 在报告中暴露 `completion` 与 `files`；同锁内复核 |
| 活动引用 | 其他活动 Topic、项目 profile、当前长期 Spec；根目录、子路径、相对链接和符号链接；任意普通文件大小与扩展名 | 以引用文件所在目录解析相对链接，结合有明确边界的路径匹配与分块扫描；搬移前重验并报告命中的文件 |
| 文件清单与只读查询 | 每个源文件路径、大小、哈希；清单一致；大文件内存有界；稳定来源与代码来源收据完整核验 | 统一分块哈希；`archive-list` 只做轻量定位，`archive-show` 逐项核对并报告外部漂移；保留历史字节 |
| 发布到搬移的证据链 | 发布候选仍匹配发布哈希；测试、审查证据和结果仍匹配冻结收据 | 搬移前重验候选及完成会话历史；归档读取使用只读路径映射核验同一批收据，不调用活动实施门禁 |
| 生命周期与中断 | 未完成或活动会话拒绝；发布封存；重复与中断可恢复；归档后不可实施 | 检查锁、封存状态和目标冲突；不以目录搬移切换长期 Spec 权威 |
| 文档与 CLI | 命令字段、参数示例和限制与实际结果一致 | 更新 README 与 Spec 对照表述 |

## 准入步骤

1. 完成上述全链路静态自查，列出所有尚存缺口后集中修复，避免一次审查只修一个样例。
2. 请新的独立 subagent 依据本矩阵和当前 Spec 全面审查，要求继续检查所有边界，不在首个发现处停止。确认问题全部修复后，再交给另一名独立 subagent 复审。
3. 仅在独立复审报告 `No findings.` 后报告静态审查通过。静态审查不等于运行验证；若未实际运行验证，应在交付时明示。

## 本轮已处理并获独立静态复审

- 归档前解析其他活动文件中的 `../<topic>/...` 相对链接并阻断失效引用。
- 搬移前重验 `archive/canonical-spec.md` 与发布记录中的候选哈希。
- 搬移前重验完成会话证据；搬移后通过受限路径映射只读核验相同的冻结收据。
- `archive-show` 仅将 Topic 根目录的 `runs/run-*.json` 识别为实施会话。

两名新的独立 subagent 分别对完整改动给出 `No findings.`。准入结论限于静态审查；本轮未运行测试或实际项目归档演练，不能据此宣称运行验证通过。
