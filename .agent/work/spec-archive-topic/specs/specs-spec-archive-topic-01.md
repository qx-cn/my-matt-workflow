# 长期 Spec 与已完成 Topic 归档

## 问题陈述

当前本地工作流把版本化 Spec、Ticket 和实施记录保存在 `.agent/work/<topic>/`。完成后没有一份可直接阅读、以此为准的长期 Spec，也没有把已完成 Topic 从活动工作中归档的入口。使用者必须重新追溯历史变更，才能判断某项能力目前承诺什么。

## 目标结果

1. 每个已发布的能力有一份可直接打开的长期 Spec，完整描述当前有效行为、验收和不变量。使用者查询已发布行为时以它为准。
2. 已完成 Topic 可从活动工作区移入归档区，保留 Spec 修订、Ticket、实施会话、审查和证据，且可定位和阅读。
3. 长期 Spec 的每次更新都能追溯到来源 Topic 和原版，并阻止未完成或来源失效的变更成为当前权威。

## 范围边界

- 本次覆盖 `local` 后端的项目内文件；外部 Tracker 与 `project-docs` 后端需要另行设计写入和权威关系。
- 本次行为发布流程限定一个 Topic 对应一个行为 Spec id。新 Topic 在创建 Spec 时保持这一边界；既有多 Spec Topic 不自动发布或搬移，须先制定保留每份原始产物与 Ticket 血缘的拆分方案并完成迁移，再分别走发布与归档流程。
- 活动 Topic 的 Spec 仍是该次变更的实施边界。长期 Spec 只代表**已发布**的当前行为；历史版本只供追溯。发布成功后 Topic 立即封存、不可再实施，可处于短暂的“待搬移归档”状态；此时长期 Spec 已生效。
- 归档工具验证结构、来源、完成证据和版本顺序。它不能仅凭文本差异判断语义合并正确，合并结果需要独立审查。
- 不因 Ticket 勾选、文件存在或一次静态检查就推断功能已实施、发布或部署到任何宿主。

## 行为与验收

### 长期 Spec 发布

1. 使用者能直接打开长期 Spec 的稳定路径，读到同一能力当前完整的行为、验收和不变量；无需从多个 Topic 增量文件拼接。旧版留存且不可作为当前要求误读。
2. 发布前先准备完整候选文本，对照上一长期 Spec 与本次 Topic Spec，明确新增、修改、移除的行为及保留的不变量。独立审查后才能发布。审查记录须给出审查者标识、结论、审查报告路径、来源 Spec 哈希、旧长期 Spec 哈希和候选哈希；发布入口核对这些值与实际文件一致，并要求结论无未解决问题。记录能证明审查覆盖的字节与结论，不能仅凭自填标识证明审查者独立，独立性仍需由工作流程核实。
3. 发布入口先预览来源、目标、旧版和候选哈希。应用时若候选、旧版或来源内容改变，拒绝发布并要求重新预览与审查。
4. 只有来源 Topic 的实施工作已完成，所有纳入范围的验收仍已满足，且没有活动实施会话时，才能发布。每张实施 Ticket 的完成证据须对应其冻结的 Spec 和 Ticket 定义；历史工作缺少可验证证据时显示缺口，不凭状态字段自动放行。
5. 单一行为 Spec 的 Topic 只发布一次。后续变更另建 Topic；长期 Spec 顺序递增并指向不可变的上一版。发布先进入封存中状态，成功写入长期 Spec 后成为“已发布、待搬移归档”；两种状态均禁止新实施。中断时能区分尚未生效与已生效，并能重试或明确恢复，不留下“Topic 已封存但长期 Spec 未更新”的无说明死状态。多 Spec Topic 必须先完成上述拆分，不能只发布其中一份后封存整个 Topic。

### Topic 归档

6. 使用者可预览一个 Topic 的完成状态、长期 Spec 发布状态、目标归档路径和待保留文件；任何未完成、冲突、活动会话或尚未合并的行为 Spec 都阻止归档。没有实施 Ticket 的文档或研究 Topic 可以归档，但必须有明确的完成记录、来源及“无待发布行为变更”声明；不得把行为 Spec 伪装成此类 Topic 绕过发布门禁。
7. 应用归档后，整个 Topic 从 `.agent/work/<topic>/` 移至 `.agent/archive/<topic>/`，活动总览不再列出它；归档列表和明确路径仍能定位历史文件。归档不删除或重写原始证据。
8. 归档后的 Topic 不能重新进入实施。新需求或修正须建立新 Topic，并以当前长期 Spec 为基线。重复归档、目标已存在、路径越界、符号链接及归档中断必须安全拒绝或可恢复。
9. 归档前检查会因目录移动而失效的活动引用。归档记录保存受校验的旧前缀 `.agent/work/<topic>/`、新前缀 `.agent/archive/<topic>/`、Topic 文件清单与哈希。归档读取入口只将**该 Topic 内**的冻结 `spec_ref`、Ticket 路径和会话来源路径映射到对应归档文件，逐项核对哈希；外部路径按原路径验证或明确报告失效。原始 Ticket、journal 和收据字节不改写。不得用活动实施入口的 `verify_run_sources` 直接校验搬移后的历史 journal，也不得把它们判为当前可实施会话。

## 不变量与失败边界

- 同一能力在任一时刻只有一个当前长期 Spec；Topic 的变更尚未发布时，不得悄悄改变它。发布成功即切换权威，不以目录搬移完成为生效条件。
- 旧长期 Spec 的字节和来源记录不能因新版本发布被覆盖；历史引用须指向不可变路径。
- 归档路径映射只对该 Topic 的历史只读查询生效，不能让活动 Ticket 或新会话通过重定向使用旧的冻结来源。
- 完成状态、验收、来源文件和运行证据在预览与写入间发生变化时，发布或归档必须失败并可重试。
- 归档不等于部署或宿主安装完成；这些状态独立报告。
- 本地文件可被绕过 runtime 直接修改；归档入口应检测可观察的漂移，并明确人工语义审查的边界。

## 已确认的承重决策

1. 用户明确要求长期维护、可直接阅读且以此为准的 Spec，因此将长期 Spec 作为**已发布行为的唯一当前权威**；Topic Spec 只约束未发布的实施变更。避免多个当前文本相互矛盾，验收由直接阅读当前长期 Spec 和回溯历史版本完成。
2. 用户要求归档已完成 Topic。本轮采用移动完整 Topic 目录并保留全部原件，使活动与历史工作在文件布局上可区分；路径迁移必须先检查引用和中断恢复。长期 Spec 发布与目录搬移是两个可恢复的状态转换，发布后的封存 Topic 不再属于可实施工作。
3. 语义合并由 Agent 起草、独立 Agent 审查，runtime 负责可机械验证的准入与原子状态，不把 Ticket 状态或文本 diff 当成语义正确性的证明。

## 验证策略

审查应覆盖首次发布、后续修订、行为删除、来源或旧版漂移、部分完成、验收重开、无完成证据、并发新会话、发布中断、重复发布、归档后查找和重新实施拒绝。静态门禁只能证明代码与格式状态；实际项目试用须记录合并前后当前行为能否被准确重建。

## 依据与未知

- 来源：本次对话中用户提出的长期权威 Spec、已完成 Topic 归档和每项独立审查要求。
- 当前仓库已有版本化 Topic Spec、Ticket 血缘、实施会话、`work-overview` 与 `prune-releases`；这些不等同于长期 Spec 或 Topic 归档。
- 对于没有 runtime 完成记录的旧实施 Topic，需另行设计可审核的人工补证格式；当前命令在缺证时拒绝发布和迁移。无实施 Ticket 且无待发布行为变更的文档 Topic 使用独立完成记录，不要求虚构实施会话。
