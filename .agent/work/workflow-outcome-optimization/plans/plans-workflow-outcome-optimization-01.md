# 诊断与 SPEC 工作计划

来源：本轮用户请求；目标是判断 workflow 对正确、完整、真实意图交付的贡献，提出删/改/加与加载结构方案。授权范围是并行只读分析、必要本地探针、保存诊断与 SPEC；本轮不实施正式变更。

1. 核对仓库/profile、当前 runtime、历史决策与原会话；固定源码和证据版本。
2. 建立所有 Skill 与资源/策略/组合 inventory，分三个并行工作单元检查正文、可达依赖与 runtime，不将安装复制当实际读取。
3. 对可证明的机械缺陷做临时公共 CLI/精确函数探针；仅在临时目录运行，不改源码。
4. 主 Agent 合并跨组根因，以 observed 优先、static 路径其次；保留好的机制与证据不足项。
5. 形成完整候选行为 SPEC；新上下文独立审查事实、影响、内部成立及未决语义，最多一次差异复审。
6. 固定审查单元 finalize 确认 match，保留来源 manifest、报告和可复现证据；只交付诊断/方案/SPEC。

分工角色与完整覆盖记录见诊断报告和 skills/rules/runtime 三份报告。用户本轮允许多对象并行，优先于审查方法“一次只深审一个”的默认次序。用户明确止于 SPEC，优先于 to-spec 默认自动继续拆 Ticket 的 chain。

后续实施、实际模型对照、提交/发布/安装各是独立阶段；不能把本文件当它们的完成记录。最终状态由本 Topic 的验证收据和用户确认决定。

## Revision 2 补充阶段

用户接受追加建议后，三组并行完成需求/写作、准确率/实现/排障、完成率/自动化审核；主 Agent 统一 runtime 与安装边界，形成完整 revision 2。七项标准采用机制、真实任务和可观察结果，不另增七套流程。源审查已 finalize match；新增合同交新上下文独立设计审核，随后检查唯一 current、AC 编号、条款映射及改动范围。实施、完整测试与能力试点仍未启动。
