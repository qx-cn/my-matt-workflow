用户接受前版及追加建议后，三个子 Agent 并行审核需求/写作、准确率/实现/排障、完成率/自动化，主 Agent 合并为完整 revision 2。基线 HEAD `c10906c`，源码与历史方案冻结单元 `29b34fc74cc270435dc400eeffb045142e563c21ed6048633048050732a4abec`；finalize 为 match。这里是文本与代码路径分析，没有新的模型效果对照。此前复现的 runtime 缺陷保留原证据等级，本轮没有重跑或伪称新事故。

## 关键结论，按影响排序

1. **完成率必须按真实交付计算。** 更严门禁能减少错误完成，却可能留下更多未修复 blocked；它们不能计入成功。revision 2 第 8 节按用户指定阶段、固定预算、独立验收、全部分配任务定义分子分母，分开首次正确和返工后正确。只要求 Spec 的任务到 Spec 即完成，开发任务只出 Spec 不算。
2. **排障的固定门槛阻挡证据获取。** `my-diagnosing-bugs:62` 允许尚未复现时读“日志、配置、Git 历史、现有测试、调用链”，`:75` 又要求复现命令出现前阅读代码就停止；`:72/:93/:97` 分别要求秒级、完全最小化、固定 3–5 假设。这是可证明的冲突与静态适用性风险，尚无频率实测。改为按区分原因的证据价值推进，保留症状匹配、因果检验、原场景回归和未知披露，见 §4.8/AC23。
3. **测试报告把可查事实误列为缺失。** `my-test-report:76` 禁止从“测试名、代码或预期”补验证点，过宽地排除了代码中实际输入、断言和替身边界；作者动机与实际通过确实不能这样推断。拆分静态内容、动机和执行证据，见 §4.7/AC25。前轮已发现，本轮补齐 Spec 承接，不是新事故。
4. **自动化与安装精简必须划清身份和授权边界。** `installer.py:909` 的 verify 在 `:915–916` 取锁之前，简单传递该布尔值会产生漂移窗口；现有 manifest 也没有完整检查成功 receipt。共享受保护内容的验证，无变化免打包/免重写与跨调用免测试分开，见 §4.9–4.10/AC19–22。机械 next_command 不创建阶段授权。

### 精简的止点

runtime 先合并事实生产与判断，保留 Ticket/batch/quick 及审查 scope 差异；安装先减少同操作重复，再改投影与无变化短路。首版不建设跨进程缓存、测试选择平台、批次状态迁移或通用流程引擎。Wayfinder 会话硬停保留为行为试点候选，不借此次分析扩成自治实现。

新规则预期改善具体失败路径，无法保证七项能力全部上涨。按同模型、工具、预算和任务初始状态比较；分开正确率、返工、用户纠正、无效等待、运行成本。全部七项共用试点方案，不变成每个任务七份必填表。
