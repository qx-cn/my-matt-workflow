# 诊断与修改方案

**结论：这套 workflow 在帮助 Agent，现有证据不支持整套推倒。它的几个关键实现和规则却会降低可靠性：把已经登记的失败当作普通记录，把过程形状当成质量，把调用前提留给下一阶段补。先修这些问题，再做有证据的减法。**

本轮是诊断与 SPEC，不是候选版本实施。新版本相对普通强模型的净收益尚未通过同条件对照证明。

## 范围、分工与证据

按用户指定的当前仓库审查，基线 HEAD `c10906c`。宿主当前 runtime 为 `20261002-093849`。源码、测试和选定历史工件固定为 522 文件的 review unit，content_id：`36ce314358fac1f680ba8c536ef07e1f594964478395a56578923248445b91b0`。先建立 inventory，再按三个互相可交叉读取的分工并行深审；主 Agent 合并根因与方案，另派新上下文审查 SPEC。

| 分工 | 覆盖 | 责任与结果 |
|---|---|---|
| Skills 审查 | 32 个 Skill 正文、宿主配置、可达辅助文件 | 检查实际入口、调用契约、存在价值、测试方法与局部门槛；完整逐 Skill 归宿表另附 |
| 共享规则审查 | 39 个资源/策略/组合对象 | 检查权威、读取条件、分发、协议冲突与表达规则；完整逐资源归宿表另附 |
| runtime 与证据审查 | 实施、批次、审查、完成、测试与度量的代码/测试；历史工件 | 使用快照派生的临时项目复现当前可达行为，区分机制和模型效果 |
| 汇总与方案审查 | 交叉影响、历史原会话、SPEC | 将同一失败链合并；独立检查事实、兼容、承重选择与未知 |

证据分为：**static**（原文与代码的确定影响路径）、**observed**（本轮实际探针或可定位历史运行）、**comparative**（相同模型/条件的效果对照）。本轮没有 comparative。对“能力较强的模型已经会做什么”不作未经验证的推定。

源文件行号对应审查基线。分组报告的静态 KEEP 表示职责有可解释价值，INCONCLUSIVE 表示效果未知，两者不矛盾。包装进安装件、被链接、实际读取、常驻上下文是不同状态，不能用文件总量推断模型一直加载全部材料。

## 最影响结果的问题

### 1. 已经发现阻断问题，runtime 仍允许当前 Ticket 完成

**证据：observed，公共 CLI。** 当前设计明文要求：“`spec-challenge` 一律不由 Agent 自行裁决”（既有 quality Spec:120）；`resources/review-loop.md:49` 要将挑战交用户决定。但 `tools/workflow_lib/batches.py:108–138` 只把自审 findings 写入记录，`:141–147` 只检查内容绑定与六节齐全。`ticket_completion.py:28–45` 的普通批次 finish 不检查这些未解决发现。

本轮分别登记 `blocking/correctness` 与 `blocking/spec-challenge`，定向测试通过后查询状态，仍得到 finish 建议，调用 finish 成功并提交。探针只是注入合法结构的发现，不是在证明测试夹具本身存在真实业务缺陷；它准确证明已知阻断没有参与状态决策。

结果影响：Agent 可能已经承认当前实现错误或 Spec 前提失效，却继续按错误定义推进后续 Ticket。批次审查有机会补救，但不应该是已知问题的第一道有效阻断。

**改动**：机器已登记的发现必须参与 finish/next_command。未解决 blocking 在当前批准范围内修复并重新测试/自审；spec-challenge 即时走既有裁决路径；已修复历史与当前未解决状态分开。不用新 gate 评判自由文本质量，也不把每个 advisory 都改成用户批准。

**预期改善**：避免“知道错了仍提交、以错误定义继续开发”。优先级最高。

### 2. 基线缺环境会吞掉当前已经执行的失败，允许批次收口

**证据：observed，公共 CLI。** `batches.py:203–204`：基线 unavailable 时 `unverified.append(...); continue`，不检查当前执行结果；`:230–234` 只据 `new_failures` 等判断通过。

本轮临时 Git 项目第一次全量命令缺依赖、无法执行；当前同命令恢复为真正的 unittest，断言失败且退出 1。定向测试通过，使用仓库测试 seam 注入合法格式的 review pass 后，batch test 输出 `new_failures=[]`、`known_failures=[]`，batch close 成功。摘要只列“未验证项”，已知问题为空。

严谨边界：没有可比基线，不能证明这个失败是本次新增；但是当前失败是已经观测到的事实，不能称为仅未验证。review pass 是脚本夹具，不代表实际独立模型审查忽视了故障。

**改动**：当前结果与基线可比性分开。当前实际失败且无可比基线，明确记录失败并阻止普通收口，直到修复通过或取得可信基线证据。保留可证明的旧失败豁免、完整不可运行的环境缺口与已修复的部分执行处理。

**预期改善**：完成声明更可信，不通过掩盖当前测试失败获得“绿灯”。

### 3. 首次 triage 新 Bug 没有 Spec，却直接进入必须有 Spec 的 Ticket 阶段

**证据：static，完整调用路径。** `my-triage/SKILL.md:54` 在 brief 确认后“随后调用 my-to-tickets”；`composition/manifest.json:84–87` 固定这个 handoff。`my-to-tickets/SKILL.md:12` 却要求“从当前有效 Spec 形成……切片”，`:14,22` 要源 Spec 血缘；triage 的 brief 模板没有创建版本化 Spec 的动作。

最小情形：配置有效的 local 项目，首次收到已复现的新 Bug，用户确认 brief 并同意转开发，项目没有覆盖此工作的 current Spec。下一阶段合规地停住，或只好造血缘/套用无关 Spec。问题不是再问一次能补齐的。

**改动**：无匹配 current Spec 时 confirmed brief → to-spec → to-tickets；有合法匹配 Spec 时复用，变更其定义时正式修订。同步调用清单和交接授权，复用已确认输入，不重新访谈。

**预期改善**：新入口可以走完全链路，同时保持可追溯的实施边界。

### 4. 修复已经通过，仍因为修改同一行或体积变化被硬停

**证据：observed，精确快照函数探针；未跑完整 review-stop CLI 链。** 原文 `review-loop.md:28,30` 把相邻修复行重叠与超过第一轮 1.5 倍体积作为停止条件。`review_loop.py:98–107` 没有要求当前仍存在 blocking；`ticket_review.py:338–365` 在登记结果后执行停止判断。

本轮对实际函数给出 pass/零发现，分别构造同一行的第二次修复与体积越阈值，仍得到需用户处理的停止理由。这两个信号不能证明实现失败，也不能证明授权变更。

**改动**：保留四轮/三次修复和文档一轮全面审查加一次复审的成本边界；把几何信号变成诊断。真实定义冲突、证据缺口、无进展和预算耗尽按具体失败路径处理。补负向回归测试或恢复原范围所需场景，不自动算新增需求。

**预期改善**：修好后能继续，用户不替 Agent 裁决普通修复；仍避免无止境审查。

### 5. 测试规则限制证据形状，还排除了必要的独立持久化验证

**证据：static；历史失误支持优先验证此类别，不证明现版 Agent 已照此失败。** `workflow-delivery.md:24`：“多条验收不能共用同一个测试”；`my-implement/SKILL.md:10` 同样要求不共用测试。`my-tdd/SKILL.md:26` 又将“不经接口而查询数据库”归为反模式，辅助例子把 createUser → getUser 当正确验证。

失败机制有两种：一个真实关闭/重开/恢复流程的多项独立断言被迫拆成局部 case；读写接口共用错误缓存/编码时彼此读回会绿，但真实存储不满足契约。测试函数数量和入口一致性都不是独立事实源。

**改动**：验收 ↔ 可定位断言/观测，多对多映射。持久化、事务、约束、脱敏和恢复本身是契约时允许独立存储核验与 close/reopen。修改正式 adapter/router 时验证实际接入，不能只测内部 helper。测试替身不自动成为新 port 的价值证据，统一 seam 合同。

**预期改善**：鼓励足以揭露真实失败的场景，减少为了映射而造测试；保留行为测试、独立预期值、最小反馈和非 TDD 合理例外。

### 6. 同一行为存在不同协议和许可答案

**证据：static。** `user-intervention.md:3` 说“已确认的授权继续有效”，`:8` 又说外部写“每次都问”。merge policy 要方案再批、出现新不确定性立即停止；humanizer 要“未确认不得写入”，test-report 又强制嵌入 humanizer。共享规则明明已经说润色不是写入前强制步骤。

实施协议也有冲突：`work-scope.md:3` 要“多 Ticket 做 Topic test/review”，现行 implementation-session:7–9 已改成 batch test/review/close、Topic review 可选。旧 work-scope 仍由 implement → tdd 的可达 seam 分支读取。公共 CLI 的最后一张 finish 也返回过早的 Topic complete，门禁随后正确拒绝，造成额外命令摩擦。

**改动**：统一授权只判断具体动作是否已有授权、是否出现新范围/取舍；移除各入口的二次门槛。实施顺序只由 runtime/统一适配定义，所有状态与回执使用同一下一步判定。自动审批和未授权外部写边界继续有效。

**预期改善**：任务同意后可以顺畅完成，不在不同 Skill 中取得不同答案；减少走到无效命令再回头查状态。

### 7. 上下文管理和辅助表达规则需要按真实用途收窄

**证据：static；实际加载量和成本未知。** context-hygiene:3 要求访谈/Spec/Ticket 在“同一个未中断上下文”，进入实施又要求新上下文；主链没有消费该指针，handoff 才读取。ask-matt:22–28 又按 first-match 先以“空间还够 → 继续”，后面才处理换宿主/交接。显式交接请求可能被容量分支覆盖。

本轮用户明确规定按读者成本选表达；教学 visual-communication:3–13 仍按题材类型“默认必须”图示，none 可被机械阻断。架构方法还统一禁用 service/API/boundary 等项目固有词，降低与代码和 ADR 的核对能力。

**改动**：基于容量、分支、职责与恢复做 checkpoint，当前批准定义和持久状态可跨上下文恢复。交接需求优先于容量判断。人类文档按理解成本选图/表，Agent 文档按明确约束与可解析性；已有领域词保持原文。writing/rendering/humanizer 只在产物适用时读。quick 不填无关空节，standard 保留风险覆盖并引用证据。

**预期改善**：降低长任务断链与格式驱动的无效工作。没有读取 trace，不宣称已量化上下文节省。

### 8. 度量能记录工作，却不能单独回答“是否更常一次做对”

**证据：static + 既有执行记录。** 现有 quality_metrics 记录发现、修复、审查来源、用户介入和逃逸，方向正确；逃逸数缺任务暴露量、观察窗口与引入版本的充分绑定，未登记不能算零。旧评估记录也明确承认 fresh-agent 对照未完成。

**改动**：先做小规模真实任务比较，冻结模型/档位、版本、输入、环境、权限与隐藏验收；以首次完整正确、错误完成、重要逃逸和返工为主，成本为副。附观察窗口和任务数，可先手工补记录，不建大评测平台、不为每条资源添加假语义测试。

**预期改善**：以后按结果决定删/改/加，避免“短了、测试多了、发现多了”成为收益替代品。

## 应明确保留的部分

- **需求来源和两个对齐点**：避免把类比/方案误当目标；代码可查事实由 Agent 查，普通细节不追问。已完成确认可复用。
- **current Spec、修订血缘与已完成历史**：完整最终态比补丁叠加更低歧义；错误定义修订，历史完成通过补偿保持可追溯。
- **现状断言与设计影响核验**：事实错会使测试和审查一起沿错误 Spec 通过。当前设计四部分报告直接针对实际失误，应保留。
- **逐 Ticket 自审 + 批次独立审查**：不同职责，独立审查能核实正式调用路径和跨 Ticket 集成；不恢复所有 Ticket 多轮独立审查。
- **真实影响面、Spec challenge 和可达 finding**：不要求缺陷一定锚定验收编号，也不因 Spec 写了错误规则就放行。
- **内容绑定、快照、身份、退出码和恢复状态**：强模型也不能凭记忆证明自己审的是当前内容；机械保证交给程序。
- **测试 oracle、最小反馈和整理**：独立预期值/实际行为比镜像实现更可靠；现版已有等价验证例外，不用重新发明全面流程。
- **逃逸记录与未知状态**：没有可靠记录标未知；已派审查者不等于取得审查结果，源码 check 不等于真实效果。
