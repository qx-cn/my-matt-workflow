## 1. 任务完成率

**KEEP：恢复所需事实已足够具体，勿再加通用表单。** `skills/my-handoff/SKILL.md:9–11` 要求“先运行 runtime status”“提交、远端、release 与各宿主安装状态按实际证据分别说明，未知保持未知”。这直接防止接手者按叙述误判完成和重复施工。r1 §4.1/4.2/5.3 已修阶段衔接、持久授权与跨上下文连续性；继续保留。

**真实缺口：状态被标 complete 与预算内真正交付未被充分分离。** r1 §8:210–214 有真实任务对照与缺陷/成本记录，尚未把成功分母、首次成功和最终成功写成明确判据。更严失败门禁可能减少假完成，却增加未修复 blocked；不能据此宣称完成率提升。

建议正式条款：
- 真实正确交付 = 在预先确定的时间/成本预算和授权范围内，完成用户指定阶段的必要产物，且通过独立于实施结论的目标/验收核查。用户只要求 Spec，则合格 Spec 即该任务完成；实现任务只出 Spec 不算完成。
- 对照保留所有分配任务；未完成、超预算、环境阻塞、用户输入缺失分别标注，不能为提高比例删除。外部环境因素另分层解释；比例同时给分子/分母。
- 分别记录首次独立验收通过、修复后最终通过、错误完成声明、未完成及返工成本。被门禁正确挡住是防错成功，不是交付成功。
- 用现有 metrics 加轻量人工记录即可，不建设评分平台，不把所有样本都变成新的发布前强制关卡。

验收场景：a) 当前测试失败被挡住后仍未修复：错误完成降低、真实完成不计成功；b) 能在预算内修复继续且验收通过：计最终成功，首次不通过；c) 用户只要求 Spec，正确停止：计 Spec 阶段成功，不能因未实现判失败。

## 2. 自动化

**KEEP：按目标保持阶段边界，有依据继续而不自动扩张。** `skills/my-wayfinder/SKILL.md:15` 原文“默认情况下，Wayfinder 是规划”；`:75` 明确“当前流程未批准下一阶段时只建议……不得直接跳到实现”。`my-handoff:9` 持久状态恢复、Wayfinder `:73` 写入前重读避免覆盖，也应保留。

**真实缺口 A：机械可执行下一步不等于当前请求授权下一步。** r1 §4.1 有阶段止点，§4.2 要求成功 mutation 返回可执行 next_command。两者应显式衔接，否则为了连续运行而追着下一步越过“只出 Spec”的授权界线。

建议条款：共享状态 evaluator 输出机械允许动作、证据缺口和建议命令；调用 Skill/Agent 同时遵守用户目标与阶段止点。状态可执行性不能创建授权。命令执行前仍在原写入边界复核当前事实，旧 status 不作为执行许可。无需让 runtime 解析自然语言授权或新增授权数据库。

验收场景：最后 Ticket 后 next_command 正确为 batch test；恢复时旧 next_command 已因内容变化失效，mutation 必须拒绝旧证据；请求只到 Spec 即使后续 to-tickets 合法也停止；已批准完整实施范围内普通修复/继续不重复询问。

**真实缺口 B：runtime 重复规则实现增加自动化分叉。** 已接受扩展报告 R1–R3 证明 next/action、三套 test runner、快照/receipt 核验重复，适合纳入 r2 最小范围。统一的是事实生产和判定谓词；Ticket 全通过、batch 基线比较、quick 验收，以及 Ticket 下游定义/branch HEAD/artifact 所有权各自语义必须保留。不可拿代码减少比例代替质量验收。

**候选而非确证缺陷：Wayfinder 会话硬停止。** `skills/my-wayfinder/SKILL.md:48`“每个会话绝不解决多于一个 Ticket”，`:61`“本会话不亲自解决其他 Ticket”。此前 skills 审核:75/116 已准确标为候选，尚无真实频率证据。它可能阻断用户已明确要求连续解决的多个低成本决定，也可能正符合用户逐决定参与方式。建议保留默认分步；只有用户明确要求同一地图范围内继续决策、下一决定不需新增用户输入且预算允许时，允许继续。不得把地图的范围内决定授权扩成实现/外部写入授权。若不希望增加本轮范围，写入行为试点而不立即改规则；不新增普遍 stop_after 字段。

自动化评价：记录合法且必要步骤的自主完成比例、无效 next_command、重复许可请求、无因停顿、恢复信息丢失、越阶段/越范围事件、实际工具/等待成本。工具次数减少不等于自动化提高；无权限操作为零是底线。

## 3. 安装升级与 runtime 精简：建议纳入 r2 的精确边界

### 3.1 无变化 deploy：免重写与免测试是两个决定

源码依据：`tools/workflow.py:367` 总是先 `_run_all_up_gate`；`:376–389` 再核实当前 release、判断源码等价，必要时 build。`release.py:762–764` 对稳定快照再次 source_gate。`release.py:525–534` 返回 manifest 只有 upstream、技能/runtime 清单、组合/消费/目标清单，没有完整测试通过 receipt。

因此既有 release/input digest 不足以证明当前检查条件已通过。r2 首版应承诺：
1. 变化源码的一次正常成功 deploy 仅对实际打包稳定快照执行一次完整 check；源码在门禁期间变化导致重试应单独记录，不被“恰好一次”禁止。
2. 无变化时免 source-match 临时完整打包；目标实际托管内容、目标投影与 release 一致时返回 current、免安装重写。没有有效成功检查 receipt 时仍执行一次完整 check，不承诺跨调用零测试。
3. 若要在 r2 首版同时承诺跨调用跳过完整 suite，必须把最小 receipt 协议纳入正式范围和失效测试：绑定规范化路径/内容（增删和链接）、测试/配置、build/validator/protocol、Python/必要依赖环境、命令结果与 upstream 参数；结果必须完整成功，未知/旧格式/中断/变化不能复用。产物身份摘要与测试证据身份分离。不要以“无需缓存平台”为由省掉这些字段。

推荐本轮采用前两点、将第 3 点列为可选后续，避免为了减重复引入新持久协议。纯 Skill 文本变更仍可保留一次 full check；不建设受影响测试选择器。

### 3.2 同操作验证复用必须在实际保护边界内

原文：`installer.py:909` 外层 verify，`:915–916` 才取得 REFERENCE_LOCK 和 install lock，`:706` 锁内再次 verify，`:732 → :190` 验旧安装引用 release。第一与第二次可改为锁内一份权威结果；旧安装可能引用不同 release，不能直接省掉不同包验证。仅把锁外 bool 传入锁内不满足约束。

建议条款：同一受保护操作按 release 内容身份复用已验证上下文；身份或保护区间变化重新核验。不得承诺所有同调用校验都只 hash 一次——最终 staging/installed bytes 是不同对象，保留。doctor 只读调用可按稳定包身份复用，不掩盖执行中漂移；跨 host 各自锁与结果独立。

保留 `installer.py:795–800` staging 清单、`:859–867` 最终 Skill/runtime 清单、`:892–898` 恢复。SOURCE/RELEASE/HOST 分别报告，不折叠成一项“成功”。

验收场景：相同 release 多 host 共享包验证但逐 host 内容核验；旧 host 引用不同包分别核验；两次检查之间篡改/清理不能被锁外缓存漏过；宿主实际文件被改，即使 release_id 相同也不能 current；未知同名目录和中断事务保护不退化。

### 3.3 结构精简应有止点

纳入：统一状态谓词；共用执行事实内核与快照/receipt 完整性核验；隔离 legacy adapter 与 build/install 职责；保留 CLI alias；确定性投影清单与旧三宿主字节输出等价。

暂不纳入：双份 batch 存储迁移、通用 workflow DSL/服务、跨进程缓存平台、按变更选测试系统。不得为追求更短源码削弱定义/内容绑定、失败事实、作用域语义、独立 provenance、事务和完成历史。

## 4. 本组结论

最可信的改善是减少假完成、状态分叉和无谓停顿，以及安装中的重复测试与复制；真实完成率和自动化净收益仍需固定条件任务对照。r2 应把现有好规则作为 KEEP，与新增机制、评价标准分开；不把七项标准变成七套每任务必填清单。
