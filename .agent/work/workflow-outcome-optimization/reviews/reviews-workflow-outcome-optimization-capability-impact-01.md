# 当前 Spec 对七项交付能力的影响评估

审查对象：固定审查单元（持久来源索引见 `../evidence/extension-source-manifest.json`），content_id `e37074a3d70f4215d62fdb0f8a0cae14138c5477f7f6b2afa1618de6e845ecea`。只读取其冻结的 Spec 和相关方法正文，没有运行模型对照实验，没有修改正式 workflow。以下行号指冻结文件，与该快照的 source_path 映射对应。

## 结论

当前 Spec 最直接改善的是**已知失败能否真正阻止错误交付、测试是否覆盖真实故障、批准后的工作能否连续推进**。它调整 Agent 的决策条件、信息供应和反馈，不改变模型本身的知识或推理能力。减少干扰有可能让现有能力发挥得更好，但不能据此声称所有能力或一次做对率已经提高。

应区分两种完成率：

- **真实正确交付率**：在固定时间/成本上限内，满足用户目标及独立验收的任务占全部分配任务的比例。
- **状态 complete 比率**：runtime 标 complete 的任务比例。更严格的门禁短期可能让此指标降低、blocked 增加，却减少错误完成声明。被挡住但尚未修复的失败，不能计作成功交付。

Spec 自己已经明确：“没有对照结果时不声称提升成功率或一次做对率”（AC17，192 行）；“相对强模型无本包 baseline 的收益”仍未知（220 行）。因此下面的判断都是作用机制和待验证预期。

## 排障的一个最小补充方向

这不是新增实验结论，而是本轮阅读冻结正文得到的文本冲突：`skills/my-diagnosing-bugs/SKILL.md` 第 62 行允许未复现时继续读取“日志、配置、Git 历史、现有测试、调用链”；第 75 行却写“在这条命令存在前就开始阅读代码、构建理论，立即停止”。读代码往往正是构造有效复现的前提，Agent 会因两条规则选择不同下一步。

此外第 68–73 行要求反馈循环“快速：以秒计，而不是分钟”“可由 Agent 运行”；第 93 行要求最小化到每一个剩余元素都不可缺少；第 97 行强制先生成 3–5 个假设。这些可以解释对慢恢复、间歇或明确单根因缺陷的额外负担，但尚未用新真实任务证实发生频率，不能直接按收益已证实删除。

最小补充是将现有阶段合同改为：

1. 允许读代码、日志与配置来构造复现，并显式区分观察、假设和已证明结论；没有复现时保持证据限度，不做无依据修复。
2. 复现速度、确定性、最小化程度按该故障能达到的条件与投入收益判断；先争取能区分对错的信号，不把“秒级”作为普遍硬门禁。
3. 假设数量由现有证据决定；存在竞争解释时设计能区分它们的实验，不为凑 3–5 个制造猜想。
4. 保留用户症状匹配、可证伪预测、原始场景修复后复验和回归证据。

需求理解与写作已有较明确的方法，当前没有必要再加一层通用清单；先通过上述真任务测出遗漏，再只改造成失败的规则。

## 验证口径

沿用 Spec 210–214 行三条件试点：宿主/项目原规则而无本包、当前版、候选版。固定模型/思考档位、工具、权限、任务初始快照和时间/成本；条件隔离，避免后跑者看到先跑答案，评估者只拿用户目标与隐藏验收。

优先报告绝对任务数、真实正确交付、错误完成声明、首次验收通过、返工/逃逸缺陷、用户介入与无效等待、成本。把失败分为错误需求、实现错误、证据不足、环境阻断和流程阻断，才知道收益来自哪里。少量任务只能证明案例改善，不能给七项能力承诺百分比。

最合适的预期表述：**当前 Spec 有望提高交付可靠性和流程连续性，较明确地减少几类已知错误；对需求理解、文档写作和深层排障的增量更有限，需要真实任务证明。**
