## 1. 准确率

### KEEP：独立 oracle、实际影响和 Spec 挑战

- `skills/my-code-review/SKILL.md:46`：“实施者声明与理由不能替代核实或降低严重度。”同段要求独立找调用者与消费者；第 48 行“不以‘Spec 要求如此’为由放行”。这能拦下局部代码符合文件要求但实际系统不可用的结果；不应因缩短 workflow 删除。
- `skills/my-code-review/SKILL.md:55–59` 限定 finding 必须有实质影响、在范围内且能证明失败路径。它减少想象性缺陷和无效修复；保持此准入，不能为提高发现数放宽到猜测。

### 修改：r1 已覆盖的证据缺口应落实到源正文和例子

证据等级：禁令是静态事实；这些业务漏检是可达风险示例，未在本轮证明其真实发生频率。r1 已复现的 baseline 当前失败和 self-review blocker 漏门禁属于已观察 runtime 缺陷，应继续保留原证据分类。

### 建议验收条款

- 含持久化、脱敏或恢复契约的任务，可以结合公开入口、独立存储观察和 close/reopen 提供证据；其中一层失败不能用另一层通过掩盖。存在“写与读共享错误源”的候选实现时，独立验收能使其失败。
- 对准确率的评价使用用户目标和独立预期，而非 Agent 自建测试通过率；把错误完成声明、缺失验收和逃逸缺陷分别记录。环境缺失记为未验证，不能删除该任务或换成“通过”。

真实任务：为已有 SQLite 服务增加敏感字段脱敏和恢复读取，保留一个测试环境中不落盘但返回正确结果的错误候选；从正式写入口→存储核验→关闭重开→真实消费者读取，并使用独立给定的边界值验收。此任务分别暴露 oracle 共错、持久化与接线遗漏，不要求每个普通小修都做存储检查。

## 3. Bug 排查能力

### 高优先级修改：消除证据获取与复现准入的直接冲突

`skills/my-diagnosing-bugs/SKILL.md:62` 允许“尚未复现”时读取“日志、配置、Git 历史、现有测试、调用链”；第 75 行却要求“在这条命令存在前就开始阅读代码、构建理论，立即停止”。第 13 行同样要求建立模块心智模型。Agent 需要读调用链才能选正确 seam 时，两条规则导向相反行为，可能停止合法调查或机械忽略其一。

修改为：构造复现本来就可以包括只读调查、临时探针与可证伪假设；分别标注观察、假设与有证据支持的结论。不要以是否先拿到命令决定能否读代码。无复现时保持“未复现”的证据界限，不将猜测当根因，不把未运行的原场景宣称为已验证。

证据等级：可直接证明的文本冲突；未宣称本轮观察到用户因此被阻塞。

### 中优先级修改：将秒级、完全最小化和固定假设数改为投入收益判断

- 第 68–73 行要求“确定”“以秒计，而不是分钟”“人只能通过 [固定脚本] 参与”；第 48 行又把 30 秒不稳定循环几乎视为无用。慢恢复、性能退化和必须由操作员触发的故障仍可提供有效反馈，不能因时长或接口形状排除。
- 第 52 行：“50% 概率的 flaky Bug 可以调试；1% 不行。”没有普遍适用的概率门槛；是否可诊断取决于每次成本、样本数、日志/统计信号与实验设计。删除阈值式断言，记录试次数、失败次数与测试条件，避免把少量未复现当已解决。
- 第 93 行要求删去任一剩余元素都会变绿才可继续。减少场景确有价值，但穷尽最小化可能比直接验证明确根因昂贵，且过度缩减可能丢失原场景差异；达到可区分解释的程度即可推进，保留原场景用于复验。
- 第 97 行：“测试任何一个假设前，先生成 3–5 个有排序的假设。”明确单因缺陷不应先凑数；存在竞争解释时才显式比较并用能区分它们的实验。第 9 行允许说明理由后跳阶段，确有兜底，但不能消除后文硬门禁的冲突和反复解释负担。
- 第 38 行“Bug 就已解决了 90%”是无依据的效果数值；可改成反馈信号通常能显著缩小排查范围，不保留固定百分比。

这些均为静态适用性风险，不是已量化的效率损失；删掉阈值时仍保留高价值机制，不能降成凭感觉改代码。

### KEEP：症状匹配、可证伪预测、正确 seam 和原始场景复验

- 第 70、83–85 行要求反馈匹配用户准确症状，避免修相邻 bug。
- 第 99–103 行要求假设能给出可证伪预测。
- 第 125 行指出浅 seam 无法证明跨调用方/全链路故障。
- 第 131–135 行要求 red→修复→green，并重跑“原始、未最小化的场景”；第 139–145 行清理临时埋点并保留结论。
- 第 62–64 行的授权范围和证据限度应保留，但“没有紧凑命令不得宣称已定位根因”应改成“结论强度由证据决定；没有原场景验证不得声称已验证修复”。例如明确的历史日志与静态可达路径可支持源代码缺陷判断，仍不能冒充已在原故障环境复现。

### 可直接进入 r2 的验收条款

1. Agent 可以在没有红命令时读取授权的代码、日志、配置与历史，并构造隔离探针。输出区分已观察症状、候选解释、排除/支持证据和剩余未知；不得把未复现写成已复现。
2. 只要现有实验能够区分相关解释，分钟级循环、低频概率信号或必要人工参与不单独阻止诊断推进。提高速度/确定性/最小化按风险与投入收益选择，不能以固定秒数、概率、模板或穷尽最小化作为所有 Bug 的门禁。
3. 假设数量由证据决定；单一明确候选可直接设计验证，有竞争解释时记录能区分它们的预测。不要求凑 3–5 项。
4. 能建立行为回归时保留修复前失败、修复后通过及原场景复验；不能建立时保留原因、替代证据与未验证范围。概率故障记录可解释的试验条件和观察，不以几次绿色宣称确定解决。修复已授权且证据充分时可继续，新增权限/生产动作仍依统一授权规则。

真实任务组：
- 慢恢复：Bug 至少需约 2 分钟的状态恢复才能触发；应保留有效分钟级信号，不能因秒级门槛停住。
- 间歇竞态：必须先读日志和调用链才能构造压力探针；结果用重复试验和因果干预评估，验收对修复后无症状证据的强度，而非固定复现概率。
- 明确单因：已保存失败输入能定位一处错误条件；无需造额外假设，但仍要检查原输入与邻界输入。
- 证据不足：只有不可用生产环境的症状报告；Agent 应继续可用只读调查、给出局限和所需证据，不猜测修复也不谎称完成。此任务“不宣布解决”是正确证据行为，但不计成功修复。

## 对 r2 整合的建议

将 Bug 排查作为独立工作流子节和改动包项，给上述四条合并为少量可判定 AC；别只在效果指标表出现“排障能力”。准确率与实现两项引用 r1 的既有规范条款及相应真实任务，补上首次/最终正确和独立验收口径即可。七项效果评价共用一次试点方案，避免七套评审门禁或要求每个任务运行全部场景。
