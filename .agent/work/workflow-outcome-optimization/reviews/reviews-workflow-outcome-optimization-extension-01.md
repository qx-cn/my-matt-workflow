# Runtime 与安装精简及能力收益分析

结论：runtime 和安装升级都有明确可精简的重复工作。现有 SPEC 最直接改善交付可靠性与自动化连续性；需求理解、文档写作和深层排障的增量较有限。安装升级优化尚未进入现有 SPEC，需要增补范围；不能把新增建议算成原 SPEC 已承诺的效果。

本轮三个子 Agent 并行检查 runtime、安装升级和七项能力，主 Agent 核对关键调用链并汇总。证据基线仍为 `c10906c`，固定审查单元为 `e37074a3d70f4215d62fdb0f8a0cae14138c5477f7f6b2afa1618de6e845ecea`。这是追加分析，没有修改正式 workflow 或运行安装、发布、完整测试及模型效果实验。下面的计数是限定正常路径的静态调用计数，不是耗时实测。

## 1. Runtime 可以怎样精简

最有价值的精简是减少同一规则的独立实现，让状态、测试证据和完成判断保持一致。代码行数本身不是目标。

| 已找到的复杂度 | 为什么值得改 | 最小改法 |
|---|---|---|
| Ticket、batch、Topic 各自判断下一步 | 一处修了，另一处仍可能返回无效命令；最后 Ticket 当前就可能建议尚不能执行的 Topic complete | 共用状态评估及门禁谓词，status 与 mutation 回执复用；实际写入前仍重查状态 |
| Ticket、batch、quick 三套测试执行 | 退出码、环境缺失、部分执行、中断、内容变化的修复容易漏同步 | 共用“执行并记录事实”的函数，保留 Ticket 全通过、batch 基线比较、quick 验收的不同策略 |
| Ticket 与 branch 重复校验快照、回执 | 相同保护维护分叉，容易漏检查 | 共用完整性校验，保留各自 HEAD、Spec、规则、下游定义和作用域要求 |
| 旧协议与新批次路径交织 | 增加主路径理解和恢复成本 | 隔离兼容 reader/adapter；先保留旧记录与旧恢复语义，后续有充分理由再迁移 |
| 几何阈值硬停、重复 CLI 定义 | 某些限制没有判断实际正确性，别名重复只是维护负担 | 按已有 SPEC 降为诊断；完全同 handler 的名字保留兼容 alias，内部只定义一次 |

代码依据：`ticket_implementation.py:356–397`、`batches.py:181–257`、`topic_service.py:273–355,469–487`、`ticket_review.py:287–324`、`branch_review.py:117–154`。详见 runtime 分工报告。

目标内部职责保持四项即可：状态与可恢复写入；证据生产；完成/下一步判断；CLI 和兼容适配。源码构建分发与项目执行分别组织模块，不需要新增服务、进程或通用流程引擎。

应保留内容与定义绑定、实际退出码和运行完整性、未解决阻断、真实审查来源、快照、目录所有权、失败恢复和完成历史。这些保护针对模型无法仅凭推理保证的事实。

批次的重复状态存储也值得后续整理，但涉及已存记录与恢复协议，风险较高。第一步只抽公共函数、统一判定，避免为精简先引入新格式和迁移工程。

## 2. 安装升级可以怎样精简

目前存在确定的重复：

- **源码变化的一次 deploy 会跑两轮完整 unittest。** `workflow.py:367` 先运行检查，随后 build 对实际打包快照再次执行 `source_gate`（`release.py:762–764`）。可以只保留后者，使检查与打包绑定同一稳定内容。
- **安装多层重复 verify_release。** 外层 `installer.py:909`、内层 `:706` 都验证；已有 v2 安装时又校验其引用包。
- **每次 release 验证重建三个宿主投影。** 正常情况下，同版本 deploy、宿主已有该版本 v2 安装，路径包含 4 次 release 验证，再加源码匹配临时构建，共 15 次整套 Skill 的宿主投影复制；实际安装 staging 另计。不同旧版本、错误恢复、清理等路径次数不同。
- **doctor 对多个宿主引用的同一 release 重复验证。** 源码匹配还通过临时完整打包计算产物等价。

因此推荐按成本和风险分两步：

1. **先去掉同一次操作的重复工作。** 固定快照只做一次完整检查；在正确的锁与内容身份边界内共享 release 验证结果；doctor 复用同包验证。保留安装 staging 与最终目标的检查，因为包正确不代表复制成功。
2. **再优化无变化更新与投影。** 通过完整构建输入摘要判断产物是否变化；相同且实际安装内容正确时直接报告 current，跳过重写。确定性投影可直接生成文件清单，避免为验证反复复制整套目录，但须证明与现有投影字节等价。

先不建设跨进程缓存平台。若后来复用持久测试证据，必须绑定源码、测试/配置、构建器/校验器、命令和必要环境身份；仅凭 Git HEAD、时间戳或 release_id 不够。正文变化是否可以只跑部分测试，需要先建立可靠依赖边界；第一版仍可保留一次完整检查。

推荐对外体验是一个已授权的更新入口，内部自动判断需不需要构建，支持共享发布验证后分别安装指定宿主，并明确输出 source、release、每个 host 的结果。它仍须保留包完整性、路径/symlink/托管归属检查、写锁、安装事务、备份回滚及安装后核验。现有 `install` 本来就不会重跑完整 unittest，这项不重复优化。

原 SPEC 明确不改变 release/install 交付机制，当前也没有完整定义上述精简的验收。因此安装去重、无变化短路、投影等价及故障恢复需要作为新增工作包。不能按原 SPEC 做完后就宣称安装升级已得到这些收益。

## 3. 七项能力能提高到哪里

工作流可以改善模型取得信息、选择动作、验证结果和继续执行的条件。它不改变模型基础知识与推理能力；最终效果需要在相同模型、任务初始状态、工具权限和预算下检验。

| 项目 | 当前 SPEC 的预期作用 | 尚未解决的部分 |
|---|---|---|
| 任务完成率 | 减少错误完成与无谓停顿，补齐 triage 衔接和恢复；有望提高预算内真实正确交付 | 更严门禁短期可能增加 blocked；被挡住而未修复的任务仍不算完成 |
| 准确率 | 当前失败不能被吞掉；多对多验收和独立存储证据减少假阳性，作用较直接 | 错误验收、错误 oracle、未发现的需求偏差仍可能存在 |
| 需求理解 | 复用已确认目标、保留来源、减少阶段间信息丢失，主要是间接改善 | 现有方法已要求关键歧义澄清；新版没有额外证明能理解更复杂业务 |
| 文档写作 | 按读者选表达、减少强制图示与重复、允许可靠恢复，改善适用性与可读性 | 论证深度、事实材料与编辑判断不会由减规则自动产生 |
| 代码实现 | 对接线遗漏、状态恢复、持久化与影响面问题有直接针对性 | 复杂算法、架构与性能实现能力不能普遍保证；最终正确和首次做对不同 |
| Bug 排查 | 验证 seam 放宽、负向回归不再误判新需求，有局部帮助 | 专门排障方法的阶段硬限制尚未被原 SPEC 明确修订 |
| 自动化 | 统一下一步、复用授权、允许跨上下文恢复，连续执行改善较直接 | 外部权限、环境和真实产品取舍仍需相应输入；安装收益须新增范围 |

新增发现的排障限制很具体：`my-diagnosing-bugs/SKILL.md:62` 允许尚未复现时读取日志、配置、历史和调用链，`:75` 却要求没有能变红的命令前阅读代码就停止。此外还要求秒级复现（`:72`）、完全最小化（`:93`）、固定 3–5 个假设（`:97`）。对于需要先读代码构造复现、慢恢复或间歇故障，这些规则可能造成额外停顿；目前是静态风险，未测发生频率。

最小补充：允许为构造复现而阅读证据；按故障与验证收益决定复现速度、最小化程度和假设数量；保留用户症状匹配、可证伪预测、修复后原场景验证。不为需求和写作另加通用清单，先用真实任务找具体缺口。

## 4. 建议实施顺序与验证

先完成原 SPEC 中已复现的正确性修复；在相同变更点统一下一步和测试证据函数。安装精简作为边界独立的新增工作包，先做同操作去重，再做投影和无变化短路。排障方法做一处针对性补充。旧存储格式归一和跨进程缓存留到有足够收益证据时。

验收既看正确性，也看成本：

- runtime：每个状态返回合法下一步，中断与部分执行不复用旧成功；三类任务保留各自成功语义，旧活动任务可恢复。
- 安装：源码变化 deploy 的完整 suite 恰好一次，检查和打包同快照；篡改必须被识别，投影等价，安装中断/并发/非托管同名目录保护不退化；实测 suite 次数、复制次数与阶段耗时。
- 能力：比较预算内真实正确交付、首次独立验收通过、错误完成声明、重要逃逸、返工、用户纠正和无效等待。complete 字段、文件数、问题数、审查次数都不代替结果。

建议先用少量匹配真实任务比较当前版与候选版，需要判断 workflow 净收益时加入无本包条件；每项能力的具体案例见能力分工报告。记录环境不可比与未完成数量，不能静默删除失败样本或给七项能力承诺未经测量的百分比。
