# 以正确交付为目标的 workflow 优化

本版供用户审阅诊断和实施方案，尚未授权实施。用户本轮要求止于诊断、方案和 SPEC，因此不自动拆 Ticket、开工、提交、发布或安装。本 Spec 规定候选版本的完整行为；具体实现留给施工阶段。它不替代既有 Topic 的有效 Spec，不修改已完成历史。

篇幅说明：本次同时覆盖 32 个 Skill、30 份 resource 文件、7 份 policy、组合/分发与 runtime，包含兼容和效果验证，因此不按单功能 Spec 的短篇幅处理。每项要求以交付风险为依据，不以字数减少作为验收目标。

## 1. 问题与目标

用户用本仓库驱动开发，希望更常交付正确、完整、符合真实意图的结果。现版已经具备有价值的需求对齐、现状事实核验、批次独立审查、内容绑定和历史保留；本次保留它们，修正已经复现的完成判断漏洞和静态可证明的调用、授权、测试规则冲突，并减少没有明确风险依据的固定动作。

目标结果：

1. 可观测失败、未解决阻断和需求冲突能够改变下一步与完成判断，不只是记入报告。
2. Agent 从各种合法入口能到达正确的下一阶段，复用已确认需求和授权，不因旧协议或缺少上游产物僵住。
3. 验证覆盖真实行为与影响面，尤其是持久化、恢复、并发和正式调用路径；证据形式不能诱导低价值测试。
4. 上下文只携带当前决策所需信息；关键规则有唯一权威来源，辅助方法在适用时读取。
5. 新版可按真实任务比较收益与成本，尚无对照证据时只陈述结构修复和已复现机制的改善。

## 2. 现状事实与证据边界

审查基线：源码 HEAD `c10906c`；宿主 runtime `20261002-093849`。固定审查单元的 content_id 为 `36ce314358fac1f680ba8c536ef07e1f594964478395a56578923248445b91b0`，包含源码、测试和选定历史证据共 522 个文件。报告中的源码行号均对应这个版本。

已复现的现版问题：

- `batches.compare` 遇到不可运行基线就跳过该命令，即使当前运行失败，仍只记录未验证；公共 CLI 探针中批次成功收口。
- 增强自审登记 blocking 或 spec-challenge 后仍可 `implement finish`；内容绑定和章节校验没有消解未处理发现。
- 审查停止信号按相邻修改行重叠、体积阈值作硬判断；即便最终修好且当前审查 pass，也可能要求用户介入。

静态可证明的其他问题包括 triage 缺 Spec 的调用路径、旧 Topic test/review 指令、重复授权要求、验收与测试一对一限制、持久化旁路验证禁令及按内容类型强制图示。详细原文、位置、机制、修改方向见同 Topic 的诊断与分组审查报告。

历史记录表明错误现状断言、跨模块漏审、按实现造夹具、反复文档修补造成过实际返工；现版已经修复其中多项，不能把旧缺陷当作现版仍有同一缺陷的证明。现有机械测试、过去施工记录和最小探针均不构成新版相对强模型 baseline 的效果证明。

## 3. 范围与系统影响

范围内：Skill 正文与可达辅助文件、resources/policies、组合和资源分发清单、相关 runtime 状态/测试/审查/度量、README 与宿主投影验证。全部对象需有明确归宿；只有找到实质失败路径或本轮明确要求时才修改其行为。

范围外：新增宿主、模型升级、另造 assurance 等级、恢复已退役的修复方案门禁或并行实施 lane、强制长期 Spec、重写历史 Ticket/审查结论、真实账户/生产环境操作、自动 push/安装/迁移。

影响：

- 调用者是 Codex/Cursor/Claude 上的用户与组合 Skill；消费者包括执行 Agent、审查 Agent、runtime 和后续接手者。
- 现有公开 CLI 与已存状态应兼容读取；若结果字段扩充，旧字段保留含义，不将缺记录补成成功或零发现。
- 已完成历史保持原样；活动或旧版会话按其协议恢复，必须披露旧记录不能判断的事项。必要迁移另作可审阅计划，经授权执行。
- 内容变化继续使绑定的测试/审查通过记录失效；新增状态判断沿现有事务和写入边界，不降低快照、身份或并发保护。
- 本次不改变 release/install 的公开交付机制。构建与安装仍分别验证源码、release 和各宿主状态。
- 性能主要关注额外材料读取、命令数、审查子 Agent 数和用户介入；全部文件打包大小不等于模型实际上下文开销。

## 4. 候选版本的工作流

### 4.1 意图与授权

先识别用户要的产物与阶段止点：诊断、方案、Spec、Ticket、实现、审查或交付。已提供且已确认的目标、范围、约束与验收直接复用；只有存在会实质改变结果的未决解释、用户专属取舍或缺失授权时才询问。能查证的事实由 Agent 查证。

两个现有对齐点仍保留。已经明确完成对应确认的请求不再重复确认；用户明确要求只到某阶段时，chain 在该阶段停止。请求开发不能被解释成只给计划；请求 Spec 不能被解释成已批准实施。

授权依目标、动作、范围与有效限制判断。已明确授权的同一外部动作不重复申请；未授权的外部写入、新目的地或超出范围的行为仍须用户授权。所有 Skill/policy 只引用统一权威，不另开“每次都问”清单。自动审批系统或宿主权限拒绝仍按宿主规则处理。

### 4.2 从需求或分诊到实施

- **quick**：沿用现有低风险准入与同会话实施；不创建 Spec/Ticket。不因名字叫 quick 省略验收证据、最可能失败路径和实际影响检查。
- **standard**：需求与代码事实 → current Spec → 有血缘的 Ticket 与批次划分 → 用户已确认范围内实施 → 逐 Ticket 定向测试、自审、本地提交 → 批次全量比较与独立审查 → 修复/复审 → 批次收口 → 交付与 Topic 收尾。
- **triage**：confirmed brief 有匹配且覆盖此工作范围的 current Spec 时可交 to-tickets；没有时先交 to-spec，不重新访谈已经确认的内容。若问题改变既有 Spec，形成正式修订而非借用错误血缘。无论入口如何，风险触发的独立设计审查只在唯一设计关口执行。
- **可选整分支审查**：保留现有风险或用户请求触发方式，不能成为所有多 Ticket Topic 的隐性必选步骤。

runtime 的 status/next_command 与统一实施适配是机械顺序的事实源。TDD、work-scope、路由等只规定职责和适用条件，不重复列另一套测试、审查、收口命令。每次成功 mutation 返回的下一步都应在当前状态可执行，或明确说明需要用户/环境输入；最后一张 Ticket 完成时不能直接建议尚不可执行的 Topic complete。

### 4.3 实施与自审

实施者在动手前核实会影响方案、接口、数据或验收的现状断言，并找出受影响的真实调用者/消费者。已有结论可按来源和当前内容复用，变更后复核；不重复抄写整份 Spec 或为未涉及风险填模板。

standard 保留六类增强自审的覆盖要求：验收、事实、影响、对抗验证、简洁/约定、缺口。它们是需要考虑的风险，不是每项都必须制造发现；可引用已存在的证据，未涉及部分简短说明。quick 报告至少包含验收证据、实际影响/关键失败路径和剩余缺口，不强制填六个空节或采用 standard 的完整固定摘要。

自审发现必须控制后续行为：

1. 未解决 blocking 阻止 Ticket finish；在已批准边界内修复、测试和重新自审后继续，不为普通修复请求新批准。
2. spec-challenge 阻止依赖该定义的提交与后续实施，进入现有用户裁决路径。可独立推进且不依赖争议定义的授权工作继续。
3. advisory/fix-in-batch 必须在批次收口前处理；defer/decline 留下归属或理由。
4. 修复后保留旧发现和处置历史，最新内容绑定的结果决定当前是否可继续。不能因旧记录曾有 blocking 永久阻断已修复工作，也不能只改字段来假装已修复。

### 4.4 测试与完成证据

验收与证据采用多对多映射。每项验收必须能定位到足以区分其成功/失败的断言或观测；一个真实场景可覆盖多个验收，一个验收也可需要多个层级证据。测试函数名、文件数和一对一关系不构成覆盖证明。

默认保留最小 red-green 与行为不变整理；已有充分覆盖、characterization、机械重构、配置/文档等沿用合理例外。新增回归用例、负向路径或恢复探针若用于证明已批准行为，不算新增产品要求，也不触发修订 Spec 的门禁。

验证 seam 由风险决定：

- 模块行为用稳定接口，预期值来自独立事实源，避免复制实现算法。
- 持久状态、事务、迁移、数据约束、脱敏或恢复本身是契约时，允许直接核验存储及 close/reopen；不得以“旁路查询”为由排除正确性证据。
- 新增/修改 runtime 路由或适配器时，至少有能暴露接线遗漏的实际入口/生产形状验证；内部单元测试不能单独证明正式路径接入。
- 并发、发布兼容、权限等风险使用最接近失败机制的边界或集成证据；缺环境明确写限制，不临时扩大到真实生产操作。

替身不能自动证明新抽象有价值。“生产 + 测试”两种 adapter 不作为增设 port 的充分理由；按真实不可控边界、项目既有 seam 或实际变化需求判断，不用固定数量门槛替代设计判断。

### 4.5 全量测试与基线比较

当前测试结果和基线可比性分别记录。所有命令保留实际退出码、执行证据、失败身份及比较限度。

| 基线 | 当前 | 完成语义 |
|---|---|---|
| 可执行 | 通过 | 当前通过；保留原基线情况 |
| 可执行 | 失败 | 按可靠失败身份比较新增/已知；新增失败阻断 |
| 不可运行 | 通过 | 当前已验证通过；基线不可比，不能写已证明无回归 |
| 不可运行 | 实际执行失败 | 当前失败且无可比基线；不能归为仅未验证，不能凭零新增失败收口 |
| 任意 | 当前完全不可运行 | 未验证；沿现有风险与验收边界披露，不假装测试通过 |
| 部分可执行 | 部分失败/缺环境 | 分别保留可执行失败与环境缺口，不能整命令吞掉失败 |

没有可比基线的当前失败，需取得可信基线证据证明它已存在，或在授权范围内修复并通过，再允许普通收口。未知失败不能降为已知问题。必要验收证据缺失仍不能计通过；非必要环境缺口可依现有策略披露。接受审查风险不能绕过失败测试。

现有失败身份比较只能证明记录粒度下的差异；同名测试可能有不同失败原因，不能对外宣称已穷尽回归。对关键验收仍核实行为，不立即扩展成通用语义日志分析平台。

### 4.6 审查与停止

保留完整仓库读取、影响面审查、Spec 挑战、无验收锚点也可报告真实故障、一次全面审查加差异复审、固定快照及内容漂移失效。

保留现有码审四轮/三次修复、文档一轮全面审查加一次复审的预算；这些是明确成本边界。证据支持的同根因无进展、矛盾决策、需求变化或不可验证仍停止并请求恰当处理。

修改行重叠、体积变化是观察信号，不单独证明无进展或触发用户专属决定。当前内容已 pass 且满足其他门禁时，不能仅因这两个信号拒绝通过。仍有阻断时以具体未解决失败链解释停止，不能把位置相近直接等同同根因。新增修复验证或必要文档解释不自动构成 scope 变化。

独立性使用真实宿主的新上下文标识与来源；同会话“忘掉结论”只能算 self。宿主不支持独立审查时沿现有缺口披露策略处理；用户明确要求不可替代的独立审查时必须满足，不能擅自以 self 替换。不自动升级模型、思考档位或成本。

## 5. 指令结构与加载

### 5.1 分层

1. **会话常驻的最小约束**：用户阶段与授权边界、完成结论必须有实际证据、关键未知不能冒充事实、持久状态以 runtime 为准。若宿主或项目规则已可靠提供同义约束，本包不再另写副本。这里是常驻设计，不宣称全部 resource 当前被自动常驻加载。
2. **当前入口/阶段**：选择正确工作单元、产物与完成条件；简短说明关键触发并指向唯一规则。
3. **风险触发资源**：需求分析、领域建模、设计影响、测试 seam、审查、渲染等，说明何时读取以及会改变哪个决定。
4. **runtime/schema/script**：计数、依赖、内容/身份校验、状态、可执行下一步和测试比较。模型填写语义判断，程序检查确定性约束。
5. **按需参考与模板**：例子、术语、教程、正式报告和写作方法。包装进安装件不等于每次必须读取。

### 5.2 清单与单一来源

每个 Skill/resource/policy 在变更清单中列出归宿、真实消费者、触发条件、保留/修改/合并/按需/退役理由及证据等级。无使用或增值证据只标未知，不凭假设删除；没有用户侧独立任务的纯重复定义应合并或外置。

composition 继续作为调用关系权威，resource manifest 作为分发关系权威；正文、可达辅助文件、两份清单与 Codex/Cursor/Claude 投影必须一致。空消费者资源先查真实调用和安装可达性，需保留的给出入口，其余退役，不为凑数量新建消费者。

实施生命周期只在统一适配定义；授权只在统一清单定义；seam/替身只在共享测试合同定义；输出最终态/来源原则只在共享写作资源定义。各阶段保留必要提醒和指针，不复制会漂移的完整条款。

### 5.3 上下文与表达

需求、Spec、Ticket 可以在同一上下文连续推进；容量、任务独立性或宿主变化需要时允许压缩或交接。实施一个批次可以跨上下文恢复，以批准范围、持久状态、当前 Ticket、必要事实/验收证据恢复；不能把“同一未中断会话”变成正确性的前提。

强制交接/换宿主等动作先于“空间还够”的预算判断。子 Agent 是否使用由已授权并行任务、独立审查或明确收益决定，不以“不需要人干预”自动委派所有任务。

面向人类时，图、表明显降低理解成本才优先；简单结构允许文字。面向 Agent 的 Spec/Prompt/Skill/Ticket 优先显式约束和可解析结构，只有复杂流程/状态/依赖更适合时用图，关键规则仍有文字。教学前后端继续共享已选 visual_intent，但不能按题材类型强制选图或拒绝合理的 none。项目既有 service/API/boundary 等术语可以使用；纠正空泛概念，不统一禁用词语。

## 6. 实施改动包

| 改动包 | 修改位置 | 预期避免的失败 |
|---|---|---|
| A 完成判断 | batch 全量比较、自审登记/finish、状态下一步、对应测试 | 已知当前失败或未解决挑战仍提交/收口；返回不可执行下一步 |
| B 调用与授权 | triage、to-spec、to-tickets、composition；user-intervention 与冲突/润色 policy | 缺 Spec 血缘、自动越阶段、重复批准、另设暂停条件 |
| C 验证方法 | implement、tdd 正文/例子、testing-seams、codebase-design 辅助文件、workflow-delivery | 拆空测试、读写同错、持久化/恢复接线漏验、为测试造抽象 |
| D 审查收敛 | review-loop、runtime 停止信号及测试、design/finalization 独立性表述 | 修好仍硬停、合法负向验证被当新需求、假称独立 |
| E 加载与表达 | work-scope、context-hygiene、ask-matt、视觉/渲染规则、资源清单、README、宿主投影 | 旧协议覆盖现行流程、上下文过重或断链、格式替代读者判断 |
| F 交付与验证 | 完整候选版本、变更索引、行为案例、真实任务比较说明与度量 | 只交补丁无法替换、结构测试被当效果证明 |

先修复已复现机械漏洞，再修调用与测试合同，再调整停止信号和信息分层。每包保持可审阅差异；不以文件数决定批次，依据集成依赖划分。拆 Ticket 属于后续已批准阶段，本轮不产实施 Ticket。

## 7. 验收

以下为候选版本必须满足的外部行为；复现案例的脚本和日志保存在本 Topic evidence。

- **AC01** 基线不可运行、当前实际失败时，公共 CLI 明确返回当前失败与比较缺口，普通 batch close 拒绝收口；当前通过时保留通过及基线缺口。已知失败、部分执行和跨包同名失败原有正确行为不退化。
- **AC02** 自审含未解决 blocking 时不能 finish；spec-challenge 进入裁决路径，不能继续依赖争议定义的实现。修复后重新登记绑定当前内容的证据可继续，旧发现仍可追溯。
- **AC03** 最后一张 Ticket finish 后返回当前可执行的批次步骤；恢复、批次修复、可选 Topic review 与 Topic complete 的 status/next_command 一致。
- **AC04** 已配置 local 项目首次 triage 新 Bug、没有 Spec 时能从 confirmed brief 形成有事实来源的 Spec，再到合法 Ticket；有匹配 Spec 时复用。既有需求不重复访谈，风险设计关口不重复。
- **AC05** 用户“只出 Spec”时停于 Spec；明确批准范围内开发时继续完成。授权同一具体外部动作后不重复询问；未授权目的地或 scope 变化仍请求恰当决定。宿主权限保持有效。
- **AC06** 一项生命周期测试有分别可定位的断言时可覆盖多个验收；单项验收需多种证据时不得被一个测试替代。缺失验收必须暴露。
- **AC07** 写入数据约束/脱敏、事务及 close/reopen 的独立存储验证被允许；同一有缺陷的读写接口不能作为唯一正确性 oracle。正式路由/adapter 接入遗漏能被相应案例检出。
- **AC08** 新抽象不会只因“生产 + 测试”两个 adapter 被要求增设；已有边界可注入替身，不强迫改公开接口。
- **AC09** 两次修复触及相同行且当前审查 pass 时正常通过；体积越阈值不单独硬停。预算耗尽、真实 spec-challenge 或证据不足仍遵循既有停止路径。
- **AC10** 为已批准行为增加负向回归测试不触发新增需求门禁；新增产品行为或改变验收仍交用户决定。
- **AC11** 新上下文与 self 的来源可核实；同会话自审不能被标 independent，用户指定独立性和模型/成本限制得到遵守。
- **AC12** 核心调用路径没有旧 Topic test/review 硬要求；源文本、组合/分发与三宿主投影一致，所有声明路径可达。每个审查对象有唯一 inventory 行和明确处置。
- **AC13** quick 不强制空六节和完整标准摘要，仍可重建各验收、实际验证、关键风险与缺口。standard 仍覆盖六类风险，允许引用证据而非复制。
- **AC14** 换宿主必须交接时不被“空间足够”分支吞掉；跨上下文恢复能重建目标、授权、定义、状态、证据与下一步，不要求模型遗忘或保留无限上下文。
- **AC15** 简单教学结构可以有理由地选择文字；复杂图保留必要文字定义。项目既有术语不受统一禁词影响。
- **AC16** 交付一套可直接替换的完整源码/发布包，包含所有受影响正文、辅助文件、清单、runtime、测试和使用说明；明确删除/合并项及兼容限制，不仅交零散新条款。发布和每个宿主安装仅在分别授权后执行。
- **AC17** 验证报告区分文本/机械契约、最小行为探针、历史实用证据和同条件模型对照；没有对照结果时不声称提升成功率或一次做对率。

## 8. 验证策略与真实任务建议

施工验证先复用现有 temporary Git/CLI 测试 seam，针对 AC01–03/09 写能先失败的公共行为回归；其余按实际修改跑相关文本、组合、资源、三宿主投影和恢复测试。最后运行仓库声明的完整 unittest、workflow validate 与 diff 检查，并取得退出码。文档局部改写不为复制文字另造无行为意义的测试。已有 bug 探针的结果不替代修订后复跑。

真实效果验证作为后续独立执行计划，不能塞进本轮或静态发布门禁。建议至少覆盖：

1. 局部明确 Bug，已有充分测试：看 quick 是否完整且低摩擦。
2. 有歧义的功能请求或类比：看是否抓到真正改变结果的解释，避免无意义访谈。
3. 从外部 Bug triage 开始、无 Spec：看完整衔接与血缘。
4. 持久化/恢复或路由接入：从创建、写入、关闭、重开到真实消费入口核验，避免镜像夹具。
5. 并发、共享契约或跨 Ticket 集成：看影响面与独立审查是否找到隐藏失败。
6. 基线环境缺失、当前恢复失败；以及两轮修改同一位置后 pass：看完成判断与无谓暂停。
7. 中途压缩/换宿主恢复，以及只要求 Spec 的请求：看范围、授权和状态恢复。
8. 简单教学或文档请求：看能否根据读者需要选表达，而非图示填空。

比较三种条件：宿主/项目原规则下无本包、当前版本、候选版本。固定模型、思考档位、任务初始代码、权限、工具、时间/成本上限和可见任务材料；随机分配匹配任务，条件隔离。评估者拿用户目标和隐藏验收，不能预置怀疑点或期望哪个版本获胜。不能在后一个条件沿用前一个条件已暴露的解答。

优先做少量匹配任务试点，再决定是否扩大、每类是否需要重复。报告绝对任务数、失败/逃逸/返工、缺失验收、错误完成声明、用户介入与原因、实际材料读取和成本；耗时区分环境等待与工作。用现有 metrics 配合轻量人工记录，不能自动从命令总数推断模型思考成本。样本小就按案例报告，不宣称统计显著。

判定顺序：先看正确、完整与真实意图是否退化，再看是否减少无效暂停/返工与成本。降低字数、命令数或审查数而没有交付证据不能单独算改善。发现候选版新失败时定位根因，修订对应规则；没有证据不追加普遍门禁。

## 9. 已确认要求、提案与未知

用户已确认：本仓库是目标；必须依据原文和具体行为，保留有效约束且补缺；本轮并行诊断、协调并交方案/SPEC，暂不施工；表达按信息类型和目标读者选择。

本版各行为调整均为待审阅提案，不能写成用户已批准决定。尚未知：32 个 Skill 的真实使用频率、各宿主实际材料读取量、相对强模型无本包 baseline 的收益、候选版本的真实项目一次做对率。没有 comparative 证据，不以“模型本来就会”推定某入口可删。

解除方式：先审阅本版实施边界，批准后完成候选实现和机制验证；真实效果按第 8 节另行试点。安装、迁移、推送和模型/成本升级分别遵循授权，不因批准本 Spec 自动获得。
