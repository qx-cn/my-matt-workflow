# 以正确交付为目标的 workflow 优化

用户已接受前版及追加分析的建议，并要求按七项能力标准补充审核、纳入 Spec。本版是唯一 current 的完整修订，包含 runtime、安装升级和排障精简；方向接受不等于实施或效果验证完成。当前交付止于审核与 SPEC，不自动拆 Ticket、开工、提交、发布或安装。本 Spec 规定候选版本的完整行为；具体实现留给施工阶段。它不替代既有 Topic 的有效 Spec，不修改已完成历史。

篇幅说明：本次同时覆盖 32 个 Skill、30 份 resource 文件、7 份 policy、组合/分发与 runtime，包含兼容和效果验证，因此不按单功能 Spec 的短篇幅处理。每项要求以交付风险为依据，不以字数减少作为验收目标。

## 1. 问题与目标

用户用本仓库驱动开发，希望更常交付正确、完整、符合真实意图的结果。现版已经具备有价值的需求对齐、现状事实核验、批次独立审查、内容绑定和历史保留；本次保留它们，修正已经复现的完成判断漏洞和静态可证明的调用、授权、测试规则冲突，并减少没有明确风险依据的固定动作。

目标结果：

1. 可观测失败、未解决阻断和需求冲突能够改变下一步与完成判断，不只是记入报告。
2. Agent 从各种合法入口能到达正确的下一阶段，复用已确认需求和授权，不因旧协议或缺少上游产物僵住。
3. 验证覆盖真实行为与影响面，尤其是持久化、恢复、并发和正式调用路径；证据形式不能诱导低价值测试。
4. 上下文只携带当前决策所需信息；关键规则有唯一权威来源，辅助方法在适用时读取。
5. runtime 共用确定性判断与证据处理；安装升级减少同一内容的重复检查和投影复制，保持内容、安全与恢复保证。
6. 按任务完成率、准确率、需求理解、文档写作、代码实现、Bug 排查、自动化七项标准比较收益与成本；尚无对照证据时只陈述机制改善，不承诺能力或成功率提升。

## 2. 现状事实与证据边界

审查基线：源码 HEAD `c10906c`；宿主 runtime `20261002-093849`。初次固定审查单元的 content_id 为 `36ce314358fac1f680ba8c536ef07e1f594964478395a56578923248445b91b0`，包含源码、测试和选定历史证据共 522 个文件。报告中的源码行号均对应这个版本。

已复现的现版问题：

- `batches.compare` 遇到不可运行基线就跳过该命令，即使当前运行失败，仍只记录未验证；公共 CLI 探针中批次成功收口。
- 增强自审登记 blocking 或 spec-challenge 后仍可 `implement finish`；内容绑定和章节校验没有消解未处理发现。
- 审查停止信号按相邻修改行重叠、体积阈值作硬判断；即便最终修好且当前审查 pass，也可能要求用户介入。

静态可证明的其他问题包括 triage 缺 Spec 的调用路径、旧 Topic test/review 指令、重复授权要求、验收与测试一对一限制、持久化旁路验证禁令及按内容类型强制图示。详细原文、位置、机制、修改方向见同 Topic 的诊断与分组审查报告。

历史记录表明错误现状断言、跨模块漏审、按实现造夹具、反复文档修补造成过实际返工；现版已经修复其中多项，不能把旧缺陷当作现版仍有同一缺陷的证明。现有机械测试、过去施工记录和最小探针均不构成新版相对强模型 baseline 的效果证明。

追加审查基于同一源码 HEAD，七项能力定向审查单元为 `29b34fc74cc270435dc400eeffb045142e563c21ed6048633048050732a4abec`。安装重复次数为限定稳定正常路径的静态调用计数，不是耗时实测：源码变化 deploy 先在活源树 check，build 又对打包快照 check；verify_release 重复构建三宿主投影。排障规则中“无复现可读调用链”和“复现命令出现前停止读代码”相互冲突，秒级、完全最小化及固定假设数量另有僵硬限制。追加报告中的静态风险不能当作已观察失败频率。

## 3. 范围与系统影响

范围内：Skill 正文与可达辅助文件、resources/policies、组合和资源分发清单、相关 runtime 状态/测试/审查/度量、build/deploy/install/doctor 内部去重与投影验证、排障方法、README。全部对象需有明确归宿；只有找到实质失败路径或本轮明确要求时才修改其行为。

范围外：新增宿主、模型升级、另造 assurance 等级、恢复已退役的修复方案门禁或并行实施 lane、强制长期 Spec、重写历史 Ticket/审查结论、真实账户/生产环境操作、自动 push/安装/迁移、新服务或通用流程引擎、跨进程通用缓存、按改动自动选择测试的依赖平台。批次重复存储格式归一列为后续候选，不在本次强制迁移。

影响：

- 调用者是 Codex/Cursor/Claude 上的用户与组合 Skill；消费者包括执行 Agent、审查 Agent、runtime 和后续接手者。
- 现有公开 CLI 与已存状态应兼容读取；若结果字段扩充，旧字段保留含义，不将缺记录补成成功或零发现。
- 已完成历史保持原样；活动或旧版会话按其协议恢复，必须披露旧记录不能判断的事项。必要迁移另作可审阅计划，经授权执行。
- 保证范围限于候选 runtime 执行的新工作，以及由它完成必要证据重采和状态重评的活动工作；“成功恢复”不能只指文件可读。既有活动记录中的原始当前失败、未处理 findings 和真实 spec-challenge 重新参与门禁，不因旧 `new_failures=[]` 或旧六节齐全而豁免；缺字段保持未知，重采必要证据。旧几何停止若已有绑定当前内容的有效 pass，候选 runtime 可据新规则解除，保留原停止与恢复依据。
- 旧 runtime 与候选 runtime 混写同一活动 Topic 不在支持范围，不能承诺旧 writer 会执行新门禁。发行切换前盘点参与宿主的 runtime/release，并给出统一使用候选 runtime 的切换方案；安装/迁移分别授权，不自动升级所有宿主。只读旧记录和已完成历史不因此被重写；若还要用旧协议继续写，明确作为未获本次保证的旧工作处理，不能记为候选版成功案例。
- 内容变化继续使绑定的测试/审查通过记录失效；新增状态判断沿现有事务和写入边界，不降低快照、身份或并发保护。
- 保留公开 CLI 与 release/install 职责，允许共享内部验证、投影清单算法和无变化短路；同一授权更新入口完成必要路由。源码检查、release 完整性、每个宿主实际状态仍分别报告，失败不被合并成成功。
- 性能主要关注额外材料读取、命令数、审查子 Agent 数和用户介入；全部文件打包大小不等于模型实际上下文开销。

## 4. 候选版本的工作流

### 4.1 意图与授权

先识别用户要的产物与阶段止点：诊断、方案、Spec、Ticket、实现、审查或交付。已提供且已确认的目标、范围、约束与验收直接复用；只有存在会实质改变结果的未决解释、用户专属取舍或缺失授权时才询问。能查证的事实由 Agent 查证。

两个现有对齐点仍保留。已经明确完成对应确认的请求不再重复确认；用户明确要求只到某阶段时，chain 在该阶段停止。请求开发不能被解释成只给计划；请求 Spec 不能被解释成已批准实施。

授权依目标、动作、范围与有效限制判断。已明确授权的同一外部动作不重复申请；未授权的外部写入、新目的地或超出范围的行为仍须用户授权。所有 Skill/policy 只引用统一权威，不另开“每次都问”清单。自动审批系统或宿主权限拒绝仍按宿主规则处理。

### 4.2 从需求或分诊到实施

- **quick**：沿用现有低风险准入与同会话实施；不创建 Spec/Ticket。不因名字叫 quick 省略验收证据、最可能失败路径和实际影响检查。
- **standard**：需求与代码事实 → current Spec → 有血缘的 Ticket 与批次划分 → 用户已确认范围内实施 → 逐 Ticket 定向测试、自审、本地提交 → 批次全量比较与独立审查 → 修复/复审 → 批次收口 → 交付与 Topic 收尾。
- **triage**：confirmed brief 有匹配且覆盖此工作范围的 current Spec 时可交 to-tickets；没有时先交 to-spec，不重新访谈已经确认的内容。若问题改变既有 Spec，形成正式修订而非借用错误血缘。无论入口如何，风险触发的独立设计审查只在唯一设计关口执行。
- **可选整分支审查**：保留现有风险或用户请求触发方式，不能成为所有多 Ticket Topic 的隐性必选步骤。

runtime 的 status/next_command 与统一实施适配是机械顺序的事实源。TDD、work-scope、路由等只规定职责和适用条件，不重复列另一套测试、审查、收口命令。机械可执行性不产生用户授权；Skill/Agent 同时遵守用户目标与阶段止点，不要求 runtime 解析自然语言或新增授权数据库。每次成功 mutation 返回的下一步都应在当前状态可执行，或明确说明需要用户/环境输入；最后一张 Ticket 完成时不能直接建议尚不可执行的 Topic complete。

### 4.3 实施与自审

实施者在动手前核实会影响方案、接口、数据或验收的现状断言，并找出受影响的真实调用者/消费者。已有结论可按来源和当前内容复用，变更后复核；不重复抄写整份 Spec 或为未涉及风险填模板。

standard 保留六类增强自审的覆盖要求：验收、事实、影响、对抗验证、简洁/约定、缺口。它们是需要考虑的风险，不是每项都必须制造发现；可引用已存在的证据，未涉及部分简短说明。quick 报告至少包含验收证据、实际影响/关键失败路径和剩余缺口，不强制填六个空节或采用 standard 的完整固定摘要。

自审发现必须控制后续行为：

1. 未解决 blocking 阻止 Ticket finish；在已批准边界内修复、测试和重新自审后继续，不为普通修复请求新批准。
2. spec-challenge 阻止依赖该定义的提交与后续实施，进入现有用户裁决路径。可独立推进且不依赖争议定义的授权工作继续。
3. advisory/fix-in-batch 必须在批次收口前处理；defer/decline 留下归属或理由。
4. 修复后保留旧发现和处置历史，最新内容绑定的结果决定当前是否可继续。不能因旧记录曾有 blocking 永久阻断已修复工作，也不能只改字段来假装已修复。

### 4.4 测试与完成证据

验收与证据采用多对多映射。每项验收必须能定位到足以区分其成功/失败的断言或观测；一个真实场景可覆盖多个验收，一个验收也可需要多个层级证据。测试函数名、文件数和一对一关系不构成覆盖证明。

默认保留最小 red-green 与行为不变整理；已有充分覆盖、characterization、机械重构、配置/文档等沿用合理例外。新增回归用例、负向路径或恢复探针若用于证明已批准行为，不算新增产品要求，也不触发修订 Spec 的门禁。

验证 seam 由风险决定：

- 模块行为用稳定接口，预期值来自独立事实源，避免复制实现算法。
- 持久状态、事务、迁移、数据约束、脱敏或恢复本身是契约时，允许直接核验存储及 close/reopen；不得以“旁路查询”为由排除正确性证据。
- 新增/修改 runtime 路由或适配器时，至少有能暴露接线遗漏的实际入口/生产形状验证；内部单元测试不能单独证明正式路径接入。
- 并发、发布兼容、权限等风险使用最接近失败机制的边界或集成证据；缺环境明确写限制，不临时扩大到真实生产操作。

替身不能自动证明新抽象有价值。“生产 + 测试”两种 adapter 不作为增设 port 的充分理由；按真实不可控边界、项目既有 seam 或实际变化需求判断，不用固定数量门槛替代设计判断。

### 4.5 全量测试与基线比较

当前测试结果和基线可比性分别记录。所有命令保留实际退出码、执行证据、失败身份及比较限度。

| 基线 | 当前 | 完成语义 |
|---|---|---|
| 可执行 | 通过 | 当前通过；保留原基线情况 |
| 可执行 | 失败 | 按可靠失败身份比较新增/已知；新增失败阻断 |
| 不可运行 | 通过 | 当前已验证通过；基线不可比，不能写已证明无回归 |
| 不可运行 | 实际执行失败 | 当前失败且无可比基线；不能归为仅未验证，不能凭零新增失败收口 |
| 可执行 | 当前完全不可运行 | 保留现版阻断；不能把当前失去执行能力降为仅未验证 |
| 不可运行 | 当前完全不可运行 | 未验证；沿现有风险与验收边界披露，不假装测试通过 |
| 部分可执行 | 部分失败/缺环境 | 分别保留可执行失败与环境缺口，不能整命令吞掉失败 |

没有可比基线的当前失败，需取得可信基线证据证明它已存在，或在授权范围内修复并通过，再允许普通收口。未知失败不能降为已知问题。必要验收证据缺失仍不能计通过；非必要环境缺口可依现有策略披露。接受审查风险不能绕过失败测试。

现有失败身份比较只能证明记录粒度下的差异；同名测试可能有不同失败原因，不能对外宣称已穷尽回归。对关键验收仍核实行为，不立即扩展成通用语义日志分析平台。

### 4.6 审查与停止

保留完整仓库读取、影响面审查、Spec 挑战、无验收锚点也可报告真实故障、一次全面审查加差异复审、固定快照及内容漂移失效。

保留现有码审四轮/三次修复、文档一轮全面审查加一次复审的预算；这些是明确成本边界。证据支持的同根因无进展、矛盾决策、需求变化或不可验证仍停止并请求恰当处理。

修改行重叠、体积变化是观察信号，不单独证明无进展或触发用户专属决定。当前内容已 pass 且满足其他门禁时，不能仅因这两个信号拒绝通过。仍有阻断时以具体未解决失败链解释停止，不能把位置相近直接等同同根因。新增修复验证或必要文档解释不自动构成 scope 变化。

独立性使用真实宿主的新上下文标识与来源；同会话“忘掉结论”只能算 self。宿主不支持独立审查时沿现有缺口披露策略处理；用户明确要求不可替代的独立审查时必须满足，不能擅自以 self 替换。不自动升级模型、思考档位或成本。

### 4.7 需求理解与文档质量

保留现有用户证据、已确认目标、非目标、关键歧义澄清和最终态写作方法。流程内部一致不等于符合用户意图；需求与验收需能追溯到用户材料或明确标记的假设，不能把 Agent 自行选定的实现细节反写为用户要求。存在会改变交付的多个解释时，用一个有区分力的例子、反例或问题解决该分歧；明确任务直接复用已确认内容，不强制每次新访谈或另建审批关口。

Spec/Ticket 下传保留成功行为、重要限制与证据来源；拆分不能遗漏跨 Ticket 才能验证的用户结果。若实现满足 Ticket 文字却违背上游目的，应作为定义问题处理，不能用“验收通过”掩盖它。既有 Spec 挑战和影响面审查承担此职责，不增设平行审查链。

文档按目标读者完成其使用任务：说明当前有效行为、必要前提、操作或决策、失败/限制及可定位事实来源。沿用最终态正文，不把修订过程堆在正文末尾；历史与当前规则分开。事实、推断、建议和未验证结论的界限清楚；没有材料支撑时保留未知。示例、图表、润色和人类阅读检查按任务价值选择，不作为所有产物的固定工序，也不强制每节有引用或每份文档套同一模板。

测试报告允许从当前代码中可定位的输入、前置状态、断言、替身与依赖提取静态验证内容，标明来源及覆盖边界。不能仅凭测试名推断覆盖，不能把作者设计动机推断为事实；缺失的动机保持未知或标记为分析判断。代码存在不证明执行通过，只有对应当前内容的实际运行记录支持执行结论；人工待测仍待测。此条修正 `my-test-report:76` 的过宽禁令，不取消其执行证据约束。

### 4.8 Bug 排查

保留与用户实际症状一致的调查目标、可检验假设、能区分原因的实验、修复后原场景与回归验证。按证据和诊断价值选择下一步：

- 无稳定复现时可读取日志、配置、历史、调用链和已有测试以构造复现；不要求先有 red 命令才能读代码。
- 稳定、快速、无人值守的复现优先，但不是开工门槛。慢恢复、间歇故障或需要外部交互时可使用代表性集成场景、重复采样或已授权人工观测；记录环境、观测、频率和局限。不能凭固定失败概率断言“不可排查”，也不能把偶发未失败当作已修复。
- 最小化以保持症状与提高区分力为准，成本高于收益时停止缩减。假设数量由已有证据决定；有一个明确候选可以直接检验，多个候选按可区分实验推进，不为凑 3–5 项编造假设。
- 明确区分观察事实、待证假设与已获支持的因果结论；历史日志与静态可达路径可支持代码缺陷判断，但不能冒充原环境复现。删除“已解决 90%”等无依据效果数值。无法复现时仍可提出或实施有依据、在授权范围内的修复，但不得声称原故障已验证消失；必要验收缺失不能计成功，不能从“先做排障”越到未经授权的产品变更。

### 4.9 Runtime 内部职责

第一阶段只收敛重复确定性逻辑，不引入新进程、框架或状态格式迁移。

1. 状态评估与门禁谓词共用：status、next_command、mutation 回执使用相同完成与下一步规则；实际写入前在原有事务/锁边界重新核验当前状态。旧 status 结果不是写入授权或完成凭据。
2. 测试执行与证据内核共用：记录命令、当前内容、环境、退出码、执行完整性和失败事实；Ticket 的全通过、batch 的基线比较、quick 的验收策略保持区别。中断、未完成或内容改变不能复用旧成功。
3. 快照与回执共用完整性校验，策略分别保留：Ticket 的定义/下游范围，branch 的 HEAD，artifact 的归属与生命周期。不能把不同内容身份视为同一 scope。
4. legacy reader/adapter 与主流程隔离，兼容 alias 共用实现但保留公开名字。构建分发与项目执行职责分开组织；不为减少模块数合并不相关业务，不重写已完成历史。

### 4.10 安装升级校验

采用已有 `deploy --target ...` 更新入口，内部自动选择复用或构建，输出 source、release 与请求宿主各自结果。只操作已授权宿主；多宿主共享验证若处于同一协调调用，可共享下述上下文，各宿主仍独立事务及结果。不要求新增多宿主 CLI 或跨命令缓存来完成本次优化。

- 需要构建新候选时，对实际打包的稳定快照执行一次完整 check，去掉活源树上额外的一轮完整 suite；失败即停止。取样与打包内容变化须拒绝或重新建立匹配快照。正常无重试路径“恰好一次”不禁止真实失败恢复后的必要重跑。
- 同一操作内，按内容身份复用 release 验证上下文，建立及使用须受恰当的发布引用/内容保护约束；不能把锁外旧布尔值带入锁内后直接信任。doctor 对同一个包复用只读验证时也需稳定身份或漂移检测，未知即重验。不同旧 release 与新 release 分别验证，包正确不替代 staging 与最终目标检查。
- 确定性宿主投影直接计算预期文件清单与内容摘要，避免仅为验证复制三套完整树。新算法必须与现有物理投影逐路径、逐字节等价，包括增删、metadata、路径与链接处理；实际安装仍 staging 所选宿主，保留所有权与内容核验。
- 完整构建输入摘要覆盖决定产物的路径/内容、增删/链接、构建器/投影器与 upstream 参数；输入不变、release 有效且实际托管宿主内容匹配时返回 current，跳过临时打包和宿主重写。旧记录缺少可用摘要时回退完整校验或构建，不补造缓存命中。只看 release_id、Git HEAD 或时间戳不足以短路。
- **首版不复用跨调用的测试通过凭据。** 无变化 deploy 仍可保留一次完整 check；它的承诺是省去临时打包和重复安装，不承诺零测试。未来若要跳过该检查，须单独扩展绑定源码、测试/配置、命令、构建/校验协议及 Python/依赖环境的成功 receipt；产物等价不等于测试证据仍有效。`install` 安装已有包保持不运行源码全套测试。
- 保留稳定快照、release 内容 hash、路径/symlink/托管归属保护、写锁、安装 staging、事务、备份回滚与最终内容核验。source、release、host 任一失败均可定位；某宿主成功不能遮盖另一宿主失败。未经授权不自动安装、迁移或扩大目的地。

## 5. 指令结构与加载

### 5.1 分层

1. **会话常驻的最小约束**：用户阶段与授权边界、完成结论必须有实际证据、关键未知不能冒充事实、持久状态以 runtime 为准。若宿主或项目规则已可靠提供同义约束，本包不再另写副本。这里是常驻设计，不宣称全部 resource 当前被自动常驻加载。
2. **当前入口/阶段**：选择正确工作单元、产物与完成条件；简短说明关键触发并指向唯一规则。
3. **风险触发资源**：需求分析、领域建模、设计影响、测试 seam、审查、渲染等，说明何时读取以及会改变哪个决定。
4. **runtime/schema/script**：计数、依赖、内容/身份校验、状态、可执行下一步和测试比较。模型填写语义判断，程序检查确定性约束。
5. **按需参考与模板**：例子、术语、教程、正式报告和写作方法。包装进安装件不等于每次必须读取。

### 5.2 清单与单一来源

每个 Skill/resource/policy 在变更清单中列出归宿、真实消费者、触发条件、保留/修改/合并/按需/退役理由及证据等级。无使用或增值证据只标未知，不凭假设删除；没有用户侧独立任务的纯重复定义应合并或外置。

composition 继续作为调用关系权威，resource manifest 作为分发关系权威；正文、可达辅助文件、两份清单与 Codex/Cursor/Claude 投影必须一致。空消费者资源先查真实调用和安装可达性，需保留的给出入口，其余退役，不为凑数量新建消费者。

实施生命周期只在统一适配定义；授权只在统一清单定义；seam/替身只在共享测试合同定义；输出最终态/来源原则只在共享写作资源定义。各阶段保留必要提醒和指针，不复制会漂移的完整条款。

### 5.3 上下文与表达

需求、Spec、Ticket 可以在同一上下文连续推进；容量、任务独立性或宿主变化需要时允许压缩或交接。实施一个批次可以跨上下文恢复，以批准范围、持久状态、当前 Ticket、必要事实/验收证据恢复；不能把“同一未中断会话”变成正确性的前提。

强制交接/换宿主等动作先于“空间还够”的预算判断。子 Agent 是否使用由已授权并行任务、独立审查或明确收益决定，不以“不需要人干预”自动委派所有任务。

面向人类时，图、表明显降低理解成本才优先；简单结构允许文字。面向 Agent 的 Spec/Prompt/Skill/Ticket 优先显式约束和可解析结构，只有复杂流程/状态/依赖更适合时用图，关键规则仍有文字。教学前后端继续共享已选 visual_intent，但不能按题材类型强制选图或拒绝合理的 none。项目既有 service/API/boundary 等术语可以使用；纠正空泛概念，不统一禁用词语。

## 6. 实施改动包

| 改动包 | 修改位置 | 预期避免的失败 |
|---|---|---|
| A 完成判断 | batch 全量比较、自审登记/finish、状态下一步、对应测试 | 已知当前失败或未解决挑战仍提交/收口；返回不可执行下一步 |
| B 调用与授权 | triage、to-spec、to-tickets、composition；user-intervention 与冲突/润色 policy | 缺 Spec 血缘、自动越阶段、重复批准、另设暂停条件 |
| C 验证方法 | implement、tdd 正文/例子、testing-seams、codebase-design 辅助文件、workflow-delivery | 拆空测试、读写同错、持久化/恢复接线漏验、为测试造抽象 |
| D 审查收敛 | review-loop、runtime 停止信号及测试、design/finalization 独立性表述 | 修好仍硬停、合法负向验证被当新需求、假称独立 |
| E 加载与表达 | work-scope、context-hygiene、ask-matt、视觉/渲染规则、资源清单、README、宿主投影 | 旧协议覆盖现行流程、上下文过重或断链、格式替代读者判断 |

| G Runtime 收敛 | 状态/门禁、测试执行与证据、快照校验、legacy adapter、CLI alias | 多处判定漂移、重构误抹掉不同 scope 与成功语义 |
| H 安装升级 | deploy/build、installer、doctor、projection 与相关测试 | 重复全量检查/临时构建/复制；优化后漏报漂移或安装失败 |

先修复已复现机械漏洞，再修调用与测试合同，再调整停止信号和信息分层。在同一修改点同步抽取共用判定，避免先全库重构。安装先去同操作重复，再改投影和无变化短路；排障规则独立验证。每包保持可审阅差异；不以文件数决定批次，依据集成依赖划分。拆 Ticket 属于后续已批准阶段，本轮不产实施 Ticket。

## 7. 验收

以下为候选版本必须满足的外部行为；复现案例的脚本和日志保存在本 Topic evidence。

- **AC01** 基线不可运行、当前实际失败时，公共 CLI 明确返回当前失败与比较缺口，普通 batch close 拒绝收口；当前通过时保留通过及基线缺口。已知失败、部分执行和跨包同名失败原有正确行为不退化。
- **AC02** 自审含未解决 blocking 时不能 finish；spec-challenge 进入裁决路径，不能继续依赖争议定义的实现。修复后重新登记绑定当前内容的证据可继续，旧发现仍可追溯。
- **AC03** 最后一张 Ticket finish 后返回当前可执行的批次步骤；恢复、批次修复、可选 Topic review 与 Topic complete 的 status/next_command 一致。
- **AC04** 已配置 local 项目首次 triage 新 Bug、没有 Spec 时能从 confirmed brief 形成有事实来源的 Spec，再到合法 Ticket；有匹配 Spec 时复用。既有需求不重复访谈，风险设计关口不重复。
- **AC05** 用户“只出 Spec”时停于 Spec；明确批准范围内开发时继续完成。授权同一具体外部动作后不重复询问；未授权目的地或 scope 变化仍请求恰当决定。宿主权限保持有效。
- **AC06** 一项生命周期测试有分别可定位的断言时可覆盖多个验收；单项验收需多种证据时不得被一个测试替代。缺失验收必须暴露。
- **AC07** 写入数据约束/脱敏、事务及 close/reopen 的独立存储验证被允许；同一有缺陷的读写接口不能作为唯一正确性 oracle。正式路由/adapter 接入遗漏能被相应案例检出。
- **AC08** 新抽象不会只因“生产 + 测试”两个 adapter 被要求增设；已有边界可注入替身，不强迫改公开接口。
- **AC09** 两次修复触及相同行且当前审查 pass 时正常通过；体积越阈值不单独硬停。预算耗尽、真实 spec-challenge 或证据不足仍遵循既有停止路径。
- **AC10** 为已批准行为增加负向回归测试不触发新增需求门禁；新增产品行为或改变验收仍交用户决定。
- **AC11** 新上下文与 self 的来源可核实；同会话自审不能被标 independent，用户指定独立性和模型/成本限制得到遵守。
- **AC12** 核心调用路径没有旧 Topic test/review 硬要求；源文本、组合/分发与三宿主投影一致，所有声明路径可达。每个审查对象有唯一 inventory 行和明确处置。
- **AC13** quick 不强制空六节和完整标准摘要，仍可重建各验收、实际验证、关键风险与缺口。standard 仍覆盖六类风险，允许引用证据而非复制。
- **AC14** 换宿主必须交接时不被“空间足够”分支吞掉；跨上下文恢复能重建目标、授权、定义、状态、证据与下一步，不要求模型遗忘或保留无限上下文。
- **AC15** 简单教学结构可以有理由地选择文字；复杂图保留必要文字定义。项目既有术语不受统一禁词影响。
- **AC16** 交付一套可直接替换的完整源码/发布包，包含所有受影响正文、辅助文件、清单、runtime、测试和使用说明；明确删除/合并项及兼容限制，不仅交零散新条款。发布和每个宿主安装仅在分别授权后执行。
- **AC17** 验证报告区分文本/机械契约、最小行为探针、历史实用证据和同条件模型对照；没有对照结果时不声称提升成功率或一次做对率。
- **AC18** 候选 runtime 恢复旧活动记录时重评当前失败、未解决发现和停止状态，未知字段不补成功。升级前已合法完成的历史不重开；旧 writer 混写限制与参与宿主切换方案明确披露，未经授权不安装/迁移。


- **AC19** runtime 共用逻辑后 Ticket、batch、quick 的成功语义不混淆；执行中断、内容变化、部分失败不能借旧记录通过。status 与 mutation 的下一步一致，状态在两者之间变化时写入重检并拒绝失效动作。Ticket 下游定义、branch HEAD、artifact scope 校验各自保留。
- **AC20** 正常稳定的源码变化 deploy 仅在最终打包快照上执行一轮完整 suite；失败不发布，漂移拒绝或重新取快照。同操作对受保护的同内容 release 复用验证；不同旧包、新包及漂移后对象不混用。记录实际 suite 与验证次数，不仅检查输出文案。
- **AC21** 构建输入不变且 release/目标实际内容正确时，无变化 deploy 返回 current，不临时打包或重写目标；它仍可运行一轮 check。release 或已安装内容篡改能被发现，不能误报 current；旧摘要缺失回退有效校验。源码、测试/配置、构建/投影器和 upstream 参数变化走相应重新校验路径，不能误用产物身份代替测试身份。
- **AC22** 所有支持宿主的新投影清单与原物理投影逐字节等价；路径/链接保护、非托管同名目录、安装中断回滚、并发写、最终目标校验不退化。安装已有 release 不额外运行源码完整 suite；多宿主结果分别呈现。验证重复减少须附计数与阶段耗时，性能收益不预填百分比。
- **AC23** 慢恢复、间歇故障、必须先读调用链才能造复现三类案例都能推进调查；不因秒级、完全最小或固定假设数量硬停。证据不足的 root cause 保持假设，原场景未验证保持缺口；有效修复用原症状及能区分原因的回归验证。
- **AC24** 对有决定性歧义的请求，需求和验收能区分影响交付的解释，并回溯用户材料或标记假设；明确请求不重复访谈。跨 Ticket 集成的用户结果有验收归属，内部契约通过但违背上游目的的案例能进入 Spec 挑战，不能计正确交付。
- **AC25** 选取面向 Agent 的 Spec 与面向人的说明各一份，独立读者仅凭有效正文能识别当前规则、必要前提、下一步及限制；无相互冲突的修订补丁。事实/推断/未知可区分，缺来源不杜撰，简单内容无需强制图示或润色工序。另给仅有测试代码、无运行日志的任务：准确提取静态输入/断言与替身边界，设计动机未知且不宣称通过；补充失败日志后明确报告失败。能力效果另按第 8 节测量，不能把格式检查当写作水平证明。
- **AC26** 七项能力各有明确机制、代表任务、可观察指标和限制；正确交付分母包含全部已分配任务，blocked/超时/环境失败不静默剔除。首次独立验收、修复后最终正确、错误完成声明分开记录；未授权行为列为自动化失败而非成功。没有试验结果时只报告待验证预期。

## 8. 验证策略与真实任务建议

施工验证先复用现有 temporary Git/CLI 测试 seam，针对 AC01–03/09 写能先失败的公共行为回归；其余按实际修改跑相关文本、组合、资源、三宿主投影和恢复测试。安装/runtime 重构另用故障注入和计数验证 AC19–22，排障和读者任务验证 AC23–25；共用内核必须先锁定原各入口的正确语义，不能只测新 helper。最后运行仓库声明的完整 unittest、workflow validate 与 diff 检查，并取得退出码。文档局部改写不为复制文字另造无行为意义的测试。已有 bug 探针的结果不替代修订后复跑。

真实效果验证作为后续独立执行计划，不能塞进本轮或静态发布门禁。建议至少覆盖：

1. 局部明确 Bug，已有充分测试：看 quick 是否完整且低摩擦。
2. 有歧义的功能请求或类比：看是否抓到真正改变结果的解释，避免无意义访谈。
3. 从外部 Bug triage 开始、无 Spec：看完整衔接与血缘。
4. 持久化/恢复或路由接入：从创建、写入、关闭、重开到真实消费入口核验，避免镜像夹具。
5. 并发、共享契约或跨 Ticket 集成：看影响面与独立审查是否找到隐藏失败。
6. 基线环境缺失、当前恢复失败；以及两轮修改同一位置后 pass：看完成判断与无谓暂停。
7. 中途压缩/换宿主恢复，以及只要求 Spec 的请求：看范围、授权和状态恢复。
8. 简单教学或文档请求：看能否根据读者需要选表达，而非图示填空。
9. 慢启动恢复、低频故障、先读调用链才能造复现的 Bug：看是否产生区分原因的证据，以及是否准确披露未验证。
10. 已授权安装升级：覆盖源码变化、无变化、包/宿主篡改、旧包、并发、中断与回滚；看次数减少后保护是否仍有效。

真实正确交付指固定预算与授权范围内，完成用户指定阶段的必要产物并通过独立目标/验收核查。只要求 Spec 时合格 Spec 即成功；实现任务只给 Spec 不算成功。Wayfinder 单会话决策数量暂保留现有默认，作为行为试点观察项；本版不将它扩展为自动实施授权，也不新增另一种全局会话门禁。

七项标准作为横切评价，允许一个真实任务覆盖多项，不要求每次运行填写七份报告：

| 标准 | 机制与代表任务 | 可观察结果 | 效果边界 |
|---|---|---|---|
| 任务完成率 | 合法下一步、缺 Spec 衔接、授权复用、恢复；任务 1/3/6/7 | 固定预算内正确且完整交付数 / 全部已分配任务；blocked、超时、缺环境分列 | 拦住错误完成有价值，但未修复任务不算成功 |
| 准确率 | 独立 oracle、失败不吞没、真实行为验收；任务 4/5/6 | 首次独立验收通过率、错误完成声明、关键逃逸及返工 | 门禁不保证验收或业务解释本身正确 |
| 需求理解 | 来源/假设区分、决定性歧义和跨 Ticket 用户结果；任务 2/3/7 | 隐藏用户场景满足、重要遗漏/误解、用户纠正与无效询问 | 不以问题数量或 Spec 字数评价理解；现有有效方法主要保留 |
| 文档写作 | 最终态、目标读者、事实边界；任务 8 | 独立读者完成指定理解/操作任务的正确率；歧义、无依据断言与必要信息遗漏 | 美观、图数和格式通过不等于可用；不承诺语言论证普遍增强 |
| 代码实现 | 真实入口、持久化/恢复/影响面与受约束自审；任务 4/5 | 隐藏行为/集成验收、首次与最终正确、实际逃逸及实现返工 | 针对具体漏验，不能推定算法、性能和架构能力普遍提高 |
| Bug 排查 | 证据驱动复现与判别实验；任务 1/9 | 有证据的根因、原症状修复、区分性回归、误诊/无效实验和耗时 | 无原环境只能报告证据范围，不把猜中原因算证明 |
| 自动化 | 共用状态、范围内授权、恢复、安装去重；任务 3/7/10 | 批准范围内正确完成、无效介入/停顿、恢复成功与校验耗时 | 未授权推进、漏报失败和重复外部副作用均失败；外部权限仍需真实输入 |

准确性同时看任务级整体正确与重要缺陷，不用大量简单断言冲淡严重失败。一次做对指交付后首次独立验收即通过；内部测试/自审修复次数另计，不能通过延后交付隐藏返工。真实外部动作结果未知时先核对状态，不能把盲目重复写入算自动恢复收益。

比较三种条件：宿主/项目原规则下无本包、当前版本、候选版本。固定模型、思考档位、任务初始代码、权限、工具、时间/成本上限和可见任务材料；随机分配匹配任务，条件隔离。评估者拿用户目标和隐藏验收，不能预置怀疑点或期望哪个版本获胜。不能在后一个条件沿用前一个条件已暴露的解答。

优先做少量匹配任务试点，再决定是否扩大、每类是否需要重复。每次运行记录 workflow commit/release、模型/档位、任务初始快照和必要权限/环境；逃逸缺陷附可定位证据、可能的引入版本及发现窗口，不能确认的字段保留未知。报告绝对任务数、失败/逃逸/返工、缺失验收、错误完成声明、用户介入与原因、实际材料读取和成本；耗时区分环境等待与工作。用现有 metrics 配合轻量人工记录，不能自动从命令总数推断模型思考成本。样本小就按案例报告，不宣称统计显著。

判定顺序：先看正确、完整与真实意图是否退化，再看是否减少无效暂停/返工与成本。降低字数、命令数或审查数而没有交付证据不能单独算改善。发现候选版新失败时定位根因，修订对应规则；没有证据不追加普遍门禁。

## 9. 已确认要求、当前边界与未知

用户已确认目标仓库、证据导向和保留有效约束、并行审核、表达按读者选择，并接受前版及追加 runtime/安装/七项能力分析建议。本次要求将建议和能力补充审核写入 Spec；本文件定义后续实施范围，不代表已开始实现、升级或能力试验。

本修订整合了 revision 1 的 AC01–18；新增 runtime 收敛、安装升级、排障与能力补缺见 4.7–4.10、改动包 G–I、AC19–26。revision 1 为 superseded，历史审查报告保留原时点判断；本版是唯一 current。后续 Tickets 引用 `spec_id=workflow-outcome-optimization, revision=2`，不拼接两版规定。

尚未知：Skill 实际使用频率、各宿主实际材料读取量、安装提速幅度、七项能力各自的真实收益与回归概率、相对强模型无本包 baseline 的净收益。机制测试证明对应失败路径被修复，不能证明七项能力全面提高。按第 8 节在同条件任务上分别验证，结果为负或不确定时如实记录；不追加没有失败证据的通用门禁。

实施、真实效果试点、提交/推送、发布、安装与迁移分别遵循当前授权。用户仅要求补充 Spec 的本阶段，到此交付停止。
