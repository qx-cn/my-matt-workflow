## 目标与依据

让使用者更快找到当前工作的下一步，让评审者更容易看出行为规格的变化，并用实际项目证据判断新机制是否值得维护。OpenSpec 提供了变更状态与下一步提示、行为规格增量、规格归档合并等可参考的做法；本项目已有版本化 Spec、Ticket 血缘、实施会话和证据收据，优化应建立在这些现有机制之上。

## 优化项

### 1. 工作总览入口

提供只读入口，按主题展示当前有效 Spec 及修订、Ticket 的可开始项与阻塞原因、已有实施会话的状态、证据状态和可执行的下一动作。信息来自现有文件与 runtime；同一个事实只保留一个权威来源。总览遇到缺失、冲突或无法判定的状态时明确显示，不把未知推断为完成。

验收：使用者从一个入口能找到指定主题的当前工作与下一动作；展示结果能回指原始文件或 runtime 结果；与现有 `next-ticket`、`implementation-next-action` 等命令的结论一致。

### 2. Spec 修订的行为变化摘要

在修订版 Spec 中明确本次新增、修改、移除的外部可观察行为及受影响验收。保留完整版本化 Spec 作为下游实施边界；变化摘要用于评审和影响分析，不另立一份实施权威。先在一个真实修订主题上试用，避免让所有 Spec 机械套用固定的 Requirement/Scenario 格式。

验收：评审者能从摘要定位每项变化在本版 Spec 中的最终表述，并能识别受影响的未完成 Ticket；摘要与完整 Spec 不矛盾。

### 3. 日常操作负担

观察从接续工作到开始当前实施单元需要查找的文件、选择和命令；将重复的状态查找与下一步提示收束到现有入口。保留确有必要的用户决策、写操作和实施门禁，不增加平行的进度状态。

验收：在同一真实任务上，与改动前相比，恢复下一步所需的人工查找与重复选择减少；原有门禁和错误状态仍可辨认。

### 4. 真实项目效果验证

为试点记录改动前后的恢复时间、遗漏验收、状态误读和重复维护量。区分源码静态检查、确定性 contract、Agent 行为证据与真实项目交付效果；`workflow.py check` 通过不能单独证明优化有效。

验收：每项试点有可定位的实际任务、前后观察和局限；无收益或维护成本超过收益的机制不继续推广。

### 5. 按需维护长期行为规格

只有当一个能力经历多次变更、现有版本化 Spec 已难以回答“当前承诺什么”时，才试做长期行为视图及变更合并。实施前先明确长期视图、版本化 Spec 与外部文档之间的权威关系、更新时机和冲突处理；归档不得仅凭任务勾选推断实施完成。

验收：试点能从历史修订重建当前行为；合并结果不丢失已批准的不变量与验收；若无法确定权威来源或合并可靠性，保留现有版本化机制。

## 实施顺序与边界

先做第 1 项，并在试点开始时记录第 4 项所需的基线；接着试做第 2 项，再根据实际使用数据改进第 3 项。第 5 项以多次修订造成的实际查找困难为准入条件。每项实施前检查当前代码、项目配置和适用工作单元，不把这份方向记录当成已批准的详细设计或完成凭据。

每完成一项，启动独立 `review-agent` 对该项实际变更进行只读审查。若有 finding，先修复，再由独立 `review-agent` 复审；只有审查无 finding 且必要验证通过后，才进入下一项。
