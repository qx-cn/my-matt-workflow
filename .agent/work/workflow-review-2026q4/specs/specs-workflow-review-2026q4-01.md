# 审查看系统、批量实施、混合审查：My Matt Workflow 质量重构

本 Spec 自包含：施工者只需要本文和本仓库（My Matt Workflow 源码仓库）。本文规定最终行为、约束和验收；runtime 的内部数据结构、文件名和命令拼写由施工者设计，满足验收即可。"核心模型"一节是批次、审查单元、审查发现和设计审查的唯一定义，其他章节引用它；有冲突时以核心模型为准。

**称呼**
- **用户**：本工作流唯一的使用者。
- **Agent**：在用户项目中运行本工作流的编码 Agent。
- **施工者**：实施本 Spec 的 Agent。
- **现版**：施工开始时本仓库 HEAD 的代码与文本（`workflow-simplification` 完成后的状态）。

**术语**
- **批次**：同一 Topic 内按依赖顺序连续实施、由同一个实施会话完成、以一次独立审查收口的一组 Ticket。定义见核心模型 M1。
- **增强自审**：实施者在每张 Ticket 提交前按固定结构做的自审，见 M3。
- **批次审查**：批次全部 Ticket 提交后，由新上下文审查者做的一次独立审查，见 M4。
- **高风险 Ticket 审查**：对个别风险明显偏高的 Ticket，在其提交前额外做的一次逐 Ticket 独立审查；由 Agent 按风险判断是否触发，是例外而非常态，见 M4。
- **整分支审查**：多批次 Topic 在最后一个批次收口前，对整个 Topic 改动做的一次可选独立审查，见 M4。
- **设计审查**：Spec 或技术方案定稿后、拆 Ticket 之前，由 `my-review-design` 对方案做的独立审查，见 M5。
- **承重现状断言**：Spec 或方案中关于现有系统的断言，一旦不属实就会改变方案是否成立、改变接口或数据语义，或使验收无法判定。例如：现有接口返回什么、表结构与约束、既有状态与并发控制、上游能力的适用范围、部署方式。
- **影响面**：本次改动之外、行为可能因此改变的代码、数据和运行环境：调用方与消费者、对外契约（接口、消息、表结构、配置键、错误码、锁或幂等键）、存量数据、部署与回滚期间新旧版本并存、性能与资源、权限。

## 问题陈述

现版已经把人工介入压到两个对齐点，并让 runtime 防住"测试失败仍提交、审查后代码漂移、越序、审查记录不匹配"四类机械问题。但从多个真实项目的工件、提交历史和对话记录看，工程质量的主要漏洞不在这些地方：

- **审查只核对 Ticket 有没有做完，不看代码对系统做了什么。**
  - 在多个真实批次中，逐 Ticket 审查（自审和独立审查都有）几乎全部"通过、零发现"。有一个 Topic，11 份逐 Ticket 审查全部零发现。
  - 同一批代码后来被人工评审、外部审查工具或整分支审查查出一批真实缺陷：加锁后仍使用锁前读到的快照（并发竞态）、事务已提交后仍向调用方返回失败、锁内 N+1 查询、改动锁键或配置键导致滚动发布期间新旧实例互斥失效或启动失败、缺少数据权限校验、全表扫描的迁移、机械修改调用方导致下游工具静默改变行为、跨 Ticket 遗留的死代码、违反项目分层约定。
  - 在三个有完整记录的功能中，审查通过后又发现的重要缺陷至少有 15 个。
  - 这是结构性原因造成的：
    - runtime 只接受锚定到当前验收、探针或 Spec 中带编号不变量的发现，否则拒绝提交。普通项目的 Spec 没有编号不变量，因此验收之外的真实缺陷连"建议"都无法登记。
    - 审查材料包只包含改动文件，不含调用方。
    - 默认只报告本次引入的问题。
    - 下游 Ticket 承担的问题一律降为建议，而建议永远不会被修复。
    - Spec 维度遇到"Spec 就是这么要求的"时会放行。有一次整分支审查明确以"Spec 要求如此"放过了一个后来被人工评审定为 P1 的问题。
- **最昂贵的返工来自错误的 Spec 事实，流程中没有任何一环必须核实或挑战它。**
  - 约三分之一的漏网问题源于 Spec 对现有系统的错误断言或遗漏，包括字段长度、既有数据处理语义、上游接口的适用范围、数据来源选错。
  - 实施者照做，测试按实现写，审查按 Spec 放行。
  - 有一个 Topic 因此追加了 6 张补偿 Ticket，是原 Ticket 数的 1.5 倍。
  - 设计审查本该是这道关口，实际只起了一半作用：
    - 单次审查或首轮审查确实有效：约四分之三的发现是实质设计问题，其中绝大多数是"Spec 对现有系统的断言不属实"，例如按 Spec 执行会清空数据库、既有状态模型被误读、既有落库步骤被跳过。这些问题都在实施前修正了。
    - 但它的检查项只看方案内部：待决策项、逻辑、一致性、对已提出目标的闭环、措辞。核对代码是"必要时"才做，影响面、上线兼容和需求语义都不在检查项里。
    - 设计审查跑过之后，同一批功能仍有 7 个设计级缺陷漏到实施之后，全部落在这些盲区：新机制与现有写路径的并发交互、改锁键或配置键引起的发布兼容问题、上游接口的适用范围、产品规则本身错误、对外接口面过大。其中那个并发竞态，审查者已经考察过，却靠推理排除了，报告里没有留下任何痕迹；后来它被人工评审定为 P1。
    - 用户在审查会话里写死的产品规则，审查直接当成前提接受；后来人工评审推翻了它。
    - 设计审查靠用户手动触发，好几个出过现状事实错误的 Topic 从未跑过它。
- **逐 Ticket 独立审查成本高、产出低；有价值的发现集中在批次或整分支层面。**
  - 一次 6 张 Ticket 的会话派出了 22 个子 Agent，调用 runtime 107 次。逐 Ticket 独立审查全部通过，随后按层切片的整分支审查仍查出 P1。
  - 本仓库自己的施工记录显示，逐 Ticket 自审找出了约 10 个真实问题；批次级独立审查又补出 7 个，整分支审查再补 2 个。独立审查的价值主要来自"写出可执行探针、证明从正式基线可达"，而不仅仅是换了一个新上下文。
  - 用户自己在实践中采用的正是"逐 Ticket 自审 + 批次末独立审查"，现版却没有这种模式。
- **实施质量问题有共同来源：实施者缺少系统上下文，也没有人负责代码质量。**
  - Ticket 不写路径，执行简报里没有调用方和影响面，实施者每张 Ticket 都要重新探索代码。
  - 常见问题：
    - 测试夹具按实现构造，与缺陷互为镜像；
    - 只实现"样例"却勾选完成；
    - 写得过度复杂、违反项目分层；
    - 为了让环境里本就失败的全量测试变绿，去改无关文件。
  - TDD 去掉了重构步骤，审查建议又从不修复，所以没有任何环节负责整理代码。
- **Spec 阶段过度投入，而且不收敛。**
  - 有一份 Spec 4 小时内修订 11 次，体积从约 19KB 涨到 51KB，最终没有产出任何 Ticket。
  - 另一份 Spec 在 30 多轮文档审查后达到 95KB，正文里不断追加"第 N 轮修正"段落，开头只好声明"冲突时以修正说明为准"。
  - 两份 Spec 都是用户要求设计审查"修复后再审，直到通过"造成的。后续轮次主要在审上一轮补丁：一次 30 多轮的循环里，约四分之三的阻断问题是上一轮修复引入的。
  - Ticket frontmatter 把实现细节写死，例如指定函数名，用户明确反对这种过度规定。
- **效果没有被度量。** 逃逸缺陷是现版声明的护栏，但度量里没有对应字段；现版的度量还没有在任何真实项目上产生过一条记录。

## 目标结果

1. **审查能抓到系统层面的缺陷。** 审查发现以"代码位置 + 可达的出错路径或被违反的规则"为准入依据，不再要求锚定验收。影响面是审查的必查视角。Spec 本身与现有系统冲突时，审查要提出来交用户裁决，不得以"Spec 要求如此"放行。
2. **批量实施 + 混合审查成为 standard 的默认路径。** 一个实施会话连续完成一个批次的多张 Ticket：每张 Ticket 做增强自审、跑定向测试、本地提交；批次结束后跑全量测试，再做一次独立批次审查，修复后收口。个别高风险 Ticket 可以额外做一次逐 Ticket 独立审查；没有触发它的干净批次只派一次审查子 Agent。多批次 Topic 可以在最后一个批次收口前选做一次整分支审查，它不是必经步骤。
3. **实施者带着系统上下文动手，并对代码质量负责。** 每张 Ticket 动手前核实 Spec 对现状的断言，列出影响面；红绿循环后可以在本 Ticket 触及的代码内做行为不变的整理；绝不为了让测试变绿去改无关文件。
4. **Spec 与 Ticket 更短，也更对。** Spec 中关于现有系统的断言要有可定位的代码依据，并有一节"系统影响"；篇幅与改动规模相称。Ticket 去掉强制的规则字段，不写死非契约性的实现细节。设计审查成为拆 Ticket 前唯一的独立设计关口，对承重设计自动触发，必查承重现状断言、影响面与上线兼容，并把无法验证的需求语义假设交给用户；只做一次全面审查加最多一次复审。
5. **测试分层，且不被环境卡死。** 每张 Ticket 跑定向测试；批次收口时跑全量测试，并与基线对比。基线上本来就失败的用例不阻断，但要报告；只有新增失败才阻断。
6. **逃逸缺陷可以被记录和汇总。** 审查之后才发现的缺陷能记到对应 Topic、批次和 Ticket 上，并标明"本应由哪一层抓到"。
7. **不增加用户负担和文本量。** 对齐点仍然只有两个；主链加载的 Skill 文本总量不超过 35,000 字符（现版约 32,000）。

判断标准：本文"行为与验收"中的 AC 全部满足，并且端到端测试中的注入缺陷场景（见验证策略）按预期被拦下或放行。

## 范围边界

**范围内**
- Skill：`my-code-review`、`my-implement`、`my-tdd`、`my-to-spec`、`my-to-tickets`、`my-grilling`、`my-grill-with-docs`、`my-handoff`、`my-review-design`（检查项、报告格式、触发与轮数，见 M5）、`my-tech-design`（只涉及调用设计审查的时机）、`my-review-artifact`（只同步它对设计审查的引用）。
- 共享资源：`resources/review-loop.md`、`resources/workflow-delivery.md`、`resources/adapters/` 中与实施、审查、Ticket 选择相关的适配文档、`resources/user-intervention.md`（只同步措辞，不新增找用户的条件）。
- runtime：`tools/workflow.py` 与 `tools/workflow_lib/` 中与 Topic、Ticket、审查、测试、度量相关的部分；`composition/manifest.json`（如调用边变化）；对应测试；README 的使用流程与命令说明。

**范围外**
- 不新增宿主，不改变安装、release、部署机制。
- 不恢复已删除的机制：`audited` 等级、修复方案门禁、长期 Spec 发布、并行实施 lane、配置预设。
- 不改变两个对齐点的位置，也不新增找用户的条件。
- 不改动其他 Skill 的方法正文，只在全局措辞（例如审查发现模型）变化时同步引用。
- 不要求施工者在真实项目上试点（见"依据与未知"）。

## 核心模型

### M1. 批次

- standard Topic 的 Ticket 被划分为一个或多个**批次**。划分在对齐点 2 随 Ticket 拆分一起展示给用户确认。只有一张 Ticket 的 Topic 视为一个批次。
- 默认整个 Topic 是一个批次。只有遇到下列情况才拆分：存在天然的集成边界（例如先做契约扩展、再迁移调用方）；或者预计改动规模超出一次审查能可靠覆盖的范围。规模阈值由施工者设计成可调的启发式，并写进 `my-to-tickets`，不做成用户配置。
- 一个批次由同一个实施会话按依赖顺序完成。批次内各 Ticket 分别本地提交。
- **批次状态**：`open`（有 Ticket 未提交）→ `reviewing`（全部 Ticket 已提交，批次审查进行中）→ `closed`（批次审查通过，或用户接受现状）。也可以进入 `needs-user`（审查停止，或出现 Spec 挑战）。
- 批次 `closed` 之前，批次内已提交的 Ticket 只是"已提交、待批次收口"。批次审查的修复以批次修复提交的形式落在同一分支上，不为每个审查发现新建补偿 Ticket。批次 `closed` 之后，其中的 Ticket 才成为不可改写的历史；之后要改变结果，仍然新建补偿或迁移 Ticket。唯一的例外是 M4 的整分支审查：它的修复作为最后一个批次的修复提交承接，即使涉及已收口批次的代码。
- 同一 Topic 同一时间最多一个批次处于 `open` 或 `reviewing`。

### M2. 审查发现

一条**审查发现**至少包含：

- **位置**：文件与行区间，或配置键、表结构、契约名称等可定位对象。
- **视角**：`correctness`（改动本身）、`impact`（影响面）、`spec`（是否符合 Spec）、`spec-challenge`（Spec 与现有系统冲突，或照 Spec 做会导致可达故障）、`maintainability`（可维护性与项目约定）。
- **依据**：可达的出错路径，或被违反的验收、不变量、项目规则；需要时附复现方式。
- **严重度**：`blocking` 或 `advisory`。
- **处置**（只对 advisory）：`fix-in-batch`（本批次顺手修，局限在已触及的代码内）、`defer`（附建议的归属）、`decline`（附理由）。

准入规则：
- 能写出从正式基线可达的出错路径，或违反了明确的验收、不变量、项目规则，就可以是 `blocking`。**不要求**锚定到验收编号。
- `spec-challenge` 一律不由 Agent 自行裁决：批次进入 `needs-user`，由用户决定修订 Spec、接受风险，还是按原 Spec 继续。
- 验收覆盖仍然要输出：每条验收标明已满足、对应某条发现，或不适用并说明理由。但覆盖清单只是 `spec` 视角的一部分，不是审查发现的准入门槛。
- 猜测、没有影响的风格意见、工具已经覆盖的事项、明确的有意行为，不进入发现。

### M3. 增强自审

每张 Ticket 提交前，实施者写一份简短的自审记录，固定包含以下几节；某节无内容时写"无"并附一句理由：

1. **验收对照**：验收 → 测试 → 代码位置。多条验收不得共用同一个测试。
2. **现状核实**：Spec 或 Ticket 中关于现有系统的断言，逐条给出代码依据；发现与代码不符时，按 M2 的 `spec-challenge` 处理。
3. **影响面**：本 Ticket 改动的每个对外契约、共享函数、表结构、配置、锁、错误码，各列出调用方或消费者，并写明检查结果；涉及发布期间新旧版本并存、存量数据、并发、权限、性能的，写明结论。
4. **对抗检查**：至少执行一项针对最可能出错路径的检查（负向测试、探针、边界输入），附命令和结果；确实无法执行时说明原因。
5. **简洁与约定**：有没有推测性代码、重复实现、只实现了样例的路径、违反项目分层或命名约定之处，以及做了哪些整理。
6. **已知缺口**：留给批次审查重点关注的地方。

runtime 只检查自审记录是否存在、各节是否齐全，不评判质量。

### M4. 批次审查

- **输入**：
  - 批次审查单元：从批次基线到批次最后一个提交的提交范围；
  - 批次内全部 Ticket 及其验收；
  - 当前有效 Spec；
  - 已决事项清单；
  - 适用的项目规则；
  - 各 Ticket 的影响面清单。影响面清单标注为"实施者声明，待核实"，审查者必须独立核实，实施者的设计理由不能降低严重度。
- **读取范围**：审查者可以在审查单元对应的提交上读取完整仓库，不限于改动文件。
- **视角**：一次审查覆盖 M2 的全部视角。影响面是必查视角：审查者要自己找出改动契约的调用方与消费者，并核对跨 Ticket 的集成与遗留代码。
- **独立性**：由新上下文的审查者执行，继承实施者的模型和思考档位，不降级；用户可以临时指定更强的模型。派发审查时不得给结论定调，例如"最多算小问题""不要报某类问题"。
- **规模大时**：可以按区域切片、并行派出多个审查者，再由主 Agent 合并去重。每个切片审查者都必须拿到全批次的改动清单，以免丢失跨区域的影响面。
- **高风险 Ticket 审查（按需，例外）**：
  - 实施者判断某张 Ticket 的风险明显高于同批次其他 Ticket 时，可以在它提交前额外派发一次逐 Ticket 独立审查。是否触发由 Agent 判断，不需要用户确认。
  - 可参考的风险信号：涉及 M5 所列承重类别（持久状态或存量数据、并发与锁、对外契约、发布与回滚兼容、改变其他模块的既有行为）、不可逆的数据迁移、权限与安全边界。命中信号不等于必须触发；多数 Ticket 不需要它，避免退化回逐 Ticket 独立审查。
  - 触发时，在该 Ticket 的自审记录中写明理由。审查绑定该 Ticket 的改动内容，输入为该 Ticket 的验收、当前有效 Spec 与影响面清单，读取范围、视角、发现格式和独立性同本节；`blocking` 和 `fix-in-batch` 项在该 Ticket 提交前处理完。
  - 它补充而不替代批次审查：批次审查照常进行，可以看到这次审查的结果，但不得因此缩小自己的范围。
- **多批次 Topic**：
  - 最后一个批次的审查，影响面覆盖整个 Topic 的改动。整分支审查不是 Topic 完成的前置条件。
  - **整分支审查（可选）**：用户要求时执行；Agent 判断跨批次风险较高时（例如多个批次改动了同一共享契约，或前序批次收口后又追加了补偿 Ticket）也可以执行，并记录理由，不新增找用户的环节。它在最后一个批次收口前进行，审查单元为 Topic 基线到当前提交，输入、视角、独立性、修复与复审规则同本节。修复作为最后一个批次的修复提交落在同一分支，即使涉及已收口批次的代码，也不新建补偿 Ticket。
- **修复与复审**：
  - 只有 `blocking` 和 `fix-in-batch` 的项进入修复。
  - 复审只看修复差异及其影响面。复审范围之外的新发现默认归为 `advisory/defer`。
  - 修复只允许改正、删除、收窄；需要新增要求时转为 `spec-challenge`。
  - 轮数上限与停止信号沿用现版审查循环的语义，不新增停止信号。
- **内容绑定**：批次收口时，当前 HEAD 必须等于最后一次通过审查的提交，或者两者之间的差异已经被复审覆盖；否则拒绝收口。

### M5. 设计审查

- **定位**：拆 Ticket 前唯一的独立设计关口。它只评审、不改文档、不重新访谈，也不替用户补齐决策。各环节分工如下：
  - 访谈：向用户取得决策和需求语义，能查到的事实当场查证。
  - `my-to-spec` / `my-tech-design`：作者对自己写下的承重现状断言负责，逐条给出依据（AC-27），并完成写作自检。
  - 设计审查：独立核实上述断言，并检查作者容易看不到的部分。
  - `my-to-tickets`：只负责切分和覆盖，不做设计审查。
  - 批次审查：从代码一侧发现的设计问题以 `spec-challenge` 回流。
- **检查项**（四组，缺一不可）：
  1. **承重现状断言核验**：在仓库（及方案引用的其他仓库或文档）中逐条核实承重现状断言。读代码是必做项，不是"必要时"。
  2. **影响面与上线兼容**：按术语"影响面"逐项检查方案对现有调用方、现有写路径与并发控制、存量数据、发布与回滚期间新旧版本并存（含锁键、配置键、表结构的变更顺序）、性能与数据量的影响。
  3. **方案内部成立**：待决策项、推导与依赖、内部一致性、异常与状态闭环；涉及公开接口、数据语义、迁移、持久状态时，检查更小或维持现状的方案能否得到同等结果，即复杂度是否必要。
  4. **需求语义与 Spec 挑战**：列出方案依赖但无法从代码或已决事项验证的产品或业务规则假设；方案与现有系统冲突、照方案做会导致可达故障时，按 M2 的 `spec-challenge` 提出。用户在审查请求中顺带给出的规则，同样属于待确认的假设，审查不能直接当成前提接受。
- **不属于设计审查的内容**：措辞、格式、最终态写作、篇幅，这些由作者自检和普通产物审查负责。
- **报告**：
  - **承重断言核验表**：每条断言标为三种之一：已核实（附代码或文档位置）、与现状不符（对应一条发现）、无法核实（转入 Spec 的"依据与未知"）。
  - **审查发现**：沿用 M2 的字段。位置写 Spec 章节；有代码依据时，同时写代码位置。视角取 `correctness`（方案内部）、`impact`、`spec-challenge`。
  - **已考察但排除的风险**：每条附一句排除理由和依据。
  - **待用户确认的需求语义假设**。
  - 某节无内容时写"无"，并附一句理由。
  - 每条发现用一个具体的出错场景或时序说明影响，不只写结论。
- **触发**：方案涉及下列任一类时，`my-to-spec` 与 `my-tech-design` 在定稿前自动执行一次设计审查：持久状态或存量数据、并发与锁、对外契约（接口、消息、表结构、配置键、错误码）、发布与回滚兼容、改变其他模块的既有行为。以上都不涉及时不触发，但要在 Spec 中写明"未触发设计审查"并附一句理由。用户可以随时单独调用。
- **轮数**：一次全面审查加最多一次复审。复审只看修复差异，以及修复可能影响到的断言和影响面。用户的"直到通过"一类指令不重置这个预算。仍未解决的问题列给用户裁决。
- **独立性**：由新上下文审查者执行；派不出时，按增强自审完成，并如实记为 `self`。
- **上报**：`spec-challenge` 发现和待确认的需求语义假设，在下一个现有对齐点一并交给用户，不新增对齐点。用户的裁决写入已决事项，之后的设计审查和批次审查不得重开。

## 行为与验收

### 1. 代码审查（`my-code-review` 与审查结果格式）

- AC-1 runtime 接受只带位置、视角、依据、严重度、没有验收锚点的审查发现；带验收锚点的发现照旧可以提交。
- AC-2 视角取值只能是 M2 列出的五种，取值非法时，报错要指出具体字段。
- AC-3 `blocking` 发现缺少位置或依据时，提交被拒绝，报错指出缺失字段。`advisory` 发现缺少处置时同样被拒绝。
- AC-4 审查结果仍然必须给出验收覆盖清单，漏掉任何一条验收时提交被拒绝。覆盖清单为"全部满足"不等于审查通过：存在 `blocking` 发现时，结论不能是通过。
- AC-5 审查结果含 `spec-challenge` 发现时，对应批次进入 `needs-user`，交付摘要和状态输出用平实中文说明需要用户决定什么。
- AC-6 `my-code-review` 正文以 M2 的五个视角组织审查，并明确写出：影响面为必查；不得以"Spec 要求如此"为由放行可达故障；验收覆盖只是 `spec` 视角的一部分。正文不再要求"Code pass / Spec pass 两遍"的固定仪式，审查方法由审查者按风险组织。
- AC-7 独立调用 `my-code-review`（不经 `my-implement`）时，默认报告范围包括本次改动直接调用路径上被放大的既有问题，并标注"既有/非本次引入"；与改动无关的旧问题仍不报告。
- AC-8 审查循环规则只在 `resources/review-loop.md` 定义一次；runtime 中不再保留第二份规则全文，需要时读取或引用该资源。

### 2. 批量实施与混合审查

- AC-9 `my-to-tickets` 在对齐点 2 展示批次划分及理由；默认整个 Topic 一个批次。用户确认的划分写入 Topic 的持久状态。
- AC-10 standard 下，一个干净批次（无审查发现）的完整路径是：逐张实施 → 定向测试 → 增强自审 → 本地提交，全部完成后跑批次全量测试 → 一次独立批次审查 → 收口。未触发高风险 Ticket 审查时，整个批次只派一次审查子 Agent；Agent 不需要手写或复制任何哈希、内容 id。
- AC-11 `my-implement` 写明高风险 Ticket 审查的风险信号，以及"多数 Ticket 不需要"的口径。触发时：
  - 该 Ticket 的自审记录必须写明触发理由；
  - 审查结果按 M2 格式记录，绑定该 Ticket 的改动内容，计入该 Ticket 与所属批次的审查记录，来源如实记为 `independent` 或 `self`；
  - 其中的 `blocking` 或 `fix-in-batch` 项未处理时，该 Ticket 不能提交；
  - 批次审查不因此被跳过或缩小范围。
- AC-12 Ticket 提交前，runtime 要求该 Ticket 声明的定向测试在当前内容上通过，且自审记录各节齐全；任一条件不满足就拒绝提交，并指出缺什么。
- AC-13 批次收口前，runtime 要求：
  - 批次内全部 Ticket 已提交；
  - 全量测试相对基线没有新增失败；
  - 存在绑定当前内容的批次审查通过记录，或用户的接受记录。
  - 任一条件不满足就拒绝收口，`status` 给出下一条应执行的命令。
- AC-14 批次审查的修复以批次修复提交落在同一分支，提交说明引用对应的审查发现；不为修复新建补偿 Ticket。批次收口后，再修改其中 Ticket 的结果，runtime 要求走补偿或迁移 Ticket；唯一例外是 AC-16 的整分支审查修复。
- AC-15 批次审查期间，内容在审查通过后又发生变化时，收口被拒绝，`status` 指向对变化部分的复审。
- AC-16 多批次 Topic 的最后一个批次收口后，Topic 即可完成，整分支审查不是前置条件；最后一个批次的审查材料包含整个 Topic 的改动清单。整分支审查按 M4 可选执行：
  - 在最后一个批次收口前进行，审查单元为 Topic 基线到当前提交；
  - 修复作为最后一个批次的修复提交承接，即使涉及已收口批次的代码，也不新建补偿 Ticket；
  - runtime 记录是否执行、由谁发起（用户 / Agent）及理由。执行了整分支审查时，最后一个批次收口还要求存在绑定当前内容的整分支审查通过记录。
- AC-17 宿主无法派出新上下文审查者时，批次审查以增强自审完成，结果如实记录为 `self`，交付摘要写明独立性缺口；runtime 不把它记成 `independent`。
- AC-18 quick 等级不受影响：仍然不建 Spec 和 Ticket，只做同会话自审，但自审记录使用 M3 的结构。

### 3. 实施质量（`my-implement`、`my-tdd`、执行简报）

- AC-19 `my-implement` 要求每张 Ticket 动手前完成实施计划，计划包括：要改的文件和接口；M3 第 2 节的现状核实；M3 第 3 节的影响面清单；每条验收对应的测试断言。现状核实发现 Spec 与代码不符时，先停下来按 `spec-challenge` 处理，不得任选一边直接实现。
- AC-20 runtime 生成的执行简报除现有内容外，还要包含：前置 Ticket 改动过的文件与契约；同批次已提交 Ticket 的影响面清单；Ticket 中给出的非约束性触点提示（见 AC-28）。
- AC-21 `my-tdd` 在红绿循环之后恢复一个受限的整理步骤：只在本 Ticket 触及的代码内，做行为不变的去重、命名、按项目分层调整放置位置；不做跨模块重构。测试预期值必须来自独立事实源（Spec、已知正确的字面量、演算示例），测试夹具不得照搬实现的数据来源。
- AC-22 `my-implement` 明确禁止为了让测试或检查通过而修改与 Ticket 无关的文件、配置或环境。测试因环境原因无法运行时，如实报告并按"环境阻塞"处理。
- AC-23 交付摘要的"审查发现与修复"一节按视角和来源（自审 / 批次审查 / 用户）分别列出发现数与修复数；`fix-in-batch` 的项写明已修复，`defer` 的项写明建议归属。

### 4. 测试分层与基线

- AC-24 Ticket 的 `test_commands` 是定向命令，必须能匹配配置条目（含 ` *` 前缀匹配），这一点保持不变。只有占位符、无法执行的命令无法通过 Ticket 校验。
- AC-25 Topic 第一个批次开始实施前，runtime 在批次基线上运行一次全量测试集合并记录结果，作为**测试基线**。批次收口时用全量测试与基线对比：基线已失败、现在仍失败的用例不阻断，但要列入交付摘要的"已知问题"；新增失败阻断收口。
- AC-26 某条全量命令在基线上根本无法运行（环境缺失）时，runtime 将其记为"无法验证"，不阻断收口，但交付摘要的"未验证项"必须列出该命令，状态输出也要明确提示。

### 5. Spec、Ticket 与设计审查（`my-to-spec`、`my-tech-design`、`my-to-tickets`、`my-review-design`）

- AC-27 `my-to-spec` 的模板新增两节：
  - **"现状事实"**：每条关于现有系统行为、数据、接口的断言，附可定位的依据（模块、函数或接口名，或实际查询或执行结果）。无法核实的断言列入"依据与未知"。
  - **"系统影响"**：逐项写明调用方与消费者、存量数据与迁移、发布与回滚期间新旧版本并存、并发与锁、权限、性能与数据量、可观测性。不涉及的项写"无"并附一句理由。
- AC-28 Ticket 的 frontmatter 不再强制 `rule_sources`、`rule_scope`、`rule_constraints`、`rule_conflicts`；适用规则由 runtime 在开始实施时按实际路径解析。Ticket 可以带一个非约束性的"触点提示"，列出预计涉及的模块、目录或契约，供执行简报和审查参考，不作为写入边界。现版已有这些字段的 Ticket 仍然可以读取和实施。
- AC-29 `my-to-tickets` 要求：每张 Ticket 完成后系统处于一致、可发布的状态。不允许一张 Ticket 明知会留下可达缺陷、等后续 Ticket 修复，除非对齐点 2 明确确认，并且该中间状态有开关或其他隔离手段。Ticket 正文不写死非契约性的实现细节，例如内部函数名、局部算法步骤。
- AC-30 修订 Spec 时，新版本整合全部修改，不在正文末尾追加"第 N 轮修正"一类补丁段落；被替代的版本状态改为 `superseded`，同一 `spec_id` 任一时刻只有一个 `current`。
- AC-31 Spec 篇幅与改动规模相称。`my-to-spec` 给出一个以 Ticket 数量为基准的参考上限（由施工者设定）；超出时必须在 Spec 开头说明原因。承重决策的论证只写一到两句，详细推理写入 ADR 或 Topic 内的决定记录。
- AC-32 Spec、技术方案与 Ticket 的文档审查（设计审查及主 Agent 临时派发的文档审查）只做一次全面审查加最多一次复审：复审只看修复差异及其可能影响到的断言和影响面；仍有未解决的问题时，列给用户裁决，不再开新一轮。用户要求"直到通过"或扩大范围时，同样不重置这个预算。`resources/review-loop.md` 中文档审查的轮数规则相应改为这一口径。
- AC-33 `my-review-design` 正文按 M5 的四组检查项组织：承重现状断言核验、影响面与上线兼容、方案内部成立、需求语义与 Spec 挑战。正文明确写出：读代码核实承重现状断言是必做项；措辞、格式、最终态写作不属于设计审查；考察过、但判断不构成问题的风险，必须写入"已考察但排除的风险"，不能靠推理静默丢弃。
- AC-34 设计审查报告包含 M5 规定的四个部分：承重断言核验表、审查发现、已考察但排除的风险、待用户确认的需求语义假设。缺少任一部分，或核验表中有"与现状不符"的断言却没有对应的发现，宿主都不得把这次设计审查记为通过。
- AC-35 `my-to-spec` 与 `my-tech-design` 在方案涉及 M5 所列任一承重类别时，定稿前自动执行一次设计审查，由新上下文审查者完成；派不出时如实记为 `self`。不涉及时，在 Spec 或方案中写明"未触发设计审查"及一句理由。`my-to-tickets` 不执行设计审查；拆分中发现设计问题时，退回 Spec 修订，不在 Ticket 正文里补设计。
- AC-36 设计审查中的 `spec-challenge` 发现和待确认的需求语义假设，由宿主在下一个现有对齐点用平实中文列给用户，每条写明需要用户决定什么；Agent 不自行裁决。用户裁决写入已决事项后，设计审查和批次审查都不得重开。

### 6. 访谈与交接（`my-grilling`、`my-grill-with-docs`、`my-handoff`）

- AC-37 访谈结束时的需求摘要新增"待在代码中核实的现状假设"一项，供 `my-to-spec` 的"现状事实"逐条核实；能在访谈阶段直接查到的事实，访谈阶段就查证，不问用户。
- AC-38 `my-handoff` 涉及实施进度时，以 runtime 的 `status` 输出为准并引用它，不在交接中手工转述 Ticket 或批次的完成状态。

### 7. 度量与逃逸缺陷

- AC-39 度量记录新增按视角、来源（自审 / 批次审查）、严重度统计的发现数，每个批次派出的审查子 Agent 数，高风险 Ticket 审查的次数及其中有 `blocking` 发现的次数，以及每个多批次 Topic 是否执行了整分支审查及其发现数。
- AC-40 runtime 提供一个记录逃逸缺陷的入口：审查之后才发现的缺陷可以登记到 Topic（可细化到批次、Ticket），字段包括发现来源（人工评审、外部审查工具、测试环境、生产、后续开发）、所属视角、本应抓到它的环节（访谈、Spec 编写、设计审查、实施自审、批次审查），以及简述。缺陷发生时该 Topic 是否跑过设计审查，由 runtime 根据已有记录自动带出；没有记录时标为"未知"。已归档的 Topic 也可以登记。
- AC-41 `metrics` 汇总输出每个 Topic 的逃逸缺陷数，并按"本应抓到它的环节"分组。

### 8. 文本与一致性

- AC-42 主链（访谈 → Spec → Ticket → 实施 → 审查）运行一次需要加载的 Skill 与共享资源文本总量不超过 35,000 字符。
- AC-43 README 的使用流程与命令说明更新为批次模型，整分支审查从必经步骤改为可选步骤，并说明高风险 Ticket 审查的用法；面向用户的输出不出现内部状态名，用平实中文说明。

## 不变量与失败边界

**I-1**：任何 Ticket 都不能在定向测试未通过、或自审记录缺节的情况下提交。

**I-2**：任何批次都不能在全量测试相对基线有新增失败、或缺少绑定当前内容的审查通过记录（或用户接受记录）的情况下收口。

**I-3**：同一 Topic 同一时间最多一个批次处于 `open` 或 `reviewing`。

**I-4**：`self` 来源的审查永远不能记录为 `independent`。

**I-5**：含 `spec-challenge` 发现的审查不能以"通过"收口，必须经过用户裁决。

**I-6**：批次收口后，其中 Ticket 的结果不可原地改写，只能通过补偿或迁移 Ticket 改变；唯一例外是整分支审查的修复，它作为最后一个批次的修复提交承接。
**I-7**：审查发现的准入不依赖验收编号；任何提交路径都不能因为某条发现没有验收锚点而拒绝它。

**I-8**：Agent 不会为了让测试或检查通过而修改与当前 Ticket 无关的文件、配置或环境。

**I-9**：现版"测试失败仍提交、审查后内容漂移、越序、审查记录与审查单元不匹配"四类机械检查继续有效。

**I-10**：设计审查不能在缺少承重断言核验表、或核验表中存在未转为发现的"与现状不符"断言时记为通过。

**I-11**：同一设计产物的设计审查最多一次全面审查加一次复审；之后仍有未解决问题时，只能由用户裁决结束，任何指令都不能开启第三轮。

**I-12**：高风险 Ticket 审查和整分支审查都不能替代批次审查；任何批次收口都需要它自己的批次审查通过记录（或用户接受记录）。

## 已确认的承重决策

1. **审查发现以"位置 + 可达出错路径或被违反的规则"准入，不以验收锚定。**
   - 服务：目标 1，AC-1～AC-7。
   - 依据：真实漏网缺陷几乎都在验收之外；现版准入规则让这类缺陷无法登记。
   - 排除：保留验收锚定、只放宽 advisory。advisory 永远不会被修复，问题照样漏过。
   - 推翻条件：端到端测试中，审查者大量报出没有出错路径的噪声，导致修复循环不收敛。由 AC-3 的字段要求和停止信号拦截。
2. **"逐 Ticket 增强自审 + 批次独立审查"成为默认，取代"逐 Ticket 独立审查 + 必经的整分支审查"；保留两个按需的例外。**
   - 服务：目标 2，AC-9～AC-18。
   - 内容：
     - 默认每张 Ticket 增强自审，每个批次一次独立审查。
     - 高风险 Ticket 可以额外做一次逐 Ticket 独立审查，由 Agent 按风险判断并记录理由。
     - 多批次 Topic 可以在最后一个批次收口前选做一次整分支审查，由用户要求或 Agent 按跨批次风险判断。
   - 依据：真实记录中，逐 Ticket 独立审查普遍几乎零产出，而批次和整分支层面的审查抓到了集成和影响面缺陷；自审确实能抓到 Ticket 内部的缺陷。少数高风险改动（并发、迁移、对外契约）出错代价高，值得在提交前多一道独立检查；多批次时，跨批次的共享契约改动可能超出单个批次审查的视野。
   - 排除：
     - 默认保留逐 Ticket 独立审查：子 Agent 切换和上下文重复加载的成本高，产出低。
     - 只做批次审查、不做自审：Ticket 内部缺陷会堆积到批次末尾。
     - 完全取消逐 Ticket 独立审查和整分支审查：高风险改动和跨批次影响失去兜底。
   - 推翻条件：
     - 逃逸缺陷度量（AC-40、AC-41）显示"本应由实施自审抓到"的缺陷明显增多；
     - 度量（AC-39）显示高风险 Ticket 审查被频繁触发，使批次的子 Agent 数接近逐 Ticket 独立审查，或者它几乎从不产出 `blocking` 发现：应收紧触发信号。
3. **批次审查的修复留在批次内完成，批次收口后才适用"已完成即历史"。**
   - 服务：目标 2。
   - 依据：现版独立审查发现的每个问题都变成一张补偿 Ticket，流程材料与代码改动之比可达 100:1 以上。
   - 排除：继续用补偿 Ticket 承接批次审查发现。
4. **Spec 中的现状断言必须有依据，并要求写"系统影响"；设计审查只做一次，专查现状事实、影响面与上线兼容、需求语义假设。**
   - 服务：目标 4，AC-27、AC-32～AC-36。
   - 依据：
     - 错误的 Spec 事实是返工最昂贵的来源。
     - 设计审查的首轮确实能在实施前抓到现状事实错误，大多数发现是实质问题。
     - 循环审查主要在审上一轮补丁，只让 Spec 膨胀。
     - 设计审查跑过之后仍然漏网的设计级缺陷，全部落在它当前检查项之外：影响面、上线兼容、需求语义。
   - 排除：
     - 增加 Spec 审查轮数：外部实验和本地记录都表明，这只增加成本，不提升质量。
     - 取消设计审查、只靠作者自检：首轮审查抓到的现状事实错误大多是作者自检放过的，而且作者自检与审查结论出自同一 Agent 时没有独立性。
     - 让设计审查同时负责措辞与一致性：循环审查的轮次主要就耗在这里。
   - 推翻条件：逃逸缺陷度量（AC-40、AC-41）显示，"本应由设计审查抓到"的缺陷没有下降；或者设计审查的发现以措辞和一致性为主。
5. **测试按"定向 / 全量 + 基线"分层。**
   - 服务：目标 5。
   - 依据：真实项目中，全量测试在本地环境本来就失败，导致 Ticket 永远无法在流程内完成，Agent 还为此去改无关文件。
   - 排除：每张 Ticket 都跑全量测试，单次可能耗时十几分钟以上，而且受环境影响。

## 验证策略

- **runtime 单元测试**：覆盖批次状态迁移、AC-12/AC-13 的提交与收口前置条件、新的审查发现格式与报错（AC-1～AC-5）、测试基线对比（AC-25、AC-26）、逃逸缺陷登记与汇总（AC-40、AC-41）、高风险 Ticket 审查的记录与提交拦截（AC-11）、多批次 Topic 不做整分支审查也能完成，以及执行整分支审查时其修复可以落在最后一个批次（AC-16）、I-1～I-9 与 I-12；I-10、I-11 由文本检查和设计审查演练覆盖。
- **端到端测试**（临时玩具仓库，脚本驱动）：
  - 一个 3 张 Ticket 的批次，其中第 2 张修改了一个共享函数的语义，导致改动范围外一个调用方的行为错误。用脚本提交一份含 `impact` 视角、无验收锚点的 `blocking` 发现：runtime 接受该发现，批次收口被拒绝；批次修复提交并复审通过后，收口成功。
  - 一个干净批次：从开始到收口只记录一次审查派发，不需要手写任何哈希。
  - 一个批次中有一张 Ticket 触发高风险 Ticket 审查：该审查的 `blocking` 发现未处理时，这张 Ticket 提交被拒绝；处理后可以提交，批次审查仍然必须执行。
  - 基线上已失败的用例不阻断收口，新增失败会阻断。
  - 含 `spec-challenge` 的审查使批次进入 `needs-user`。
  - quick 链路保持可用。
- **文本检查**：
  - 主链文本量（AC-42）；
  - 审查循环规则只有一处来源（AC-8），文档审查轮数为一次全面审查加一次复审（AC-32）；
  - `my-review-design` 正文含 M5 的四组检查项和报告的四个部分，且不再出现"必要时"查阅代码的表述（AC-33、AC-34）；
  - `my-to-spec` 与 `my-tech-design` 写明设计审查的触发类别，以及"未触发设计审查"的记录方式（AC-35）。
- **设计审查演练**（用施工者自己构造的玩具 Spec 和仓库，派新上下文审查者运行一次）：
  - Spec 中故意写错一条现有接口的行为，并写一处改名锁键、却不考虑新旧实例并存的设计。预期结果：核验表把前者标为"与现状不符"并给出发现；后者作为 `impact` 发现报出。
  - Spec 中写入一条无法从代码验证的业务规则。预期结果：这条规则出现在"待用户确认的需求语义假设"中。
  - 演练结果作为交付证据附上；模型判断存在波动，未命中时如实写入"未验证项"，不为了命中去修改玩具 Spec。
- **局限**：单元测试和端到端测试只能证明机械契约，不能证明模型实际审查得更好。"审查能抓到影响面缺陷"的效果要靠真实项目上的逃逸缺陷度量来观察，不在本 Spec 的验收范围内；交付摘要的"未验证项"必须如实写明这一点。

## 施工分段

本 Spec 分五段施工，由同一个施工者在同一个工作分支上按顺序完成，不开 PR。段内的设计与实现方式由施工者决定。施工者直接按本 Spec 施工，以测试和验收标准验收，不用本仓库自身的 Topic / Ticket 工作流和审查 Skill（包括 `my-implement`、`my-code-review`）施工或审查。

1. 审查发现格式与准入（AC-1～AC-8）：改动最小，对质量的影响最大。
2. 批次模型与混合审查（AC-9～AC-18，含高风险 Ticket 审查与可选整分支审查），同时完成测试基线（AC-24～AC-26）。
3. 实施质量相关的 Skill 文本与执行简报（AC-19～AC-23）。
4. Spec 与 Ticket 的模板与规则（AC-27～AC-36），访谈与交接（AC-37、AC-38）。
5. 度量与逃逸缺陷（AC-39～AC-41），README 与文本量收尾（AC-42、AC-43）。

分段约束：
- 每段提交后，仓库必须处于一致、可用的状态：全部测试通过，现有工作流仍能端到端运行；尚未施工的段对应的旧行为保持不变。
- 每段只实现本段的 AC，以及本段 AC 直接需要的不变量和测试；设计上不得与后续段冲突，也不提前实现后续段。
- 后段可以修正前段的实现，但要在最终报告中说明原因。
- 文本量上限（AC-42）在每段结束时都不得被突破，不必等到第 5 段才处理。

每段的收口：
1. 实现本段，运行全部测试。
2. **段审查**：派一个新上下文的 subagent 做独立审查。它只审查、不改代码，不采信施工者的结论，自己运行测试，覆盖三方面：本段 AC 是否真正满足（抽查证据）；影响面（已有命令与输出、README、其他 Skill 和资源中的引用、未施工段的旧行为、本段涉及的不变量）；代码本身（正确性、边界与错误路径、可维护性、是否越出本段或 Spec 的范围边界）。每条发现写明位置、问题、可达的出错路径或违反的 AC / 不变量 / 规则，以及严重度（blocking / advisory）；不报猜测和纯风格意见。派发时不得给结论定调。
3. 修复全部 blocking 发现，以及影响面内、代价小的 advisory 发现；之后由新上下文 subagent 复审一次，只看修复差异及其影响面。
4. 本段提交，提交信息标明段号。复审后仍有未解决的 blocking 发现时，停止施工，不进入下一段，在最终报告中说明。
5. 无法派出 subagent 时，以结构化自审代替，并在最终报告中如实写明这是自审。

全部五段完成后：
- **整体审查**：派一个新上下文 subagent，对整个工作分支相对起点的改动做一次独立审查，重点看跨段的集成、影响面和遗留代码；修复与复审规则同上。
- **最终报告**：AC-1～AC-43 逐条对照（满足情况 + 证据位置）；实际运行的测试命令及结果；各段审查和整体审查的发现数与修复情况；偏离 Spec 之处及理由；未验证项（含"验证策略"中"局限"要求写明的内容）。

## 依据与未知

- **依据**：
  - 多个真实项目在本工作流前两代版本下留下的 Spec、Ticket、审查结果、提交历史和对话记录；
  - 本仓库 `workflow-simplification` 施工过程的审查记录；
  - 现版 runtime 的审查准入代码；
  - 公开的同类工作流（每任务审查、全部完成后整分支终审、"不要相信实施者报告"的审查规则）及其实验结论。
  - 具体项目细节不进入本文。
- **未知 1**：现版（`workflow-simplification` 之后）还没有在任何真实项目上运行过。部分摩擦可能已被现版解决，但本文针对的审查准入、批次模型和 Spec 事实问题在现版中仍然存在，已通过阅读现版代码与文本确认。
- **未知 2**：批次规模阈值没有实测依据，施工者设定的初值应保守，并在交付摘要中说明。
- **未知 3**："增强自审"能抓到多少 Ticket 内部缺陷，只有本仓库自己的施工记录作为参考。若逃逸缺陷度量显示自审漏网明显增多，应重新评估承重决策 2。
- **未知 4**：设计审查的结论来自少数几个真实设计上的约 50 轮审查，其中大部分轮次属于两次长循环；单次审查的样本只有十余条发现，没有对照组。新增的影响面与需求语义检查项能否抓到同类漏网缺陷，尚未验证，由 AC-40、AC-41 的度量观察。
- 本文的承重决策来自一次针对真实使用的审查，已全部经用户确认：决策 1、3、4、5 按原文确认；决策 2 按用户意见增加了"高风险 Ticket 审查"和"可选整分支审查"两个按需例外；默认整个 Topic 为一个批次。施工者不需要再次征求确认。
