# Workflow Optimization Principles

## P1 Skill 轻量有弹性

Skill 保持轻量，聚焦领域方法与选择条件；分支专属资料按需加载，确定性工作交给脚本或共享运行规则。设计阶段不提前锁死可逆的实现细节。安全、权限、兼容与迁移、证据真实性、完成门禁必须明确。只有决策会改变目标、范围、公开接口、数据语义、测试投入或风险承担，且无法从已确认材料推断时，才上报用户；普通、可逆的实现选择由 Agent 自主决定。

## P2 面向人的文档读者导向

编写面向人的文档前，先明确主要读者、用途、读者看完后要作出的决定或动作、已有知识，以及最关心的风险。文档结论先行，只保留支撑其用途所需的背景与证据；篇幅由问题复杂度和读者需要决定，不设统一字符上限，也不以“越短越好”为目标。读者分析是写作约束，不要求机械地作为固定章节展示在成品中。

## P3 表达方式按读者选择

根据读者任务和信息形状选择最小、最清楚的表达方式。面向人的文档，仅当图示、表格或图表能明显降低理解成本时才使用，例如复杂比较、映射、流程、状态变化或拓扑关系；简单内容使用文字。面向 Agent 的 Spec、Prompt、Skill 和 Ticket，优先使用明确的文字定义、结构化字段、显式约束和可解析状态；复杂流程或依赖确实更适合图示时可以辅助使用，但关键规则必须同时有文字定义。任何文档都不默认要求图示或“总览图”。

## P4 `my-teach` 课程质量

制定课程前，确认学习者是初学者还是已有基础，并了解其现实学习任务、当前能力证据和成功标准。课程按心智模型、引导练习、迁移练习、真实任务逐步加深；习题必须来自可信的真实场景，有明确练习价值和反馈标准。深度以学习者能够解释原理、迁移知识并完成真实任务为准，可增加篇幅与课程数量，但每课应有一个可验证的学习收获。文风与前置解释适配学习者水平。事实与技术内容优先通过一手资料、当前版本文档和可运行示例校验；无法确认的内容明确标注，不凭模型记忆补写。

## P5 `my-humanizer` 不造词

`my-humanizer` 不得为了显得高级、简短或有文采而自造词，也不使用无必要的生僻词和空泛抽象名词。优先采用项目既有术语、权威资料中的专业术语和普遍通行的常用表达，并保持全文一致；专业术语首次出现时，用通俗语言解释。不能仅凭“动词＋宾语”的语法形式判定一个词不合法，因为“状态查询”“规则解析”等可能是既有专业表达。确实出现现有词无法准确表达的新概念时，应说明定义与必要性，并让用户确认后再引入。描述保持简明，但不能以删掉关键含义换取简短。

## P6 内容、排版、模板分离

内容事实、文档结构与视觉呈现应保持独立职责：事实来自用户输入、项目材料或来源账本；可复用的章节骨架放在模板中；样式、版式和渲染资源放在 assets 或专用工具中。Skill 正文只保留方法、选择条件和关键约束；确定性生成或校验交给 scripts；体积较大且仅特定分支使用的参考资料按需加载。只有当内容需要独立更新、复用、验证或选择性加载时才拆分；很小、只使用一次的模板可以内联，避免产生没有收益的文件和指针。

对带前端渲染的文档型 Skill，保留一个用户入口，但内部拆成可独立调用的内容阶段和前端阶段。内容阶段产出结构化语义工件，包含读者与用途、结论、证据、章节结构、关系及必要的可视化意图，不编写 HTML、CSS 或 JavaScript；前端阶段只消费该工件和既有模板，负责布局、样式、交互、响应式适配与视觉验收，不得擅自改变事实、结论或约束。渲染时发现内容缺口，退回内容阶段修订。两个阶段之间必须有明确交接点，使运行时能够分别分配内容推理模型与前端模型；原则只定义模型角色，不写死具体模型名称。该规则适用于文档渲染，不机械套用到以前端行为本身为验证对象的 UI 原型。

## P7 高遵循模型下的指令确定性

### P7.1 指令权威

平台和宿主的硬约束不可覆盖。当前用户目标与明确授权决定任务范围；项目原生规则约束其适用路径内的实现和验证，但不能扩大任务范围或授予写操作权限。已批准的 Spec 与 Ticket 约束交付内容；profile 与 runtime gate 决定自治和写入；shared policy 与 adapter 定义通用方法；Skill 建议、默认值和示例的优先级最低。

项目原生规则与用户目标不能同时满足时，明确报告冲突及来源，不擅自覆盖任一方。能够按宿主原生作用域和覆盖规则消解的差异不算未解决冲突。

### P7.2 确认门槛

只有用户专属决定、不可逆或外部写入、新增任务范围、新增授权需要阻塞并等待确认。用户明确要求执行某项工作时，视为已经授权完成其中可合理推断的可逆本地步骤；Agent 应先完成到可审阅状态，再在真正需要授权的边界确认。

`decision_policy: ask` 只适用于会改变目标、范围、公开接口、数据语义、测试投入或风险承担的承重决定，不适用于普通技术细节。有意的 Grill HITL、内容与前端交接、破坏性操作和外部写入门禁继续保留。

### P7.3 测试范围

改动过程中运行能最快证明当前行为的最小针对性测试；Ticket 完成时运行受影响模块或链路的测试；整份计划完成、发布或合并前、项目规则明确要求，或者风险和失败证据表明影响面扩大时，才运行完整测试套件。针对性验证已经通过后，除非出现新改动、新失败或未解决风险，不重复或无理由扩大测试。

项目定义的权威门禁始终执行。安全、迁移、数据一致性等高风险改动可以直接升级验证范围。本 workflow 项目的每批源码改动仍必须通过 `python3 tools/workflow.py check`。

### P7.4 无法复现 Bug 时的推进方式

暂时无法建立 red loop 时，Agent 继续收集已授权的只读证据，包括日志、配置、Git 历史、现有测试、调用链和相关文档，并明确标记“尚未复现”。可以在临时或隔离环境中尝试安全、可回滚的复现探针。没有可变红证据前，不得宣称已定位根因，也不得实施猜测性修复。

只有后续路径会改变目标、范围、公开接口、测试投入或风险承担，或者需要人工操作、新权限、外部系统写入时，才暂停询问。`decision_policy: halt` 仍按配置停止。

### P7.5 子代理使用

仅在宿主提供子代理能力、用户未禁止、任务可以独立切分且并行确实有收益时使用子代理。数量由任务规模、风险和并发容量决定，不设固定下限；能力不可用或并行收益很低时，由主 Agent 串行完成，只有独立环境本身是验证前提时才报告能力缺口。

子代理产出属于待审查证据，不能替代主 Agent 的责任。主 Agent 负责合并结论、处理冲突、验证关键事实，并完成最终门禁与对用户的交付。
