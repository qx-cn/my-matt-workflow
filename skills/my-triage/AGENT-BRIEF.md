# 编写 Agent 简报

当 Issue 或 PR 移至 `ready-for-agent` 时，Agent 简报是一条发布在 GitHub 上的结构化评论。它是离线 Agent 将据以工作的权威规格；原始正文和讨论只是上下文——Agent 简报才是契约。

简报应说明**Agent 要做什么**，涵盖两种表面：对 Issue，是从零构建变更；对 PR，是为*现有 diff*完成剩余工作——补全它、填补缺口、处理审查意见。两者遵循同样的原则；下文 PR 示例展示差异。

## 原则

### 持久性优先于精确性

Issue 可能在 `ready-for-agent` 停留数天或数周。其间代码库会变化。编写简报时，应使它即使在文件被重命名、移动或重构后仍然有用。

- **应当**描述接口、类型和行为契约
- **应当**命名 Agent 应查找或修改的特定类型、函数签名或配置形状
- **不要**引用文件路径——它们会过时
- **不要**引用行号
- **不要**假定当前实现结构会保持不变

### 描述行为，而非过程

描述系统**应做什么**，而不是应**如何**实现。Agent 会重新探索代码库并作出自己的实现决策。

- **好：**“`SkillConfig` 类型应接受一个类型为 `CronExpression` 的可选 `schedule` 字段”
- **坏：**“打开 src/types/skill.ts，并在第 42 行添加 schedule 字段”
- **好：**“当用户不带参数运行 `/triage` 时，应看到需要关注的 Issue 摘要”
- **坏：**“在主处理函数中添加 switch 语句”

### 完整的验收标准

Agent 需要知道何时完成。每份 Agent 简报都必须有具体、可测试的验收标准。每条标准都应可独立验证。

- **好：**“运行 `gh issue list --label needs-triage` 会返回已经过初步分类的 Issue”
- **坏：**“分诊应正常工作”

### 明确的范围边界

说明哪些内容超出范围。这可防止 Agent 过度打磨，或对相邻功能作出假设。

## 模板

```markdown
## Agent 简报

**类别：** bug / enhancement
**摘要：** 需发生事项的一行描述

**当前行为：**
描述现在发生什么。对于 Bug，这是损坏的行为。
对于增强，这是该功能所建立的现状。

**期望行为：**
描述 Agent 完成工作后系统应如何表现。
具体说明边界情况和错误条件。

**关键接口：**
- `TypeName` —— 需要改变什么，以及为什么
- `functionName()` 返回类型 —— 当前返回什么，对比应返回什么
- 配置形状 —— 所需的任何新配置选项

**验收标准：**
- [ ] 具体、可测试的标准 1
- [ ] 具体、可测试的标准 2
- [ ] 具体、可测试的标准 3

**超出范围：**
- 本 Issue 不应更改或处理的事项
- 看似相关但实际独立的相邻功能
```

## 示例

### 好的 Agent 简报（Bug）

```markdown
## Agent 简报

**类别：** bug
**摘要：** Skill 描述截断时丢失词中部分，产生损坏的输出

**当前行为：**
当 Skill 描述超过 1024 个字符时，无论单词边界为何，都会恰好在第
1024 个字符处截断。这会产生以词中部分结尾的描述（例如
“Use when the user wants to confi”）。

**期望行为：**
截断应在 1024 个字符之前的最后一个单词边界处发生，并追加
“...” 表示已截断。

**关键接口：**
- `SkillMetadata` 类型的 `description` 字段 —— 无需修改类型，
  但填充该字段的验证/处理逻辑必须尊重单词边界
- 任何读取 SKILL.md frontmatter 并提取描述的函数

**验收标准：**
- [ ] 少于 1024 个字符的描述保持不变
- [ ] 多于 1024 个字符的描述在 1024 之前的最后一个单词边界截断
- [ ] 被截断的描述以 “...” 结尾
- [ ] 包含 “...” 在内的总长度不超过 1024 个字符

**超出范围：**
- 改变 1024 字符限制本身
- 支持多行描述
```

### 好的 Agent 简报（增强）

```markdown
## Agent 简报

**类别：** enhancement
**摘要：** 新增 `.out-of-scope/` 目录支持以记录被拒绝的功能请求

**当前行为：**
当功能请求被拒绝时，Issue 会以 `wontfix` 标签和评论关闭。决策或理由
没有持久记录。未来遇到类似请求时，维护者需要回忆或搜索既往讨论。

**期望行为：**
被拒绝的功能请求应记录在 `.out-of-scope/<concept>.md` 文件中，
其中包含决策、理由以及请求该功能的全部 Issue 链接。分诊新 Issue 时，
应检查这些文件是否匹配。

**关键接口：**
- `.out-of-scope/` 中的 Markdown 文件格式 —— 每个文件应有
  `# Concept Name` 标题、`**Decision:**` 行、`**Reason:**` 行，
  以及包含 Issue 链接的 `**Prior requests:**` 列表
- 分诊工作流应尽早读取全部 `.out-of-scope/*.md` 文件，
  并按概念相似性匹配传入的 Issue

**验收标准：**
- [ ] 以 wontfix 关闭功能会在 `.out-of-scope/` 中创建或更新文件
- [ ] 文件包含决策、理由和已关闭 Issue 的链接
- [ ] 若匹配的 `.out-of-scope/` 文件已存在，新 Issue 会追加到其
      “Prior requests” 列表，而不是创建重复文件
- [ ] 分诊期间会检查并展示已有 `.out-of-scope/` 文件，
      当新 Issue 与既往拒绝匹配时亦然

**超出范围：**
- 自动匹配（由人工确认匹配）
- 重新打开以前被拒绝的功能
- Bug 报告（仅增强被拒绝时写入 `.out-of-scope/`）
```

### 好的 Agent 简报（PR）

对于 PR，“当前行为”描述 diff 的状态，简报要求 Agent 完成或修复它，而非从零构建。

```markdown
## Agent 简报

**类别：** enhancement
**摘要：** 完成贡献者为 `triage list` 添加的 `--json` 输出标志

**当前行为：**
该 PR 添加了将 Issue 列表序列化为 JSON 的 `--json` 标志。正常路径可用，
且 diff 符合项目命令结构。仍有两个缺口：错误仍以人类文本输出（而不是 JSON），
且新标志没有测试覆盖。

**期望行为：**
使用 `--json` 时，所有输出——包括错误——都在 stdout 上为格式良好的 JSON，
并且命令退出码不变。没有该标志时，既有的人类可读输出保持不动。

**关键接口：**
- 命令错误路径在使用 `--json` 时应输出 `{ "error": string }`，
  而非纯文本错误
- 复用 PR 已添加的序列化器；不要引入第二个

**验收标准：**
- [ ] `triage list --json` 在成功和错误场景都输出有效 JSON
- [ ] 退出码与非 JSON 命令一致
- [ ] 有一项测试覆盖 `--json` 成功输出和一项错误场景
- [ ] 默认（非 JSON）输出逐字节保持不变

**超出范围：**
- 为任何其他命令添加 `--json`
- 改变 PR 已定义的成功载荷 JSON 形状
```

### 不好的 Agent 简报

```markdown
## Agent 简报

**摘要：** 修复分诊 Bug

**要做什么：**
分诊功能坏了。查看主文件并修复它。
第 150 行附近的函数有问题。

**要修改的文件：**
- src/triage/handler.ts（第 150 行）
- src/types.ts（第 42 行）
```

它不好，因为：
- 没有类别
- 描述模糊（“分诊功能坏了”）
- 引用会过时的文件路径和行号
- 没有验收标准
- 没有范围边界
- 没有描述当前行为与期望行为
