# 架构候选内容阶段

只负责代码库探索、候选判断与语义工件，不生成 HTML、CSS、SVG 或 JavaScript。

## 范围与证据

用户给出模块、子系统或痛点时采用该范围；否则用足够长的 Git 历史找反复变动的热点，热点不明显再扩大。读取项目配置指定的领域术语、相关 ADR、规则和测试，不假设固定存在 `CONTEXT.md` 或 `docs/adr/`。

使用 `my-codebase-design` 的模块、接口、深度、接缝、适配器、杠杆、局部性词汇。探索理解摩擦：

- 理解概念是否需要跨许多浅模块跳转；
- 接口是否几乎和实现一样复杂；
- 为测试而抽出的纯函数是否失去调用局部性；
- 紧耦合模块是否跨接缝泄漏；
- 当前接口是否让重要行为难以测试。

对候选应用删除测试：删除它若只移动复杂度，不算深化机会；能把复杂度集中进更小接口后方，才保留。

## 候选判断

每个候选记录：

- 稳定 `candidate_id`、标题、涉及模块与文件；
- 有代码、测试或变更历史支持的摩擦；
- 通俗的深化方向，但不预先设计接口；
- 局部性、杠杆和测试面的具体收益；
- 成本、回归风险、ADR 冲突和未知；
- `Strong`、`Worth exploring` 或 `Speculative` 推荐强度及理由。

按决策价值排序，给出首要推荐。只有当结构、依赖、调用顺序或前后变化用图能明显降低维护者理解成本时才添加 `visual_intent`；候选不默认需要前后图。

## 语义工件

按共享交接格式设置 `document_kind: architecture-review`、临时 HTML 输出路径与 `template_ref: HTML-REPORT.md`。正文包含 reader brief、结论、证据与未知、候选列表、首要推荐。每个候选是独立 `section_id`，且所有代码事实带文件位置或命令证据。

保存前确认：候选来自证据而非启发式清单；推荐强度可解释；ADR 冲突只在摩擦足以重开决定时出现；没有前端实现。
