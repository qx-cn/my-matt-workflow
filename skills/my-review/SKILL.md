# 审查

派一个新上下文的子 Agent 做独立只读审查（派不出子 Agent 时说明原因，改为自审并标明是自审）。子 Agent 不会自动继承父会话内容，传资料时注意别带偏它：

- **只传原始材料，别传你的总结或辩解**：本地能读的文件（仓库路径、基准 commit、改动与未跟踪文件列表、已有的 `design.md` / `refs/`、规范文件）只传路径，让子 Agent 自己跑 `git diff` 和 `Read`；没有本地路径的内容（聊天里的原始需求、个人规则、抓下来的飞书文档或画板预览图）原样贴全文。初审不传旧审查记录，任何时候都不要传主 Agent 自己总结的改动导览、“为什么这么写合理”的解释或自夸式测试小结。
- **缺少依据直说**：核实不到的地方写明缺什么材料，不自己脑补事实。

代码和文档统一分两级报告：

- **必须修**：会导致运行错误、漏掉或违背核心需求与对外契约、有安全隐患、严重妨碍读者理解（如乱翻英文原词、满篇黑话、缺关键图表样例、大坨文字墙、画板撞框漏边），或违反仓库明文规则（贴出规则原话）。写清出错场景或卡住读者的具体位置。
- **建议**：其余值得作者留意的问题，如可维护性、补充测试、需要进一步核实的疑问（写明核实什么）、细微措辞或审美偏好，以及改动文件里原本就有的老问题（标“既有”）。

每条写明级别、文件与行号（无行号时写章节和原句）、问题和原因。纯格式缩进交给 lint 或校验脚本。最后用一句话给出总体结论；没发现问题就写 `No findings.`。

## 审代码改动

如果对比基准是远端分支，主 Agent 先 `git fetch` 对应远端分支（不执行 pull、merge 或 rebase），用拉下来的最新远端基准做对比；fetch 失败就停下说明，等用户同意后再用本地旧基准。审分支文档差异时同理。

没指定范围时，取 `git merge-base HEAD <默认分支>`，看 `git diff <merge-base>` 加未跟踪文件，并顺手查看相关调用方与测试。重点看三件事：

- **正确性**：逻辑 bug、真实并发锁与幂等漏洞、存量数据兼容、错误处理、安全与性能。
- **是否符合技术方案或需求**：对照 `design.md`（或原始需求）逐项核对，抓出漏做、做偏、擅自多做，或漏补方案验收表对应测试的部分。
- **代码质量**：是否遵守 `AGENTS.md` 等仓库规范；重复代码、命名含糊、职责混杂或过度设计按工程经验判断，并标明是经验判断（归入“建议”）。

## 审文档

审技术方案、发布文档或测试报告（含专门检查文风可读性）时分两步走，先验好不好懂，再验代码事实准不准：

1. **第一步（无背景同事盲读）**：主 Agent 先列 5 到 10 个评审人最关心的问题，**只把待审文档和画板预览图传给子 Agent**（这步不让它读仓库源码）。让子 Agent 当自己是第一次参加评审会的同组研发：先只凭文档回答问题，再逐节挑出所有让人发懵的地方。
2. **第二步（对照真实源码核查事实）**：盲读完后，把真实源码（建表 `.sql`、`.proto`、核心代码）传给同一个子 Agent，核对文档里的现状假设、表名、列名、接口、错误码与恢复命令是否和真实源码一致。

审文档遵守以下分级标尺：

- **别逼技术方案塞代码内部细节**：省略源码行号、存量私有函数签名、锁 key 拼接或内部并发占位细节是正常的，绝不判为遗漏；但若漏掉了影响外部行为的核心契约、状态规则或关键异常边界，按“必须修”报告。
- **以下让人看不懂或事实失真的问题直接判“必须修”**：
  1. 擅自把团队日常固定直呼英文的服务简称、操作词（如 `Approve`、`Reject`、`Dry Run`）机翻成中文或混用多套译名；拿空泛口号当目标；造缺宾语歧义词（如“系统草稿”）、裸写“副作用”、混入未改动的边缘底层名词，或用顿号堆报菜名标题。
  2. 双状态机混塞一张巨表、缺“状态 × 操作权限矩阵表”、加新状态却没列“存量接口校验条件切换表”、跨服务多步调用堆大段文字不画时序图、3 项以上映射用分号挤成一段、验证表把动作与检查点糊成一列、单元格塞成小作文、满段乱套行内代码灰框、新增文件缺真实样例，或把次要兼容点塞进主干标题满篇刷屏。
  3. 状态图漏画合法转移箭头、框内塞未解释的黑话、判定图让报错节点指回正常主干、画板文字压框，或表名/列名/接口/错误码/恢复命令与真实源码冲突。
- 画板局部像素间距、高亮词多少、双栏卡还是紧凑表这类个人喜好最多归入“建议”。
- **审 Skill 或 Rule 文件**：对照 `AGENTS.md` 检查是否足够通用脱敏、职责清晰无跨文件重复、同阶段约束有没有过载，以及**规则文件自己是不是在说直白自然的工程师人话**。

## 审计划与设计

审计划、技术方案和 Skill / Rule 设计时，额外想清楚四点（普通代码审查不用套）：**目标**是否对齐原始需求、**措施**在什么前提下仍可能失效、有没有**成本**更低的简单做法、现有材料和验证算不算有效**证据**（区分事实、推断与未知）。按实际风险提问题，不加打分表。

## 修复后

审查结论只对当前版本有效。主 Agent 拿到审查报告后按下面四步收尾：

- **先核实再改**：对照源码核实报告里的问题真不真（如果审查者逼技术方案塞源码行号或私有锁细节，直接驳回并向用户说明），不盲从。
- **只修“必须修”**：“建议”项列给用户挑，未经用户点名同意，不顺手改代码或扩改文档。
- **同步文档**：修代码或修方案涉及事实纠偏或规则调整时，按全局规范把本地 `design.md` 与已授权飞书文档（局部更新保留原画板）一块改齐，需要拍板时先问用户。
- **最多复查一次**：修完确认成立的“必须修”后，最多再派一个新子 Agent 复查一次。复查时只传代码基准、更新后的方案路径、上一轮要修的原条目和改动文件范围，别附带“我已修复某某问题”的自我辩解，只查改对没有以及有没有带出新问题；还有问题就如实汇报。
