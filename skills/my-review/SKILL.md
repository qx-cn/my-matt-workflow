# 审查

审查者是新上下文的子 Agent，只读不改。不假定子 Agent 继承父会话，资料按下文阶段提供，缺少依据时说明限制，不自行补全事实；派不出子 Agent 时说明原因，改为自审并标明是自审。主 Agent 向子 Agent 传递资料遵守以下隔离约束：

- **优先传客观路径**：有本地可读路径的材料（仓库根路径、分叉基准 SHA、变更与未跟踪文件清单、已有的 `spec.md` / `decided.md` / `refs/`、适用规范文件）只传路径，由子 Agent 自行运行 `git diff` 与 `Read`。
- **无路径材料原样粘贴**：对话内的原始需求、宿主内存中的个人规则、预抓取的远端文档，或受限子 Agent 无法直读的修改前片段，原样粘贴全文，不缩写改写；审含画板的文档时一并提供画板导出预览图或 JSON DSL。
- **禁传主观导览与自证记录**：初审不传既往审查记录（单次复查仅按“修复后”传入上一轮确认成立的“必须修”原条目），且不传主 Agent 归纳的改动导览、替偏离做辩护的合理性说明或自证式测试总结（用户显式指定待审的原始日志除外）。

代码与文档共用以下分级：

- 必须修：会导致错误行为、不符合 Spec 或需求、有安全问题，或违反仓库明文规则（引用原文）。写清触发场景。
- 建议：其余值得作者知道的问题，包括可维护性、缺失的测试、无法从代码证实的风险或疑问（写明要核实什么）、局部排版微调，以及改动路径上原本就有的问题（标"既有"）。

每条写级别、文件和行号（无行号时用章节或原文定位）、问题和理由。工具能判定的纯格式问题交给格式化和 lint；语义歧义及约束遗漏仍需报告。最后用一句话给出总体判断；没有发现就写 `No findings.`，不代表效果已经验证。

## 审代码改动

若对比基准对应远端分支，主 Agent 在生成差异、派出审查者前先 fetch 对应分支，后续比较使用本次取得的版本。fetch 失败时说明原因并暂停，用户明确接受旧基准后才能继续。用户明确指定固定提交或纯本地基准时无需 fetch。

按分支差异审文档时同样适用。此步骤不执行 pull、merge 或 rebase。

范围：用户指定的基准；没指定时，用 `git merge-base HEAD <默认分支>` 的结果，看 `git diff <merge-base>` 加上 `git status` 中的未跟踪文件，并按需阅读相关调用方和测试。

从三个方面看：

- 正确性：逻辑错误、边界情况、并发、存量数据、错误处理、安全、性能。
- 是否符合 Spec 或需求：逐条对照，指出遗漏、偏离和多做的部分。
- 代码质量：是否遵守 AGENTS.md 等仓库规范；重复实现、命名不清、职责混杂、过度设计等问题按经验判断，并标明是判断。

## 审文档

用于 Spec、技术方案、发布文档或 Skill / Rule 文件：

- **业务与设计文档**：
  - 先列出读者最可能问的 5 到 10 个问题；第一阶段仅向审查子 Agent 提供待审文稿（限定其在盲答阶段不读取同仓其余文件或 Git 历史）让其仅凭文稿回答，待回答完后再向同一审查者提供事实依据，核对答案、现状与已确认决定。
  - 改写稿同时对照相关前稿，检查歧义、矛盾和未说明的假设，以及对象、条件、动作和关联约束是否遗漏或改变；已确认约束遗漏按“必须修”处理。
  - 审技术方案时区分受众：只核对核心业务问题、方案与兼容逻辑、备选取舍及风险边界，不要求贴函数内部源码行号或枚举 `spec.md` 中的全量同名字段清单。
- **可读性、视觉层级与表达**：对照全局写作规范与对应 Skill 要求核查以下要点。阻断理解、跳步失真、受众越界或画板重叠归入“必须修”，不影响准确理解的局部段落长短或载体微调归入“建议”；已有术语、明确对应的中文说明与两列条件动作表不机械判错，指出原表达、含义问题及修改依据，资料不足时不猜：
  - **主次与总览**：Spec 与技术方案中核心业务痛点是否排在第一位，未把调研期放弃的备选方案缺陷混作现网痛点；技术方案文首是否有简明的`方案总览`。
  - **动机、归属与判据**：引入分支、过滤、转换或操作步骤前是否交代了业务动机、上下游或表字段归属及可查验的状态判据（如 `表名.字段 = 枚举值`，无归属不明的裸状态词），是否消除了未解释的代码内部黑话、编造的未实现函数名与机翻造词。
  - **回滚与异常恢复**：改动涉及数据落库、状态或游标推进、对外契约或不可逆变更时，是否分开说明了“服务版本回滚”与“异常数据/状态恢复步骤”，并写明了经代码核实的状态判据、工具限制与恢复原因。
  - **标题、载体与链接**：章节标题是否为简短专业的名词短语（操作步骤或流程章节可用简短动宾短语）；多维枚举映射或成对对比是否选用了合适的独立表格或双栏载体；引用外部参考资料时是否带有可点击的真实 URL（不写无链接的本地文件名）。
  - **画板与图文配合（含画板文档适用）**：结合预览图或 JSON DSL 检查画板是否无文字折行重叠、连线与锚点方向是否合理（无斜穿框体）、无空白占位画板残留，且图下正文未重复念图。
- **Skill 或 Rule 文件**：对照仓库准则与上下文工程原则，检查是否处在恰当的抽象高度（未把单次业务特例硬编码为通用规则、未复述默认常识）、是否集中定义且无跨文件重复抄写、改写是否保留了必要的执行条件与边界、常驻规则是否混入按需长流程，以及规则文件自身的句法与排版是否合规（未写成超长复合单段而向产出物传染不良文风）。

## 审计划与设计

计划、技术方案及 Skill / Rule 设计还需核对以下四项，普通代码审查不额外套用：

- **目标**：从原始需求和已确认约束确定可观察的成功条件，不自行补业务目标。
- **措施**：核验关键假设、生效条件及照做仍会失败的合理情形。
- **成本**：评估执行和维护成本，考虑满足相同约束的更简单做法，尊重已确认取舍。
- **证据**：判断材料和验证能否检验效果，区分事实、推断和未知；官方出处不能替代本地效果证据。

按风险判断，不要求每项列反例或替代方案，也不增加评分表或额外报告。

## 修复后

结论只对应所审版本；之后业务内容或代码变化时，不沿用旧版结论，是否再次发起全篇审查由用户按需显式调用决定。主 Agent 收到审查报告后按以下闭环处理：

- **先核实再动手**：先对照源码与上下文核实报告中的问题是否真实成立；发现审查误判时向用户说明依据，不盲从修改。
- **区分处理边界**：只修复确认成立的“必须修”；“建议”项汇报给用户决策，未经用户点选确认不顺手改代码，也不进入复查循环。
- **同步关联文档**：修“必须修”涉及底层代码事实偏差或方案取舍变化时，按全局实施规范同步已有的 `spec.md`（及 `decided.md`）或先请示用户。
- **单次无辩护复查**：修完确认成立的“必须修”后最多再派一次新上下文复查，按首段客观载荷传入基准与同步后的规格/规范路径、上一轮确认成立的“必须修”原条目及修复涉及的文件范围（不附带自我辩护式的修复声明），只核查修复部分及关联影响；仍有问题就如实报告。
