# 审查

审查者是新上下文的子 Agent，只读不改。给它审查对象、Spec 或原始需求，以及适用的 AGENTS.md，不给实施总结。派不出子 Agent 时说明原因，改为自审，并标明是自审。

## 审代码改动

范围：用户指定的基准；没指定时，用 `git merge-base HEAD <默认分支>` 的结果，看 `git diff <merge-base>` 加上 `git status` 中的未跟踪文件，并按需阅读相关调用方和测试。

从三个方面看：
- 正确性：逻辑错误、边界情况、并发、存量数据、错误处理、安全、性能。
- 是否符合 Spec 或需求：逐条对照，指出遗漏、偏离和多做的部分。
- 代码质量：是否遵守 AGENTS.md 等仓库规范；重复实现、命名不清、职责混杂、过度设计等问题按经验判断，并标明是判断。

每条发现分两级：
- 必须修：会导致错误行为、不符合 Spec 或需求、有安全问题，或违反仓库明文规则（引用原文）。写清触发场景。
- 建议：其余值得作者知道的问题，包括可维护性、缺失的测试、无法从代码证实的风险或疑问（写明要核实什么）、改动路径上原本就有的问题（标"既有"）。

每条写级别、文件和行号、问题和理由。格式问题交给格式化和 lint 工具，不报。最后用一句话给出总体判断。没有发现就写 `No findings.`。

## 审文档

用于 Spec、技术方案、发布文档或 Skill / Rule 文件：
- **业务与设计文档**：先列出读者最可能问的 5 到 10 个问题，交给只拿到文档的子 Agent 回答，找出答不上或答错的地方；再检查歧义、前后矛盾、未说明的假设、现状描述是否与代码一致、是否与 `decided.md` 已确认决定一致，以及是否存在生造词、编造的未实现函数名、跨章节重复叙述、满屏行内代码（`xxx`）或未拆点的晦涩长句。
- **Skill 或 Rule 文件**：对照仓库 `AGENTS.md` 检查是否复述模型默认常识、是否与 `rules/global.md` 重复、常驻规则是否混入按需长流程、文档自身格式是否违反规则，以及 `description` 是否用第三人称写清"做什么"和"何时触发"。

## 修复后

主 Agent 修完"必须修"的问题后，最多再派一次复查，只看修复部分；仍有问题就如实报告。"建议"列给用户决定是否处理，不进入修复循环。
