# 审查

审查者是新上下文的子 Agent，只读不改。按范围准备当前待审内容、相关修改前片段、原始需求或 Spec、已确认决定，以及适用规范正文或可读位置；不假定子 Agent 继承父会话，不给实施总结。资料按下文阶段提供，缺少依据时说明限制，不自行补全事实。派不出子 Agent 时说明原因，改为自审，并标明是自审。

代码与文档共用以下分级：

- 必须修：会导致错误行为、不符合 Spec 或需求、有安全问题，或违反仓库明文规则（引用原文）。写清触发场景。
- 建议：其余值得作者知道的问题，包括可维护性、缺失的测试、无法从代码证实的风险或疑问（写明要核实什么）、改动路径上原本就有的问题（标"既有"）。

每条写级别、文件和行号（无行号时用章节或原文定位）、问题和理由。工具能判定的纯格式问题交给格式化和 lint；语义歧义及约束遗漏仍需报告。最后用一句话给出总体判断；没有发现就写 `No findings.`，不代表效果已经验证。

## 审代码改动

范围：用户指定的基准；没指定时，用 `git merge-base HEAD <默认分支>` 的结果，看 `git diff <merge-base>` 加上 `git status` 中的未跟踪文件，并按需阅读相关调用方和测试。

从三个方面看：

- 正确性：逻辑错误、边界情况、并发、存量数据、错误处理、安全、性能。
- 是否符合 Spec 或需求：逐条对照，指出遗漏、偏离和多做的部分。
- 代码质量：是否遵守 AGENTS.md 等仓库规范；重复实现、命名不清、职责混杂、过度设计等问题按经验判断，并标明是判断。

## 审文档

用于 Spec、技术方案、发布文档或 Skill / Rule 文件：

- **业务与设计文档**：先列出读者最可能问的 5 到 10 个问题，让审查子 Agent 仅凭文稿回答，再向同一审查者提供事实依据，核对答案、现状与已确认决定。改写稿同时对照相关前稿，检查歧义、矛盾和未说明的假设，以及对象、条件、动作和关联约束是否遗漏或改变；已确认约束遗漏按“必须修”处理。
- **表达与名称**：按适用写作规范检查概括名称、编造的未实现函数名、重复叙述、行内代码和晦涩长句。来源里有的词也可能含混，已有术语或明确对应的中文说明与字段名不机械判错；指出原表达、含义问题及有依据的修改建议，资料不足时不猜。条件与动作表不因只有两列自动判错。
- **Skill 或 Rule 文件**：对照适用仓库规范，检查是否复述默认常识、是否存在多份规范定义或冲突、任务动作是否必要、常驻规则是否混入按需长流程、文档自身格式及 description 是否合规。

## 审计划与设计

计划、技术方案及 Skill / Rule 设计还需核对以下四项，普通代码审查不额外套用：

- **目标**：从原始需求和已确认约束确定可观察的成功条件，不自行补业务目标。
- **措施**：核验关键假设、生效条件及照做仍会失败的合理情形。
- **成本**：评估执行和维护成本，考虑满足相同约束的更简单做法，尊重已确认取舍。
- **证据**：判断材料和验证能否检验效果，区分事实、推断和未知；官方出处不能替代本地效果证据。

按风险判断，不要求每项列反例或替代方案，也不增加评分表或额外报告。

## 修复后

结论只对应所审版本；之后业务内容变化时，按既有风险触发条件核对改动及关联影响，不沿用旧稿结论，也不因每次微调增加全篇审查。

主 Agent 修完"必须修"的问题后，最多再派一次复查，只看修复部分及关联影响；仍有问题就如实报告。"建议"列给用户决定是否处理，不进入修复循环。
