# 审查

派一个新上下文的子 Agent 做独立只读审查。宿主支持只读模式或限制只读工具时优先启用只读模式，不修改任何文件或远端资源；派不出子 Agent 时说明原因，改为自审并标明是自审。

子 Agent 不会自动继承父会话内容，传资料时遵守三条边界：

- **只传原始材料，不传主 Agent 的总结或辩解**：本地可读文件（仓库路径、基准 commit、改动与未跟踪文件列表、已有的 `design.md` 或 `refs/`）只传路径，让子 Agent 自己跑 `git diff` 和 `Read`；画板预览图传本地图片路径供子 Agent 查看；没有本地路径的内容（聊天里的原始需求、抓下来的飞书文档文本）原样贴全文。初审不传旧审查记录，任何时候都不传主 Agent 自己总结的改动导览或辩解说明。
- **按产物传入原始规范**。审代码时传业务仓的 `AGENTS.md` 和对应的 `design.md`。审文档时，在盲读结束后，从本 Skill 文件的实际目录解析 `../../rules/global.md` 和 `../my-tech-design/SKILL.md`，将绝对路径交给审查者。涉及模板构件时再附 `../my-tech-design/TEMPLATES.md` 的绝对路径。飞书版式结合脚本输出和画板预览核查。
- **核实不到直接说明**：缺少依据的地方写明缺什么材料，不自己脑补事实。

范围较大时，按要回答的问题分组取证。若输出被截断，保留结果路径，按关键词或行号补读缺失段落。每核完一组，用简短消息交回结论、证据位置和剩余问题。

若重复读取同一范围仍无新证据，改用定向查询。若仍无法判断或预算将尽，先交回已核实的结论并说明缺口，续查时从缺口开始。只有完成约定范围后才可报告 `No findings.`。

代码和文档统一分两级报告：

- **必须修**：会导致运行错误、漏掉或违背核心需求与对外契约、存在安全隐患、严重妨碍读者理解（如机翻英文原词、满篇黑话、缺关键图表样例、大段文字墙、画板压框漏边），或违反仓库明文规则（贴出规则原话）。写清出错场景或卡住读者的具体位置。
- **建议**：其余值得作者留意的问题，如可维护性、补充测试、需要进一步核实的疑问（写明核实什么）、细微措辞或审美偏好，以及改动文件里原本就有的老问题（标“既有”）。

每条写明级别、文件与行号（无行号时写章节和原句）、问题和原因。纯格式缩进交给 lint 或校验脚本。最后用一句话给出总体结论。

## 审代码改动

如果对比基准是远端分支，主 Agent 先 `git fetch` 对应远端分支（不执行 pull、merge 或 rebase），用拉下来的最新远端基准做对比；fetch 失败就停下说明，等用户同意后再用本地旧基准。审分支文档差异时同理。

没指定范围时，取 `git merge-base HEAD <默认分支>`，看 `git diff <merge-base>` 加未跟踪文件，并顺手查看相关调用方与测试。重点看三件事：

- **正确性**：逻辑 bug、真实并发锁与幂等漏洞、存量数据兼容、错误处理、安全与性能。
- **是否符合技术方案或需求**：对照 `design.md`（或原始需求）逐项核对，抓出漏做、做偏、擅自多做，或漏补方案验收表对应测试的部分。
- **代码质量**：是否遵守 `AGENTS.md` 等仓库规范；纯缩进格式与个人代码风格喜好跳过不报，重复代码、命名含糊、职责混杂或过度设计按工程经验判断，标明是经验判断并归入“建议”。

## 审文档

审技术方案、发布文档或测试报告（含专门检查文风可读性）时分两步串行推进，先验好不好懂，再验代码事实准不准：

1. **第一步（无背景同事盲读）**：主 Agent 先列 5 到 10 个评审人最关心的问题，只传**待审文档、画板预览图路径、评审问题清单与本文件的《审文档》分级标尺**（盲读阶段禁止调用搜索或读文件工具查看业务源码）。让子 Agent 当自己是第一次参加评审会的同组研发：先只凭文档回答问题，再逐节挑出让人看不懂的地方。
2. **第二步（对照真实源码核查事实）**：盲读完成后，优先 `resume` 同一个子 Agent（宿主不支持 `resume` 时再派第 2 个只读子 Agent），传入真实源码路径（建表 `.sql`、`.proto`、核心代码）和前文列出的文档规范绝对路径，核对文档里的现状假设、表名、列名、接口、错误码与恢复命令是否和真实源码一致。

审文档遵守以下分级标尺（发布文档与测试报告按各自文体核查对应项）：

- **不逼技术方案塞代码内部细节**：省略源码行号、存量私有函数签名、锁 key 拼接或内部并发占位细节是正常的，不判为遗漏；但若漏掉了影响外部行为的核心契约、状态规则或关键异常边界，按“必须修”报告。
- **以下让人看不懂或事实失真的问题判为“必须修”**：
  1. **语言表达**：把团队日常直呼英文的服务简称或操作词（如 Approve、Reject、Dry Run）机翻成中文，照抄源码注释里的生硬译词，写出砍掉动作对象的半截话、把动词压到句尾的名词堆叠词组或四字公文口号，裸写“副作用”，或用顿号堆出报菜名标题。
  2. **背景与前后对比**：把新方案实施或测试期难点塞进《背景与问题》冒充现网已有故障；接口切换或架构重构漏做改造前后对比；承载路由、字典或开关的业务规则配置只贴两行示例而未列全量业务映射表。
  3. **结构与表格**。结合文体指出读者具体会漏看哪条规则或判断条件。
     - 涉及状态机时，在状态定义表里逐项核对枚举，再对照“状态 × 操作权限矩阵表”检查允许的操作。新增状态时，还要核对“存量接口校验切换表”。
     - 检查验证表是否把无关场景合在一行，窄格里的长前提是否需要移到表下。
     - 需评审的技术方案应写清方案取舍。次要兼容点反复出现在主干标题，或飞书文档后半篇难以辨认重点时，指出受影响的章节。
  4. **配图与画板**：配图未对准核心认知卡点（如该画阶段前后对比或改造边界却只画干瘪单链）、画成明显高瘦失衡的单列长条、状态图漏画合法转移箭头、节点误写嵌套 `style` 导致边框底色丢失，或画板文字溢出压框。
  5. **与源码事实一致**：文档里的现状假设、表名、列名、接口、错误码、样例格式或恢复命令与真实源码冲突。
- 画板局部像素间距、高亮词多少、双栏卡还是紧凑表这类个人喜好最多归入“建议”。

## 审规则与 Skill

审仓库规则、模板或 Skill 文件时，对照 `AGENTS.md` 检查是否保持精简泛化与脱敏、单文档与四阶段职责边界是否清晰无跨文件重复、同阶段约束有没有过载，以及规则文件自身是不是在说直白自然的工程师人话。

---

## 审计划与设计

审计划、技术方案和 Skill / Rule 设计时，额外想清楚四点（普通代码审查不用套）：**目标**是否对齐原始需求、**措施**在什么前提下仍可能失效、有没有**成本**更低的简单做法、现有材料和验证算不算有效**证据**（区分事实、推断与未知）。按实际风险提问题，不加打分表。

## 修复后

审查结论只对当前版本有效。主 Agent 拿到审查报告后按下面四步收尾：

- **先核实再改**：对照源码核实报告里的问题真不真；如果审查者逼技术方案塞源码行号或私有锁细节，直接驳回并向用户说明，不盲从。
- **只修“必须修”**：“建议”项列给用户挑，未经用户点名同意，不顺手改代码或扩改文档。
- **同步文档**：修代码或修方案涉及事实纠偏或规则调整时，按全局规范把本地 `design.md` 与已授权飞书文档（局部更新保留原画板）一块改齐，需要拍板时先问用户。
- **最多复查一次**：修完确认成立的“必须修”后，最多再派一个新子 Agent 复查一次。复查时只传代码基准、更新后的方案路径、上一轮要修的原条目和改动文件范围，不附带“我已修复某某问题”的自我辩解，只查改对没有以及有没有带出新问题；还有问题就如实汇报。
