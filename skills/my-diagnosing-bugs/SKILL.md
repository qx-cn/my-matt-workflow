# My Diagnosing Bugs

这是一套用于处理棘手 Bug 的纪律。除非明确说明理由，否则不得跳过阶段。

探索代码库时，读取已有的项目领域术语与 ADR，建立所涉模块的清晰心智模型；优先使用仓库已记录的术语和约定，不假设存在固定名称或固定位置的 `CONTEXT.md`。

读取本地术语表或 ADR 工作产物时，遵循 [工作产物访问](references/shared/adapters/artifact-access.md)。

## 阶段 1 —— 建立反馈循环

**这就是本 Skill 的核心。** 如果能得到针对这个 Bug 的**紧凑**通过/失败信号——它会因这个 Bug 变红——就能找到根因；二分、假设检验和埋点都只是消耗这个信号。若没有它，再多盯着代码也无济于事。

在这里投入不成比例的精力：积极、创造性地尝试，不轻易放弃。

### 构造方式——大致按以下顺序尝试

1. 在能够抵达 Bug 的合适 seam 写失败测试：单元、集成或端到端测试。
2. 对运行中的开发服务器执行 `curl` / HTTP 脚本。
3. 用带 fixture 输入的 CLI 调用，对 stdout 与已知正确快照做 diff。
4. 无头浏览器脚本（Playwright / Puppeteer）：驱动 UI，并断言 DOM、控制台或网络。
5. 回放已捕获的 trace：把真实网络请求、payload 或事件日志保存到磁盘，在隔离环境中重放代码路径。
6. 一次性 harness：启动系统的最小子集（一个服务、mock 依赖），以单次函数调用走到 Bug 路径。
7. 属性 / fuzz 循环：若 Bug 是“有时输出错误”，运行 1,000 个随机输入并寻找失败模式。
8. 二分 harness：若 Bug 出现在两个已知状态（Commit、数据集或版本）之间，自动化“启动状态 X、检查、重复”，以便执行 `git bisect run`。
9. 差分循环：让同一输入经过旧版与新版（或两组配置），再比较输出。
10. 人在回路的 bash 脚本：最后手段。若必须由人点击，使用 [scripts/hitl-loop.template.sh](scripts/hitl-loop.template.sh) 驱动操作，使循环仍保持结构化；捕获的输出会反馈给 Agent。

建立正确的反馈循环，Bug 就已解决了 90%。

### 收紧循环

把循环当作产品。一旦已经有一个循环，就继续**收紧**它：

- 能否更快？缓存初始化、跳过无关启动、收窄测试范围。
- 能否让信号更尖锐？断言具体症状，而非“没有崩溃”。
- 能否更确定？固定时间、设置随机种子、隔离文件系统、冻结网络。

30 秒且不稳定的循环几乎不比没有好；2 秒且确定的循环才紧凑——是调试的超能力。

### 非确定性 Bug

目标不是得到完美复现，而是提高**复现率**。将触发操作循环 100 次、并行执行、增加压力、缩小时间窗口、注入 sleep。50% 概率的 flaky Bug 可以调试；1% 不行——持续提高复现率，直到可以据此调试。

### 确实无法建立循环时

明确报告无法建立循环以及已尝试的方法。请求所缺的条件：

- 能复现问题的环境访问权限；
- 捕获的工件，例如 HAR 文件、日志转储、core dump，或带时间戳的录屏；
- 或按项目策略获准添加临时生产埋点。

随后按 `.agent/matt-workflow.md` 的已解析 `decision_policy` 处理：`ask` 或 `halt` 时停止并等待确认；`autonomous` 时，只有已批准计划明确允许才进入“有限证据模式”。有限证据模式中每项结论都必须标注置信度，不得声称已定位根因。没有紧凑、可变红的命令，就不得进入常规假设阶段。

### 完成条件——能变红的紧凑循环

阶段 1 只有在循环**紧凑**且**能变红**时才完成：必须能说出**一条已经至少运行过一次的命令**——脚本路径、测试调用或 `curl`——并附上调用及输出；该命令还必须满足：

- [ ] **能变红**：它走真实的 Bug 路径，并断言用户描述的**准确症状**，因此能因这个 Bug 变红、修复后变绿。不是“运行时未报错”，而是必须能捕获这个具体 Bug。
- [ ] **确定**：每次运行得到相同判定；flaky Bug 则应按上文固定并提升复现率。
- [ ] **快速**：以秒计，而不是分钟。
- [ ] **可由 Agent 运行**：可无人值守地运行；人只能通过 [scripts/hitl-loop.template.sh](scripts/hitl-loop.template.sh) 参与。

若发现自己在这条命令存在前就开始阅读代码、构建理论，立即停止——直接跳到假设正是本 Skill 要防止的错误。没有能变红的命令，就不能进入阶段 2。

## 阶段 2 —— 复现并最小化

运行循环，确认它变红并出现 Bug。

确认：

- [ ] 循环产生的是**用户**描述的失败模式，而不是恰好相邻的另一个失败。错 Bug 等于错修复。
- [ ] 失败可在多次运行中复现；非确定性 Bug 则须达到足以据此调试的高复现率。
- [ ] 已捕获准确症状（错误信息、错误输出或耗时），以便后续阶段验证修复确实解决问题。

### 最小化

一旦变红，把复现收缩为仍然变红的**最小场景**。逐个删减输入、调用方、配置、数据和步骤；每次删减后都重新运行循环，只保留承重元素。

理由：最小复现会缩小阶段 3 的假设空间（待怀疑的可变因素更少），并成为阶段 5 清晰的回归测试。

当每一个剩余元素都不可缺少——删除任何一个都会让循环变绿——才算完成。复现和最小化都完成前不得继续。

## 阶段 3 —— 提出假设

测试任何一个假设前，先生成 3–5 个有排序的假设。只想出一个假设会让人锚定第一个看似合理的答案。

每个假设都必须**可证伪**，并写出其预测：

> 格式：若 `<X>` 是原因，则“改变 Y 会让 Bug 消失” / “改变 Z 会让 Bug 更严重”。

若不能说明预测，该假设只是感觉；丢弃或收紧它。

在测试前展示排序后的列表。`decision_policy: ask` 或 `halt` 时等待用户的重新排序或补充；`autonomous` 时可按已批准计划继续，并记录排序依据与证据。用户通常拥有能立刻重排的领域知识，例如“我们刚部署了第 3 项”，或知道哪些假设已被排除。

## 阶段 4 —— 埋点

每个探针都必须对应阶段 3 的特定预测，一次只改变一个变量。

工具优先级：

1. 环境支持时优先调试器 / REPL 检查；一个断点胜过十条日志。
2. 在能够区分假设的边界添加针对性日志。
3. 不得“什么都打日志，再 grep”。

每条调试日志都使用唯一前缀，例如 `[DEBUG-a4f2]`。收尾时一次 grep 即可清理；无标签日志会残留，有标签日志应消失。

**性能分支。** 性能回退通常不适合靠日志。应先建立基线测量（计时 harness、`performance.now()`、profiler 或查询计划），再二分；先测量，后修复。

## 阶段 5 —— 修复与回归测试

在修复前写回归测试——但前提是存在**正确的 seam**。

正确 seam 是测试能以调用方实际遇到的方式覆盖**真实 Bug 模式**的地方。若唯一 seam 太浅（多调用方才能触发的 Bug 却只测试单一调用方；需要整条调用链的 Bug 却写单元测试），该回归测试会带来虚假信心。

如果不存在正确 seam，这本身就是结论：代码库架构阻碍了锁定 Bug。记录它，并在下一阶段标注。

若存在正确 seam：

1. 将最小复现转成该 seam 上的失败测试。
2. 观察它失败。
3. 应用最小修复。
4. 观察它通过。
5. 用阶段 1 的反馈循环重新运行原始、未最小化的场景。

## 阶段 6 —— 清理与复盘

宣布完成前必须做到：

- [ ] 原始复现不再出现：重新运行阶段 1 的循环。
- [ ] 回归测试通过；若没有 seam，则已记录其原因。
- [ ] 已移除所有 `[DEBUG-...]` 埋点：grep 该前缀。
- [ ] 一次性原型已删除，或移至标记清晰的调试位置。
- [ ] 已在按项目策略允许创建的 Commit / PR 信息中说明最终正确的假设，使下一位调试者能够学习。

然后追问：什么能预防这个 Bug？若答案涉及架构变化（没有好的测试 seam、调用方纠缠、隐藏耦合），在修复完成后将具体发现交给 `my-improve-codebase-architecture`；此时掌握的信息比修复前更多。
