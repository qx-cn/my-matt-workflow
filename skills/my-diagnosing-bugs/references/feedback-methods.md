# 选择反馈与取证方法

根据能区分哪些原因、运行成本与环境权限选择，不是必须依次穷举：

- 稳定 seam 的单元/集成/端到端测试；开发服务器 HTTP 探针；带 fixture 的 CLI 与已知正确输出比较；无头浏览器的 DOM/控制台/网络断言。
- 隔离回放真实 trace、请求或事件；一次性 harness 启动必要子集；属性/fuzz寻找边界输入；已知坏好版本之间二分；同输入旧新版本/配置的差分。
- 必须由人操作时使用结构化操作及结果记录，可参考 [HITL脚本](../scripts/hitl-loop.template.sh)；模板不是人参与的唯一合法形式。不可自动化部分标出所需输入和观察者。

收紧已有循环，缓存初始化、收窄启动/测试范围、固定时间和种子、隔离网络/存储，但不损失真实故障机制。慢恢复可复用 checkpoint；并发/间歇故障记录次数、时序、条件、失败比例及不确定性，没有通用秒数或最低概率门槛。不能为了确定性消除待调查的竞争条件。

探针应对应一个可证伪预测，尽量一次改变一个变量。支持时用调试器/REPL，或只在区分假设的边界增加日志；临时日志使用可清理的独特标记。性能问题先建立可比测量（计时、profiler、查询计划），再定位和修复。生产埋点或新权限按共享授权处理。
