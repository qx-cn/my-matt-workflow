# UI 原型

在单一路由生成**数个截然不同的 UI 变体**，用悬浮底栏切换。用户在浏览器切换变体、选择一个（或从每个变体吸收片段），然后丢弃其余部分。

若问题是逻辑 / 状态，而非外观，这是错误分支；改用 [LOGIC.md](LOGIC.md)。

## 适用情形

- “这个页面应该长什么样？”
- “在决定前，我想看这个仪表盘的几种方案。”
- “给设置页面尝试另一种布局。”
- 任何原本会让用户在脑海中对三个模糊 mockup 纠结一天的场景。

## 两种子形态——强烈优先 A

当 UI 原型**紧贴应用其他部分**时，判断更容易：真实页头、真实侧栏、真实数据、真实密度。孤立的一次性路由像真空，任何变体单看都不错。只要存在可信的现有页面承载变体，就默认使用子形态 A；只有原型确实没有附近归宿时才使用 B。

### 子形态 A——调整现有页面（首选）

路由已经存在。变体渲染在**同一路由**，由 `?variant=` URL 查询参数控制。既有数据获取、参数与认证都保留，只替换渲染部分。这是默认选择，除非有明确理由。

若原型所做的内容尚无页面、但自然应嵌在某一页面中（仪表盘新分区、设置页新卡片、既有流程中新步骤），仍属于 A；将变体挂在宿主页面内。

### 子形态 B——新页面（最后手段）

仅在被试验的内容确实没有可放入的现有页面时使用，例如完全新的顶层界面，或无法合理嵌入的流程。

创建遵循项目既有路由约定的**一次性路由**，不另造顶层结构。名称必须明显是原型（如路径或文件名包含 `prototype`），并使用同样的 `?variant=` 模式。写入真实项目路由须遵守项目策略。

采用 B 前先检查：真的没有可嵌入的现有页面吗？空路由会掩盖在真实页面中才暴露的设计问题。

两种形态都使用相同的悬浮底栏。

## 过程

### 1. 写明问题并选择 N

默认 **3 个变体**。超过 5 个就不再是根本不同，而变成噪音；上限是 5。

将计划用一行写在原型位置或文件顶部注释：

> “在现有 `/settings` 路由上，制作三个可通过 `?variant=` 切换的设置页变体。”

无论用户此刻是否在线，都应这样写。

### 2. 生成根本不同的变体

起草每个变体，并满足：

- 页面目的及可访问的数据；
- 项目组件库 / 样式系统（TailwindCSS、shadcn、MUI、纯 CSS 等）；
- 清晰导出的组件名，如 `VariantA`、`VariantB`、`VariantC`。

变体必须在**结构上不同**：不同布局、不同信息层级、不同主要可供性，而非仅颜色不同。三个略微调整的卡片网格不是 UI 原型，只是壁纸。若两个草稿太像，用明确的“不得使用卡片网格”指引重做其中一个。

### 3. 将它们接在一起

在路由上创建单一切换器组件：

```tsx
// 伪代码：按项目框架调整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形态 A（现有页面）中，将所有既有数据获取保留在切换器上方，只改变各变体的渲染子树。

子形态 B（新页面）中，一次性路由 `/prototype/<name>` 挂载同一切换器。

### 4. 构建悬浮切换器

在屏幕底部居中放置一个小型固定栏，包含三部分：

- **左箭头**：循环到上一个变体。
- **变体标签**：显示当前变体键；若变体导出名称也显示名称，例如 `B — 侧栏布局`。
- **右箭头**：循环到下一个变体。

行为：

- 点击箭头更新 URL 查询参数（使用框架路由器，例如 Next 的 `router.replace`、React Router 的 `navigate`），确保变体可分享且刷新后稳定。
- 键盘 `←`、`→` 也循环；焦点在 `<input>`、`<textarea>` 或 `[contenteditable]` 时不得拦截方向键。
- 视觉上应与页面明确区分（如高对比胶囊、轻微阴影），让人知道它不属于被评估设计。
- 在生产构建中隐藏：以 `process.env.NODE_ENV !== 'production'` 或等效检查保护，防止误合入原型时将底栏发布给用户。

将切换器放在单一共享组件中，使两种子形态均可复用；位置遵循项目共享 UI 约定。

### 5. 交给用户

提供 URL 和 `?variant=` 键。用户可在方便时切换。最有价值的反馈通常是“我想要 B 的页头加 C 的侧栏”——那才是他们真正要的设计。

### 6. 捕获答案并清理

某变体胜出后，记录胜出者及原因，再按 [SKILL.md](SKILL.md) 捕获原型。将胜出者恰当地重写并融入真实代码；其余变体保留在 `.agent/work/<feature>/prototypes/` 而不进入主线：

- **子形态 A**：把胜出者融入现有页面；从主线移除落选变体和切换器。
- **子形态 B**：将胜出者提升为正式路由；从主线移除一次性路由和切换器。

完整变体集合是一手证据，不应遗留在主分支——主分支中的变体组件和切换器会很快腐化并误导下一位读者。若策略批准，可预览后转存到一次性分支；不得自动创建分支或 Commit。

## 反模式

- **变体只改颜色或文案。** 那是微调，不是原型；真实变体应对结构有不同看法。
- **变体共享过多代码。** 共享 `<Header>` 可以，共享 `<Layout>` 则违背目的；每个变体应能自由推翻布局。
- **将变体接到真实写操作。** 只读原型无妨；需要修改时指向 stub。问题是“它该长什么样”，不是“后端能不能工作”。
- **直接将原型提升到生产。** 变体代码受原型约束（无测试、最小错误处理）；吸收胜出者时应按正式标准重写。
