# 技术方案与发布文档结构参考

以下为通用基准结构；若目标飞书知识库或团队目录已有现行模板，优先对齐团队现行模板，无实际内容的章节直接省略。

---

## 一、技术方案

用于评审方案是否成立、风险是否可控（面向人类评审人，按项目实际类型裁剪子章节，无内容的章节直接省略）：

0. **方案总览**（文首固定区块，飞书使用蓝色 `<callout emoji="💡" background-color="light-blue" border-color="blue">`，HTML 对应 Overview 卡片并额外含`关键风险与边界`卡片）：
   - **背景与问题**：把触发本需求的根本业务痛点放在第 1 条，简明列出核心背景。
   - **核心方案**：用 2 到 3 条加粗短列表概括核心改动动作、关键策略及验证方式，重点词用彩色高亮标出。
1. **背景与目标**（或 **需求概述**）：
   - **问题分析与目标**：将首要业务痛点置顶；跨时间点、跨阶段或新旧表现差异复杂时，配「顶部阶段/时间轴列标 + 上下新旧方案对比行」的二维对比图，图外补齐痛点影响、关键算例结论与预期目标；简单问题直接用列表或小表说明（必要时附新引入的名词术语表）。
   - **职责分工与改动边界**：用短列表交代本服务职责与上下游分工、本次修改的模块、直接复用的上下游/表结构/既有稳定性机制（如既有单事务、分布式锁、幂等校验），以及合理预期可能包含但决定另案处理的关联事项。
2. **核心方案设计**（围绕本项目核心问题命名子标题，使用简短专业的工程名词短语）：
   - **核心流程与系统位置**：复杂链路配流程图或时序图（用外框区分本次改动范围与既有模块），图下按复杂度选用双栏卡片（飞书 `<grid>` + `<callout>`，HTML `.comparison` + `.comparison-card`）或短列表说明各分支的业务动机与处理规则；若有周边工具改造，先交代改造原因与效果，再对比「改造前 / 改造后」。
   - **关键规则与结构转换**（按项目实际涉及的内容选写）：
     - 枚举或字典映射：使用独立表格按分类逐行展示；
     - 跨组件协议或数据结构转换：先用短列表交代转换原因及上下游、表字段归属，再用表格列出核心差异字段转换规则；
     - 状态机、并发、在途与通用性兼容：有新增风险时说明旧数据兼容与回填、在途异步任务或工作流签名兼容、多主体与多品类通用性；直接复用现有稳定机制时在「改动范围与边界」处一句话带过，不重复列大表。
   - **备选方案与取舍**：有真实权衡或调研期排除的候选方案时，简述对比维度与排除原因，不混入背景痛点。
   - **数据与接口变更**：只贴新增或修改的核心 Proto、DDL、SQL、MQ、配置片段。
3. **测试与上线方案**：
   - **验证方案与测试用例**：涉及预发数据比对、双跑或流量回放时，按复杂度配验证架构图展示数据流向，用黄色 `<callout emoji="⚠️">`（HTML `.callout.warn`）高亮安全隔离红线，并用双栏或列表说明「**核对项（及原因）**」与「**排除项（及原因）**」；用紧凑表格（`分类 | 测试场景 | 构造输入 | 预期结果`）列出测试用例。
   - **上线、灰度与回滚方案**：分开说明**上线顺序与灰度维度**、**回滚触发条件与不可逆边界**、**服务版本回滚**、**异常数据/状态恢复步骤**（写明可查验的表字段状态判据、工具适用限制与经代码核实的恢复命令），以及有变化时的**监控与容量评估**（如 QPS/存储评估、批处理非 0 与同比波动、实时流量分支上报）。
4. **前置准备与参考资料**：上线或验证前需完成的准备事项清单（权限申请、数据同步配置、待确认项），以及带真实可点击 URL 的参考资料列表。

## 二、发布文档

用于上线交付、变更评审与执行核对。章节结构保持完整，按实际改动填写：

1. **需求描述**：需求单链接 + 一两句话概述需求。
2. **方案设计**：贴技术方案文档链接。
3. **代码改动**：简要说明改动点 + 贴 MR 链接。
4. **影响范围、风险评估、监控指标**：
   - 按四维表格梳理**影响点 / 风险说明 / 监控与告警指标**：
     - **功能**：影响哪些功能、有无风险。
     - **数据**：① 历史数据与代码兼容性；② 新代码读旧数据是否兼容；③ 旧代码读新数据是否兼容；④ 产生新数据后能否回滚。
     - **主体与地区维度**：各业务主体或地区实例分别受何影响（多主体/多地区部署适用）。
     - **外部影响**：是否对上下游产生额外流量或依赖。
   - **监控指标**：批处理关注数据非 0、同比波动；实时流量关注分支上报。
5. **测试用例**：测试覆盖范围说明或思维导图。
6. **测试报告**：
   - 团队验证红线（适用时必须说明）：
     - **实时读接口**：进行线上流量录制回放测试，新旧版本返回差异须明确解释。
     - **实时写接口**：写操作前读取全部字段 → 执行写 → 写后再次读取全部字段 → 逐字段比对，确保只有目标字段变更、其他字段未被篡改。
     - **影响账本或报表数据准确性的修改**：在预发布/镜像/灰度环境进行至少 N 个交易日的双跑验证或历史数据回归（明确 N 的取值与理由），**必须全量比对，不允许仅抽样比对**，差异须明确解释。
   - 自测结果表：`功能点 | 测试场景（成功/异常）| 测试用例（单测或接口测试链接）| 测试结果 | 说明/截图`。
7. **性能分析**：新服务评估流量/容量/内存/压测结论；常规迭代说明流量变化（无影响可简写）。
8. **发布前 Checklist**：
   - 基础资源：DB 表/权限、Kafka 资源、服务鉴权/授权、上下游依赖就绪。
   - 常见踩坑核对（涉及对应组件时必查）：
     - 使用基于 DB 的分布式锁或消息去重/重试表：是否已建表并申请清理所需的 `DELETE` 权限；消息队列开启 SASL 且启用重入队时，认证配置作用层级是否正确（如集群级而非单 consumer 级）。
     - 提供或调用服务发现/名字服务：寻址注册与路由规则是否已验证。
     - 配置文件中是否残留测试环境硬编码（如 `test_xxx:port`）。
9. **灰度计划、回滚预案、发布后验证**：
   - 按阶段（如单主体/灰度地区发布、全量发布、补历史数据 SQL）列出表格：`阶段 | 日期与时间段（是否需避开特定时段）| 发布任务（部署组/流量比例/SQL）| 回滚方案/回滚SQL | 发布后验证（日志/监控/手动/灰度流量/跨周期或跨交易日观察）| 验证结果`。
10. **遗留项 & 发布记录**：后续需跟进的资源回收、表结构清理等；发布过程异常记录。
