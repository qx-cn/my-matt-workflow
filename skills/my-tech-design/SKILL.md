# 技术方案

生成一份用于技术评审的交互式 HTML 方案。让读者先理解整体改动，再按需深入承重决策；不要把它写成实现清单。

## 1. 建立事实基础

阅读当前对话、相关代码、项目规则和已有设计文档，确认：

- 问题、目标与边界；
- 当前架构和主流程；
- 受影响的模块、接口和数据；
- 已确定的决策、假设和待确认问题。

无法确认的信息标记为假设或待确认，不得自行补全。只有缺失信息会改变整体架构或关键接口时才提问。

## 2. 筛选内容

写作前识别：

- 一句话方案结论；
- 整体改动范围；
- 目标架构与主流程；
- 承重的技术决策；
- 接口或数据契约变化；
- 主要风险及验证方式。

承重决策是会影响架构、接口、数据一致性、性能、可靠性、兼容性或实施范围的选择。普通实现细节不单独展开；没有有效内容的章节直接删除。

## 3. 组织章节

按需使用下列章节：

1. **方案总览**：在一个屏幕左右说明为什么改、总体怎么改、涉及哪些模块、关键选择和最大风险；包含目标架构图或整体改动图。
2. **架构与流程**：展示目标架构和关键流程。只有理解方案需要时才补充现状图或前后对比图。
3. **关键决策**：每项说明背景与约束、备选方案、选择与理由、主要代价、重新评估条件。
4. **改动与接口**：汇总所有受影响模块。将接口标记为新增、修改或废弃，并说明目的、输入输出、关键不变量、错误语义和兼容方式。
5. **交付与风险**：按实际需要说明测试、监控、迁移、灰度、回滚、风险和待确认问题。

整体改动必须完整，局部实现可以省略。使用模块和接口描述影响范围，只在文件位置影响评审结论时列出具体路径。

## 4. 选择图形

- 系统组成与依赖：架构图；
- 处理步骤与分支：流程图；
- 跨模块调用顺序：时序图；
- 实体和表关系：ER 图；
- 生命周期：状态图；
- 架构变化：前后对比图。

每张图只回答一个主要问题，突出本次变化，图后用一句话写出结论。没有信息增量时不画图。

## 5. 控制密度

- 先写结论，再写依据；
- 一个段落不超过三句话；
- 背景、备选方案和补充细节默认折叠；
- 同一信息只保留一个权威位置，其他位置使用链接；
- 图表达关系和过程，文字表达结论、原因与约束。

## 6. 生成 HTML

复制并填写 [HTML 模板](assets/TEMPLATE.html)，不要从头设计页面框架。保留其离线导航、章节切换、折叠和打印能力；只有内容确实需要时才增加其他交互。

使用内联 SVG 绘图。CSS、JavaScript 和资源全部内联，不加载 CDN 或远程资源。删除空章节、对应的导航与翻页链接，以及所有 `{{...}}` 占位符。

保存到 `.agent/work/<topic>/designs/designs-<topic>-<time-or-sequence>.html`，不得覆盖已有方案。

## 7. 检查

完成前确认：

- 只看总览就能理解整体方案；
- 模块和接口改动没有遗漏；
- 每项承重决策包含背景、选择和代价；
- 每张图都回答明确问题；
- 假设与待确认项清晰可见；
- 没有重复文字、空章节或占位符；
- HTML 可以离线打开、切换章节并打印。
