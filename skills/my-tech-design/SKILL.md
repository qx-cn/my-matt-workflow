# 技术方案

生成一份用于技术评审的交互式 HTML 方案。让读者先理解整体改动，再按需深入承重决策；不要把它写成实现清单。

## 1. 建立事实基础

阅读当前对话、相关代码、项目规则和已有设计文档，确认：

- 问题、目标与边界；
- 当前架构和主流程；
- 受影响的模块、接口和数据；
- 已确定的决策、假设和待确认问题。

无法确认的信息标记为假设或待确认，不得自行补全。只有缺失信息会改变整体架构或关键接口时才提问。

## 2. 筛选内容

写作前识别：

- 一句话方案结论；
- 整体改动范围；
- 目标架构与主流程；
- 承重的技术决策；
- 接口或数据契约变化；
- 主要风险及验证方式。

承重决策是会影响架构、接口、数据一致性、性能、可靠性、兼容性或实施范围的选择。普通实现细节不单独展开。

## 3. 命名文档并规划章节

优先采用用户给出的标题，其次采用 Spec、Issue 或需求标题；都没有时，根据目标命名为简洁的“对象 + 变化”方案，例如“订单创建幂等改造”。不要使用泛化的“技术方案”作为文档标题。

**方案总览是唯一固定章节。**其余章节根据改动面生成，并使用实际职责命名，而不是套用固定目录：

- 修改表、字段、索引、事务语义或数据迁移时，单独生成数据库设计章节；
- 修改 Proto、HTTP 接口、事件格式或兼容规则时，单独生成协议与接口设计章节；
- 修改生命周期或复杂状态变化时，单独生成状态模型章节；
- 架构、核心流程、迁移发布、测试监控或风险足以独立评审时，各自成章；
- 琐碎内容并入最相关章节；没有有效内容的章节不生成。

先确定章节标题、顺序和每章要回答的问题，再生成导航与页面。章节名称应体现实际内容，例如“存储模型与数据迁移”或“Order Proto 契约与兼容”，而非统一写成“改动详情”。

## 4. 组织内容

**方案总览**在一个屏幕左右说明为什么改、总体怎么改、涉及哪些模块、关键选择和最大风险，并包含目标架构图或整体改动图。

其他章节按评审问题组织。涉及接口时说明新增、修改或废弃项，以及目的、输入输出、关键不变量、错误语义和兼容方式。涉及承重决策时说明背景与约束、备选方案、选择与理由、主要代价和重新评估条件。

整体改动必须完整，局部实现可以省略。使用模块和接口描述影响范围，只在文件位置影响评审结论时列出具体路径。

## 5. 选择图形

- 系统组成与依赖：架构图；
- 处理步骤与分支：流程图；
- 跨模块调用顺序：时序图；
- 实体和表关系：ER 图；
- 生命周期：状态图；
- 架构变化：前后对比图。

每张图只回答一个主要问题，突出本次变化，图后用一句话写出结论。没有信息增量时不画图。

## 6. 控制密度

- 先写结论，再写依据；
- 一个段落不超过三句话；
- 背景、备选方案和补充细节默认折叠；
- 同一信息只保留一个权威位置，其他位置使用链接；
- 图表达关系和过程，文字表达结论、原因与约束。

## 7. 生成 HTML

复制并填写 [HTML 模板](assets/TEMPLATE.html)，不要从头设计页面框架。保留其离线导航、动态章节切换和折叠能力；只有内容确实需要时才增加其他交互。

使用内联 SVG 绘图。CSS、JavaScript 和资源全部内联，不加载 CDN 或远程资源。用实际章节生成 `{{NAV_ITEMS}}` 和 `{{CHAPTER_SECTIONS}}`，并删除所有其他 `{{...}}` 占位符。

保存到 `.agent/work/<topic>/designs/designs-<topic>-<time-or-sequence>.html`，不得覆盖已有方案。

## 8. 检查

完成前确认：

- 标题准确描述了本次方案；
- 只看总览就能理解整体方案；
- 章节来自真实改动面，数据库和协议变更各有独立章节；
- 模块和接口改动没有遗漏；
- 每项承重决策包含背景、选择和代价；
- 每张图都回答明确问题；
- 假设与待确认项清晰可见；
- 没有重复文字、空章节或占位符；
- HTML 可以离线打开并切换所有章节。
