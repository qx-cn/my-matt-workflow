# 技术方案

生成一份用于技术评审的交互式 HTML 方案。让读者先理解整体改动，再按需深入承重决策；不要把它写成实现清单。

## 1. 建立事实基础

阅读当前对话、相关代码、项目规则和已有设计文档，确认：

- 问题、目标与边界；
- 当前架构和主流程；
- 受影响的模块、接口和数据；
- 已确定的决策、假设和待确认问题。

先按[最终态写作](references/shared/final-state-writing.md)收束有效内容，再组织方案。

无法确认的信息标记为假设或待确认，不得自行补全。只有缺失信息会改变整体架构或关键接口时才提问。默认读者是不了解当前代码细节、但需要评审架构与方案的工程师。

## 2. 建立改动面清单

写作前先建立内部改动面清单，不要直接压缩成章节。逐一提取当前代码和已确认目标中的明确动作，例如新增、迁移、替换、废弃、投递、消费、重跑、恢复和回滚。每项记录：改动对象、具体变化、影响范围、关键约束和验证方式。

下列任一情况视为关键改动面：

- 输入材料用独立章节描述该变化；
- 迁移数据库表、状态或其他事实来源；
- 新增或修改 Kafka、消息队列、事件、回调等外部副作用；
- 新增或修改 rerun、backfill、恢复脚本、CLI、status 等人工操作路径；
- 影响兼容性、一致性、发布顺序或回滚；
- 用户明确强调，或在材料中反复出现。

每个关键改动面必须同时出现在总览改动地图、一个名称明确的章节或小节，以及对应的验证或风险中。普通实现细节可以省略，但关键改动面不能因压缩而消失或只剩一行带过。

另外识别一句话方案结论、目标架构与主流程、承重决策和主要风险。承重决策是会影响架构、接口、数据一致性、性能、可靠性、兼容性或实施范围的选择。

同时建立内部图形清单，逐一识别系统组成与依赖、跨模块调用顺序、流程与异常分支、状态变化、实体关系及改动前后差异。只要存在这些关系，默认安排对应图形；只有文字或表格明显更清楚时才省略。不要要求每章都有图，纯结论、精确字段和简单规则优先使用文字或表格。

## 3. 命名文档并规划章节

优先采用用户给出的标题，其次采用 Spec、Issue 或需求标题；都没有时，根据目标命名为简洁的“对象 + 变化”方案，例如“订单创建幂等改造”。不要使用泛化的“技术方案”作为文档标题。

**方案总览是唯一固定章节。**其余章节根据改动面生成，并使用实际职责命名，而不是套用固定目录：

- 修改表、字段、索引、事务语义或数据迁移时，单独生成数据库设计章节；
- 修改 Proto、HTTP 接口、事件格式或兼容规则时，单独生成协议与接口设计章节；
- 修改生命周期或复杂状态变化时，单独生成状态模型章节；
- 架构、核心流程、迁移发布、测试监控或风险足以独立评审时，各自成章；
- 琐碎内容并入最相关章节；没有有效内容的章节不生成。

先确定章节标题、顺序和每章要回答的问题，再生成导航与页面。章节名称应体现实际内容，例如“存储模型与数据迁移”或“Order Proto 契约与兼容”，而非统一写成“改动详情”。

优先复用输入材料和代码中的项目术语。标题使用具体对象和动作，例如“Task 表迁移与断点”“Kafka 投递与 Snapshot”“人工重跑流程与冲突检查”。不要为归类而发明“执行模型”“身份治理”之类的抽象概念；能写成“触发方式与任务 ID”时，就不要写“执行模型与身份”。
只在描述 Proto、API、消息格式等可观察接口时使用“契约”。人工操作、并发互斥、等待行为等内容使用“流程”“规则”或“约束”。

## 4. 审校原方案

生成 HTML 前检查原方案中的标题和自然语言。代码标识符、API、表字段、Topic、命令和枚举保持不变；普通标题、说明文字和表格中的叙述可以调整。不要机械翻译团队常用英文，例如 domain、checkpoint、workflow；也不要为了归类创造原文和团队都没有的术语。“身份”只表示认证或授权主体，其他场景直接写 task ID、唯一键或区分方式。

区分两类问题：

- 原方案本身生硬、含糊或依赖代码上下文：提出原文、建议文本和理由；
- 只因 HTML 摘要过度压缩而产生：只修改 HTML。

原方案同步默认采用 `source_sync: confirm`：预览时必须在 HTML 使用建议文本，并同时给出回写清单，但未经确认不修改原文件；确认后先回写原方案，再从更新后的原方案重新生成 HTML。原文件不可编辑时只提供修改建议。

## 5. 组织内容

**方案总览**用于让不了解代码的评审者建立完整印象。在一个屏幕左右说明当前问题、总体流程、涉及哪些模块、关键选择和最大风险，并包含目标架构图或整体改动图。不能用关键词或实现标识符代替解释。

其他章节按评审问题组织。涉及接口时说明新增、修改或废弃项，以及目的、输入输出、关键不变量、错误语义和兼容方式。涉及承重决策时说明背景与约束、选择与理由、主要代价和重新评估条件；备选方案仅按最终态写作规定的例外保留。

事实来源迁移应单独说明迁移前后、切换条件、是否回读旧来源及回滚边界。外部消息按“发送时机、目标 Topic 与用途、空数据处理、失败与重试、幂等或顺序约束”分点说明，不得把这些信息压进连续段落。人工重跑或恢复能力应说明入口、参数、完整流程、互斥规则、等待与状态查询，以及它与正常流程的差异。

整体改动必须完整，局部实现可以省略。每章先用评审语言说明设计含义，再把表名、字段、函数、唯一键和 CAS 等实现证据放入表格或折叠区。章节标题下的导语不写复合键、SQL 条件、函数调用或字段清单，通常最多出现一个代码标识符。使用模块和接口描述影响范围，只在文件位置影响评审结论时列出具体路径。

整体改动地图是评审导航，不是详细设计。每行只回答改什么、怎么改、评审重点是什么，并链接到详情章节。方案摘要通常为 30～60 个中文字符，评审重点通常为 15～35 个中文字符；这是软限制，不能以牺牲可读性换取字数。单元格最多两句话，不展开函数、字段、唯一索引和异常分支。

段落只用于章节导语、单一结论及其原因，或必要的上下文说明。出现两个以上独立事实、规则、动作或约束时必须拆点；操作顺序使用编号列表，并列要求使用无序列表。正常与异常、成功与失败、包含与不包含等对比内容必须分组呈现，不得混写在同一段落。一句话同时描述条件、行为和异常，或连续出现多个实现标识符时也必须拆点。不要用分号压缩复杂流程。“两套”“相关”“当前批次”等指代离开上下文后不明确时，直接写出入口、范围或对象名称。

范围边界以及“改动前/改动后”“支持/不支持”等成对内容使用独立对比区块。每侧必须有自己的标题和列表，并保留清晰间距；宽屏可并列，空间不足时整体上下排列。禁止使用“标签 + 长文本”的行内布局，避免一侧换行后落到另一侧标题下方。

## 6. 选择图形

先识别要表达的关系，再选择图形，不要先决定图形类型。凡是存在结构、关系、顺序、分支、状态或前后变化，默认用图表达；只有纯结论、精确字段、简单规则，或文字、表格明显更清楚时才省略。不要用“正文已经说明”作为不画图的理由。

- 系统模块、边界与依赖：架构图；
- 处理步骤、条件与异常分支：流程图；
- 跨模块调用及先后关系：时序图；
- 实体、表及其关联：ER 图；
- 生命周期与状态迁移：状态图；
- 改动前后的结构或流程差异：前后对比图；
- 少量精确字段或规则对照：表格，不强行画图。

方案总览必须包含一张能独立解释整体方案的目标架构图或整体改动图。每个关键流程、复杂状态变化或跨模块协作都应有对应图形；同一章节可以使用多张图，但每张图只回答一个主要问题。

图中突出本次变化，并在适用时包含正常路径和关键异常。图后用一句话写出结论；正文补充原因和约束，不重复展开图中已经清楚表达的关系。

## 7. 控制密度

- 先写结论，再写依据；
- 一个段落不超过三句话；
- 背景、需保留的决策依据和补充细节默认折叠；
- 同一信息只保留一个权威位置，其他位置使用链接；
- 图表达关系和过程，文字表达结论、原因与约束。

## 8. 生成 HTML

复制并填写 [HTML 模板](assets/TEMPLATE.html)，不要从头设计页面框架。保留其离线导航、动态章节切换和折叠能力；只有内容确实需要时才增加其他交互。

使用内联 SVG 绘图。CSS、JavaScript 和资源全部内联，不加载 CDN 或远程资源。用实际章节生成 `{{NAV_ITEMS}}` 和 `{{CHAPTER_SECTIONS}}`，并删除所有其他 `{{...}}` 占位符。

密集表格和长列表使用整行卡片，不得放入 `span-4` 等窄栏。两栏布局只用于短段落或字段很少的对比；内容放不下时减少并列，而不是缩窄文字。

对比内容使用模板提供的 `comparison` 与 `comparison-card` 类；每个 `comparison-card` 内必须使用 `ul` 或 `ol`，不得用一个段落承载多项内容。

保存到 `.agent/work/<topic>/designs/designs-<topic>-<time-or-sequence>.html`，不得覆盖已有方案。

## 9. 检查

完成前确认：

- 标题准确描述了本次方案；
- 只看总览就能理解整体方案；
- 改动面清单中的每个关键项都能在正文和验证中定位；
- 章节来自真实改动面，数据库和协议变更各有独立章节；
- 事实来源迁移、外部消息和人工操作路径没有被合并到难以发现的泛化章节；
- 标题使用项目术语和具体动作，“契约”只用于可观察接口；
- 已扫描原方案中的生硬术语，并区分需要回写与只需修改 HTML 的问题；
- 模块和接口改动没有遗漏；
- 每项承重决策包含背景、选择和代价；
- 已建立图形清单，每个可视化关系都有对应图形，或确有文字、表格更清楚的理由；
- 总览包含能独立解释整体方案的目标架构图或整体改动图；
- 每个关键流程、复杂状态变化和跨模块协作都有对应图形；
- 图形类型与要表达的关系匹配，图中包含适用的正常路径、关键异常和本次变化；
- 本来适合用图的关系没有滞留在长段落中；
- 每张图都回答明确问题，正文没有重复展开图中关系；
- 假设与待确认项清晰可见；
- 没有重复文字、空章节或占位符；
- 整体改动地图简短但能独立读懂，并能跳转到详情；
- 长句和实现细节没有挤成难读的段落；
- Kafka 等外部消息章节已按发送、内容、空数据、失败和一致性要求分点；
- 范围边界和其他成对内容使用独立对比区块，每侧都有标题和列表；
- 运行 `python3 scripts/check_html.py <html>` 并处理全部错误；逐条复核术语警告；
- 实际渲染并检查每个章节，至少覆盖 1440px 和 1280px 桌面宽度；没有窄列逐字换行、裁剪、重叠或意外横向滚动；
- HTML 可以离线打开并切换所有章节。
