# 技术方案、发布文档与测试报告写作

本 Skill 负责把已对齐的需求和代码事实整理成**唯一一份好读好讲、契约清晰的纯 Markdown 定稿**（不再拆出第二份重叠的代码级 `spec.md` 或独立 `decided.md`）。这步只专注内容、逻辑、表格和配图，不混写飞书 XML、HTML 标签或画板坐标代码，写完再自动衔接排版发布。

依据需求讨论、同目录已有的 `refs/`、`evidence/` 和真实源码编写，遵守全局写作与同步规范：

- **查源码核实硬事实**：准备写进文档的物理库表名、字段名、协议路径、配置键和命令参数，先去仓库 `.sql`、`.proto` 或代码里查实，不靠印象瞎写，绝不凭猜测编造 SQL 列名；还没法确认的问题放进待确认项。
- **长会话优先派干净子 Agent**：如果当前聊天已经攒了大量代码排障日志，优先派一个新子 Agent 起草初稿（传入需求与决策摘要、`refs/`、源码目录，以及全局规则、本文件与同目录 `TEMPLATES.md` 的绝对路径），避免满屏源码日志把文风带歪。

---

## 1. 先看写哪一类文档

按文档类型读取 [TEMPLATES.md](TEMPLATES.md) 中对应的结构，删掉用不上的小节：

- **技术方案**（默认）：同时服务于**团队方案评审**和**后续编码验收**，篇幅通常在 **2,000 至 4,500 字**。目标是让同事 5 到 10 分钟看懂背景、核心设计、对外契约、关键取舍与回滚兜底，同时也给后续写代码的 Agent 提供明确的规则与验收标准。
- **发布文档**：写给变更审批人和上线值班同事，重点写改了什么、核心验证数据、影响范围、上线步骤和回滚恢复命令（比对明细和长报文多时单独拆到《测试报告》）。
- **测试报告**：写给验收同事，重点写验证规模与通过率、比对统计表、边界用例，以及从 `evidence/` 提取的真实请求响应报文、日志或 SQL 结果（不要拿几行注释冒充真实报文）。

---

## 2. 分清什么该写进方案、什么留给代码

一份文档要同时让同事爱看、让编码 Agent 不跑偏，关键是**写清业务不变量与对外契约，砍掉代码里本来就能查到的内部琐碎实现**：

- **必须写清楚的内容（人与编码 Agent 都需要）**：
  1. **顺着人话讲清背景与目标**：先说现实业务遇到了什么场景，再说现网为什么卡住、现成办法为什么走不通，最后直接写系统新增什么具体能力、支持哪些操作（别写“保障链路准时启动、保留完整闭环”这类空话）。
  2. **核心规则、对外硬契约与取舍**：写清状态与操作规则、新增或修改的 DB DDL、Proto/接口字段与错误码、新增文件真实样例与动态配置结构、命令行工具参数，以及 3 至 5 行的《备选方案取舍》表（直接记录关键决定与排除原因）。
  3. **主干居前，边角兼容收尾**：前面 80% 篇幅专心讲核心主流程；低频模式的兼容上限、时区过滤或并发重跑防呆等边界要求，用一两句大白话统一收拢在方案设计末尾一节轻量的《边界与兼容说明》小表里，别塞进主干标题到处刷屏。
- **坚决不写进方案的细枝末节（交给编码时读源码 + 跑单测保证）**：
  - 源码文件路径与行号（如 `.go:168`）、存量私有辅助函数名、内部临时变量名、分布式锁 key 字符串怎么拼、内部并发占位常量或 `RowsAffected == 0` 怎么回查，以及本次没改到的存量老机制，正文和图里一律不写。
- **保留团队英文原词**：日常固定直呼英文的服务简称、操作名和对象名（如 `Approve`、`Reject`、`Dry Run`、`Webhook`）全文统一用英文原词，别猜全称硬翻成中文，也别一会儿叫“签批”一会儿叫“审批”。

## 3. 用标准图和短表格代替大坨文字

写到状态机、接口改造、跨服务调用、数据库变更、灰度与回滚时，按 [TEMPLATES.md](TEMPLATES.md) 第四节的常用构件写法展开（没涉及的部分直接略过，不硬凑空表）：

- **单节只讲一件事**：每个二级小节只回答一个问题，开头用引用块 `>` 写一句直白结论，下面紧接图或表。两个子话题如果各自都有表格、代码块或多条规则，就拆成两个同级小节。
- **多用矩阵表、双栏块与外提代码块，少堆密集文字与反引号**：
  - 正反两难或二元分类（如现网两种死胡同、允许跳过 vs 报错阻断的任务）列为对称双块；3 种以上操作时机对应的结果规则直接列为 3 列场景小表，不写连串长段列表；单条列表超过两行半时拆成“短主干 + 缩进子列表”。
  - 涉及状态机时，把状态定义、状态流转图、**状态 × 可执行操作矩阵表**（哪个状态能干啥）和动作表分开列清；加新状态替代旧校验时，列一张 **4 列精炼对照表**（`接口/检查项 | 原来查什么 | 现在改查什么 | 说明`，相同规则合并同行，单格保持 1 至 2 行短词条）。
  - 3 项以上的存量状态推导或初始化映射直接列成小表格；新增对外文件（如 CSV 报表）或动态配置时，贴上 5 至 12 行真实样例代码块和字段说明表。
  - 端到端验证表拆清 `验证场景 | 触发动作 | 预期检查点（单行短分点）` 三列；异常恢复表若有重复使用的长命令行，**先把命令模板提取到表外独立代码块**，表内每格只留 1 至 2 行精炼条件与短子命令。
  - 普通英文动作词与大类名称（如 Submit、Approve、DRAFT）直接写正文，反引号只留给物理表字段、文件名、配置键与错误码，避免满页灰框视觉噪点。
- **跨组件先后调用画时序图**：涉及 3 个及以上组件来回调用、库表更新与异步动作时，直接画 Mermaid `sequenceDiagram` 时序图，配两三条短说明即可，别写三大段调用流水账。
- **配图干净无漏边**：单图节点控制在 4 到 9 个，框内和连线上只写直白状态和动作词（零内部黑话）；状态图画完逐行核对表格确认没漏掉合法转移边，分支判定图把判断节点放最前面、报错阻断画成独立终点（别指回正常主干），每张图下方配一句 `> 图 N：<核心结论>`。

## 4. 通读自检与一步发布

1. 把定稿保存到 `.agent/work/<主题>/design.md`（或 `release.md`、`test-report.md`）。如果用户还没说要发到哪里（飞书云文档 / 本地 HTML / 只留本地 `.md`），简短问一句。
2. **当自己是讲方案的人通读一遍**：
   - 背景和目标念起来顺口吗？有没有空话、生造词或乱翻的英文词？
   - 状态权限、老接口切换、跨服务时序、存量映射和文件样例都用上清爽的图和短表了吗？还有没有看着头疼的大坨文字或超大单元格？
   - 低频兼容点是不是已经收拢到末尾？写出来的表名、列名、接口、错误码和真实源码对得上吗？
3. **自动衔接发布（无需用户再敲第二个命令）**：
   - 只留本地 `.md` 时直接交付文件路径（后续可直接用于新会话编码实施）。
   - 需要发飞书或生成本地 HTML 时，直接读取本文件同级目录下的 `my-doc-publish/SKILL.md`（派子 Agent 发布时传入定稿 `.md`、`rules/global.md` 与 `my-doc-publish/SKILL.md` 的绝对路径），按里面的排版与脚本校验流程走完并交付链接。审查由用户按需调用 `my-review`，生成完不自动拉起审查子 Agent。
