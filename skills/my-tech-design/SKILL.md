# 技术方案与工程文档写作

本 Skill 负责把已对齐的需求和代码事实整理成纯 Markdown 定稿。单个需求默认用一份技术方案指导评审和编码验收，涉及独立子系统或不同评审团队时按评审边界拆分（不再拆出第二份重叠的代码级 `spec.md` 或独立 `decided.md`）。这步专注内容组织、语言表达、表格设计和配图策划，不混写飞书 XML、HTML 标签或画板坐标代码，写完按需衔接排版发布。

依据需求讨论、同目录已有的 `refs/`、`evidence/` 和真实源码编写，遵守全局写作与同步规范：

- **查源码核实硬事实**：准备写进文档的库表名、字段名、协议路径、配置键、命令参数，以及动态文件样例格式和完整业务枚举映射，都先去仓库 `.sql`、`.proto`、配置样例或代码里查实；还没法确认的问题放进待确认项。
- **把源码注释转成自然人话**：区分真实代码标识符与内部注释用语。源码注释、提交记录或草稿里常混有程序员随手写的生硬译词、自造缩写或口号，引用逻辑时改写成谁都能听懂的现代汉语动宾短句，直接讲清动作和对象。
- **在干净会话中直接起草，长会话派子 Agent 隔离**：如果当前本就是新开的干净聊天窗口，主 Agent 直接顺序完成；如果当前聊天已攒了大量代码排障日志，派一个新子 Agent 起草初稿，传入需求与决策摘要、`refs/`、源码目录，以及从本文件真实路径解析的 `../../rules/global.md`、本文件与同目录 `TEMPLATES.md` 绝对路径，避免排障日志把文风带偏。

## 1. 文档类型与定稿边界

按文档类型读取 [TEMPLATES.md](TEMPLATES.md) 中对应的结构，删掉用不上的小节：

- **技术方案**（默认）：同时服务于**团队方案评审**和**后续编码验收**，篇幅通常在 **2,000 至 4,500 字**。目标是让同事 5 到 10 分钟看懂背景与前后差异、核心设计、对外契约、方案取舍与回滚兜底，同时也给后续写代码的 Agent 提供明确的规则与验收标准。
- **发布文档**：写给变更审批人和上线值班同事，重点写改了什么、核心验证数据、影响范围、上线步骤和回滚恢复命令；比对明细和长报文多时单独拆到《测试报告》。
- **测试报告**：写给验收同事，重点写验证规模与通过率、比对统计表、边界用例，以及从 `evidence/` 提取的真实请求响应报文、日志或 SQL 结果（不用注释冒充真实报文）。

**定稿写法边界**：

- **只写当前有效的定稿内容**：技术方案只写当前有效的目标、核心设计、对外契约、方案取舍和验收条件，新决定直接覆盖作废讨论；不留“我们讨论过”“用户要求”“评审认为”等过程记录、无关修订号、模型分工或作者待办，保留必要的设计依据、引用链接和已知限制（发布文档、测试报告按用途保留验证证据、发布记录和待办）。
- **标题单一主题，动作句以动词开头**：章节标题和分类标签用简短自然的日常名词短语或动宾短语，点明本节唯一主题，不用顿号堆砌多个子点，不用口语疑问句、括号解释或错误对立的 `vs`，标题下不写“本节介绍 A、B、C”式导语。表达具体动作、规则或结论的列表引导项，用具体动词开头（例如“跳过最近 5 分钟更新的记录”“比对时忽略非业务字段”“先推送配置再做预发验证”），避免把动词压到句尾或喊四字口号。
- **省略代码内部实现细节**：代码里一查便知的文件路径与行号（如 `.go:168`）、存量私有辅助函数名、内部临时变量名、分布式锁 key 拼接字符串或 `RowsAffected == 0` 怎么回查，正文和图里都不写。

## 2. 内容选材与前后对比

一份文档要同时让同事爱看、让编码 Agent 不跑偏，关键是把真正帮读者做判断的对比、契约和边界讲透：

- **分清背景痛点与实施难点**：`1.1 背景与问题` 只写促成本次改造的真实业务痛点或上游演进原因，配 1 个具体算例；新方案开发期的参数适配或测试期的内存优化归入第 2、3 章对应设计小节，不放进背景当成现网已有故障。
- **涉及接口切换或重构时突出改造前后对比**：凡涉及接口切换、链路重构或工具改造，优先在同一场景或步骤下直观对比改造前旧做法怎么受阻、改造后新方案怎么解决。
- **补齐增量契约与《方案取舍》**：写清核心规则、本次新增或修改的增量 DB DDL（如 `ALTER TABLE`，不复制存量完整大表）、变更的 Proto 或接口字段与错误码、命令行参数，以及独立的《方案取舍》表（用 3 至 5 行写明采用方案、备选方案和排除原因）。
- **按性质区分两类配置与文件**：
  - 承载市场路由、通道字典、权限开关等业务规则的配置，用表格完整列出全部有效业务映射关系（几十条以内全列，不截断成 2 行示例去解释 JSON 基础语法）。
  - 动态产出的报表或协议报文，核实源码真实拼接格式后贴简短样例，下方配字段口径表。
- **先讲核心主流程，再集中写兼容边界**：前面 80% 篇幅专心讲核心主流程；低频模式的兼容上限、特殊主体跳过或重跑防呆等边角要求，统一收拢在方案设计末尾一节轻量的《边界与兼容说明》小表里，不塞进主干标题或全文反复提及。
- **按内容决定是否加结论句**：讲核心机制的小节开头用 `>` 写 1 句具体因果结论；多条目汇总表小节（如《方案取舍》《边界与兼容说明》《端到端验证场景》）表格本身已自明时直接进表，不硬凑空泛总结句。

## 3. 配图策划与清爽表格

### 3.1 按三步法策划配图

画图是为了帮读者省脑力，不是凑数量。动笔前按下面三步在 `design.md` 里规划好每张图（可用简洁 Mermaid 或结构化文字草稿描述，留给 `my-doc-publish` 渲染高清画板）：

1. **先抓读者最绕的卡点，再写结论图注**：找出全篇光靠文字最费劲的 1 到 3 处（如跨切点时序错位、新旧方案差异、改动范围边界、多环境比对链路），先写出图注 `> 图 N：<读者看完这张图该记住的一句话结论>`，再围绕这句话设计画面。
2. **在图里放具体算例和改造边界**：前后对比图放**同一个具体业务算例**（带真实日期、状态或单号格式）在旧机制与新方案下的不同表现；架构与流程图标出“本次改造范围”与“既有复用不动模块”的边界，每个节点写清做什么以及关键参数或条件（单图控制在 5 至 12 个核心节点）。
3. **按要表达的关系选图型**：

| 要讲清的关系 | 推荐图型 | 画法要点 |
| --- | --- | --- |
| 为什么要改、新旧机制在同一场景下的差异 | 阶段对比矩阵图 / 前后路径对照图 | 顶行对齐各时间阶段，上下两行对照旧做法痛点与新方案收益 |
| 改了哪块、没改哪块与数据怎么分流 | 带职责边界框的横向数据流 / 模块架构图 | 用虚线框区分本次改造范围与既有复用模块 |
| 多环境或多角色如何配合（如生产、同步、预发隔离比对） | 跨环境 / 跨角色泳道图 | 按环境或角色分泳道，单独标出隔离边界 |
| 多服务先后调用顺序、轮询等待与异常返回 | 跨组件时序图（`sequenceDiagram`） | 按调用顺序标清关键参数与异常返回路径 |
| 状态有哪些合法跃迁与不可逆终态 | 分组状态流转图 | 逐行核对状态表，避免遗漏合法转移边 |
| 时间切点、窗口边界或存储键值结构 | 时间轴 / 结构切分示意图 | 标出关键时间点、窗口起止或字段分段边界 |

### 3.2 表格写法

- **单节只讲一件事**：每个二级小节只回答一个问题。两个子话题如果各自都有表格或代码块（如“触发规则”和“新增文件格式”），拆成两个同级小节。
- **表内写简明结论，复杂前提移到表下**：4 列及以上的表格每列较窄，单元格内只放 1 至 2 行完整短句（用自然短语写状态变化，不用多组 `A -> B` 符号串）；带例外前提或补充解释的内容提取到表格下方用 2 至 3 条分点详述，同一列有多条动作时统一用分点列表对齐。
- **按需选用标准表格构件**：状态定义表坚持一枚举值一行，状态 × 操作权限矩阵表写明推进后的目标状态；改存量接口校验时列 4 列对照表（`接口或检查项 | 原来查什么 | 现在改查什么 | 原因说明`）。
- **拆分验证场景并把长命令移出表格**：验证表一行只测一个独立业务场景；异常恢复表先把完整长命令提取到表外全宽代码块。普通英文动作词（如 Submit、Approve、Rollback）直接写正文，反引号留给物理表字段与字面值、路径文件名、配置键、命令参数与错误码。

## 4. 口头复述自检与一步发布

1. 把定稿保存到 `.agent/work/<主题>/design.md`（或 `release.md`、`test-report.md`）。若用户未说明发布目标（飞书云文档、本地 HTML 或只留本地 `.md`），简短问一句。
2. **转排版前做一次白板口头复述自检**：
   - 把《方案总览》、所有章节标题、列表加粗小标题、卡片头与表头拎出来默念一遍：如果站在白板前给同组研发讲方案，平时嘴里会不会说出这个词？凡是照搬源码注释的生硬译词、把动词塞在句尾的名词堆叠短语、四字公文口号、空洞评价词或砍掉动作对象的半截话，当场改回自然动宾短句。
   - 检查 `1.1` 有没有混入实施期难点，路由或字典类配置有没有列全映射表，配图有没有直击最难懂的对比或边界，技术方案是否包含《方案取舍》表。
3. **自动衔接发布**：
   - 只留本地 `.md` 时直接交付文件路径。
   - 需要发飞书或出本地 HTML 时，从本 Skill 文件的实际目录解析 `../my-doc-publish/SKILL.md`，读取后完成排版、画板调整与校验。若当前会话已积累大量无关内容，再委派子 Agent，并传入定稿、发布 Skill 和按同一方式解析的 `../../rules/global.md` 的绝对路径。
   - 交付时若属重要评审方案，可提醒用户按需运行 `/my-review` 做独立盲读审查，不自动拉起审查子 Agent。
