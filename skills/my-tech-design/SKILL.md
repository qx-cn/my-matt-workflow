# 技术方案

读者是需要判断方案是否成立、风险是否可接受的工程师，不是实现清单。
依据已有需求、Spec、`decided.md` 和相关代码；现状描述附代码依据，确认不了的写进待确认项。

## 内容

- 先写需求概述：目标、不做的范围、本项目负责的部分和依赖方的分工。
- 章节围绕本项目的核心问题组织，并放在显眼位置。例如报表项目的"字段与数据来源"、接口项目的"接口契约"。
- 只写本项目新增或改变的部分。沿用现有机制的地方，一句话说明复用了什么，不展开下游和现有实现。
- 复杂规则分点写，并配具体例子，如分组计算、格式转换。
- 有真实取舍时，简述考虑过的备选方案和放弃的理由；没有就不写。
- 读者看不到 Spec 时，把判断方案所需的约束和依据写全。

以下章节有实际内容才写，没有就整节省略：
- 数据与接口变更：贴新增或修改的实际定义（Proto 片段、DDL、数据变更 SQL、MQ、配置），只贴改动部分，附一两句用途说明；没有改动的接口不写。定义只在这里出现一次，其他章节引用它。
- 上线顺序：依赖、切换条件，以及上线后看哪些指标或结果判断是否正常。
- 回滚：触发条件、恢复到什么状态、不可逆的边界和数据处理。涉及数据迁移、兼容或不可逆操作时必须写。
- 待确认项：影响判断的未知、怎么确认、由谁确认。

## 表达

文字、表格、图示选能降低理解成本的；简单内容不用图，关键规则用文字写清。
密集表格和长列表用整行区域，两栏只放短内容。成对比较用模板的 comparison / comparison-card，每侧有标题和列表。
图里节点只放短标签，长标识符、条件和例外写在旁边的正文里。

## 生成和检查

用 `assets/TEMPLATE.html` 生成 `.agent/work/<主题>/design.html`：填写标题、总览和章节占位符，导航与章节 ID 一一对应，不用的可选区块直接删掉。保留离线导航、折叠、页底评论、本地保存和 Markdown 导出；CSS、JavaScript 和 SVG 都内联。

运行 `python3 <本 Skill 目录>/scripts/check_html.py .agent/work/<主题>/design.html`，修完所有错误。
有可用浏览器时核对布局和交互；没验证的部分如实说明。

## 发布到飞书

只更新改动过的章节，保留未改章节和已有评论。工具做不到章节级更新，或没有飞书工具时，停下来说明，不整篇替换。
