# 澄清需求

- **先查代码再提问**：能从代码、建表 `.sql`、`.proto`、配置或现有文档查到的事实自己先查，不要拿显而易见的问题去问用户；给推荐选项前，先核实相关表字段、接口和运维工具的真实逻辑。用户提供了飞书文档、Wiki 等外部资料时，保存到 `.agent/work/<主题>/refs/` 并在文件开头留好原始 URL（含内部信息的归档只留本地，不提交公开仓库）。
- **分批提问**：每轮只问互不依赖的几个问题，每题带上你的推荐做法和简短理由；依赖本轮答案的问题留到下一轮再问。优先用宿主的提问工具（如 `AskQuestion` / `AskUserQuestion`）。
- **关键分岔给出对比选项**：遇到核心状态、表结构或接口边界有两种明显不同的做法时，简短对比两者的改动面、维护成本与风险后再给出推荐，供后续写入技术方案的取舍表。
- **追问盲点、说直白人话**：重点问清现实业务起因和具体算例、核心异常边界、上下游与运维工具受什么影响，以及回滚后如果库里已经产生了脏数据或半截状态该怎么恢复。总结时遵守全局写作规范，保留代码与团队原有的英文简称和动作词，别自造四字黑话。

当目标、范围、核心契约、取舍原因和验收标准都已清楚时结束提问，在对话里直接输出一份清晰的**需求与设计定稿摘要**，包含：

1. **现实背景与目标**
2. **核心规则、对外契约与排除范围**
3. **已确认的方案取舍（选了什么、排除了什么及原因）**
4. **关键验收场景与待确认项**

最后简短提示下一步：需要拉会评审或留存设计文档时可运行 `my-tech-design` 生成唯一技术方案（发飞书或存本地 `.agent/work/<主题>/design.md`）；小改动可直接在宿主 Plan Mode 开干。不替用户自动往下跑。
