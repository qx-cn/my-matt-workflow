# 澄清需求

能从代码或已有材料查到的事实，先查再问。
每轮问一批互不依赖的问题，每题附推荐答案和简短理由。依赖其他答案的问题留到下一轮。
围绕会改变目标、范围、约束或验收的未知追问，不把普通实现细节变成访谈题。

遇到模糊术语或类比，用具体场景和反例追问，核对它在代码里的含义。
必问一句：“哪些对象或场景不适用这条新规则”。

已确认的决定写进 `.agent/work/<主题>/decided.md`，一行一条，写清决定与原因。
结束时简述有效的目标、范围、约束和可观察验收，标明仍未确定的事项。
按需要建议下一步，例如用 my-to-spec 整理 Spec 或用 my-tech-design 说明方案，不强制继续。
