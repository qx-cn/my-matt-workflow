# 整理 Spec

不做访谈。依据已有讨论、PRD、已有的 `.agent/work/<主题>/decided.md` 与 `refs/`（存在时读取）以及代码事实整理，把触发本次需求的核心业务痛点与关键场景算例放在最前面（不把调研期放弃的候选方案缺陷错写成现网系统的痛点），保留原始参考文档的可点击 URL 链接，未决问题写成已知限制。若问题影响方案选择、实施或验收，则说明缺少的信息、受影响部分及开展相关工作前需确认的事项；不擅自补答案、指定负责人或将受影响部分写成已具备实施条件。

关于现状的描述要核实，并附可定位的代码位置；核实不了的不写成事实。遵守全局写作规范。

写入 `.agent/work/<主题>/spec.md`。之后的业务或方案修改直接改原文件，变更原因按 `YYYY-MM-DD | 决定内容 | 原因与背景` 一行一条记进同目录的 `decided.md`（若推翻旧决定，在旧决定行首标注 `[已废止，见 YYYY-MM-DD]`，纯措辞与排版微调不记）。

任务清单写可交付的结果；端到端验证写可观察的成功和失败条件，包含关键的边界和异常情况。

默认用下面七节；小改动可以合并或省略无关的节。

```markdown
# <主题>

## 1. 背景与目标

按业务重要性先写首要痛点与算例，再写目标与关联参考文档 URL。

## 2. 改动范围与边界

写明本服务改动模块，以及与本需求强相关但另案处理或维持原状的事项（无则省略本节）。

## 3. 现状事实

附代码位置，写清相关表字段与上下游调用契约。

## 4. 方案

写明涉及的文件、接口、表字段及分支或转换规则。

## 5. 系统影响与回滚方案

调用方、存量数据、新旧版本并存、并发与锁、服务版本回滚与异常数据恢复（运行期已产生的状态推进或数据变更如何恢复、依赖的判定字段与工具限制），按实际风险写。

## 6. 任务清单

## 7. 端到端验证
```
