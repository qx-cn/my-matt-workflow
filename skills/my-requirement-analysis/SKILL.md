# Requirement Analysis SKILL

仅在用户明确调用 `$my-requirement-analysis` 时运行。不得因普通需求文本、其他 Skill 的建议或即将制定 Plan 而自动调用。

用户明确调用本 Skill 后，在 AI 开始制定 Plan **之前**，spawn 独立 sub-agent 验证 AI 对需求的理解是否正确，防止在错误理解上构建 Plan。

## 调用时机（关键）

```
用户明确调用 $my-requirement-analysis → AI 初步理解 → ⭐ 需求审查 → 确认/修正理解 → 制定 Plan
```

**为什么在 Plan 之前？**
- Plan 是对需求的解决方案，如果需求理解就错了，后续所有工作都是浪费
- 越早发现理解偏差，修正成本越低（只需反问，无需重做 Plan）
- 主 agent 对自己的理解存在确认偏误，独立 sub-agent 能以旁观者视角发现偏差

## 适用场景

**适用：**
- 涉及多步骤实现的功能需求
- 用户给出的需求包含示例、类比或隐含假设
- 用户需求涉及多个模块或存在多种理解方式
- 需求描述较长或涉及领域概念

**不适用（直接跳过）：**
- 明确的 bug fix（如"某函数在 X 场景下 crash，请修复"）
- 单文件/单函数的简单修改
- 用户给出了精确的代码级指令（如"在 A 文件 B 函数中添加 C 逻辑"）
- 纯重构/代码风格修改
- 用户明确说"不需要分析，直接做"

## 执行流程

### 步骤 1：主 agent 准备结构化输入

主 agent 准备以下两项信息：

- `USER_ORIGINAL_INPUT`：用户的原始需求文本（**原样保留，不做删减或改写**）
- `TASK_SUMMARY`：主 agent 对需求的理解摘要（3-5 句），必须包含：
  - **目标**：用户最终想达到什么效果
  - **范围**：需要改动哪些模块/文件
  - **关键约束**：用户明确提出的限制条件
  - **验收标准**：怎样算"做完了"

### 步骤 2：快速通过判断

在 spawn sub-agent 之前，主 agent 先自检是否满足**全部**快速通过条件：

1. 用户需求是一条明确的指令，没有示例/类比/隐喻
2. TASK_SUMMARY 的目标、范围、验收标准都能直接从用户原文中逐条对应
3. 不存在多种合理的理解方式
4. 用户没有使用"比如"、"例如"、"类似"、"像...一样"、"参考"等间接描述

**全部满足 → 跳过 sub-agent，记录"需求清晰，快速通过"后直接进入 Plan**
**任一不满足 → 进入步骤 3**

### 步骤 3：Spawn 独立 sub-agent

使用 Agent 工具 spawn 一个 sub-agent，prompt 模板如下：

```
你是一名独立的需求分析审查员，未参与之前的对话。你的任务是验证 AI 对用户需求的理解是否正确。

## 用户原始输入
{USER_ORIGINAL_INPUT}

## AI 的理解摘要
{TASK_SUMMARY}

## 你的工作方式
1. 仔细阅读用户原始输入，独立形成你自己的理解
2. 将你的理解与 AI 的 TASK_SUMMARY 逐项对比
3. 用 Read/Grep/Glob 查看用户提到的文件或模块，验证 AI 理解的上下文是否正确
4. 按 4 个维度逐一审查（见下文）
5. 如果需求清晰且 AI 理解正确，快速给出 PASS

## 审查 4 维度

### 1. 目标准确性
- AI 理解的"用户想要什么"是否与用户原始表述一致？
- 是否把示例/类比误当成了任务本身？（如：用户说"像 X 模块那样做 Y"，AI 是否误解为"修改 X 模块"？）
- 是否把手段误当成了目标？（如：用户想提升查询性能，AI 理解为"加索引"而非"提升查询性能"？）

### 2. 范围完整性
- AI 理解的改动范围是否覆盖了用户需求的所有方面？
- 是否遗漏了用户的隐含需求？（如：用户举了一个具体例子，但实际影响面更广）
- 是否有过度扩展？（AI 理解的范围超出了用户实际要求）

### 3. 约束识别
- 用户明确提出的约束条件是否都被 AI 捕获了？
- 是否遗漏了项目层面的隐含约束？（如：兼容性要求、性能要求）
- 约束之间是否存在冲突？

### 4. 歧义标记
- 用户需求中是否存在可以有多种合理理解的表述？
- 如果存在歧义，AI 选择了哪种理解？这个选择是否合理？
- 是否有需要向用户澄清的关键问题？

## 输出格式

### Requirement Analysis 结果

**判定**：PASS / NEEDS_CLARIFICATION / MISUNDERSTANDING

#### 各维度评估
对每个维度给出 ✅/⚠️/❌ 及一句话说明。

#### 问题列表（仅在非 PASS 时需要）
- [MISUNDERSTANDING] 理解偏差描述 — AI 理解为 X，但用户实际意思可能是 Y
- [AMBIGUITY] 歧义描述 — 建议向用户澄清的问题
- [MISSING] 遗漏描述 — AI 未捕获的需求或约束

#### 建议
- 修正后的理解摘要（如有偏差）
- 建议向用户提出的澄清问题（如有歧义）

## 重要
- 你的目标是验证"理解是否正确"，而非评判"方案是否合理"——方案设计是后续设计审查的职责
- 需求清晰且理解正确时，直接给 PASS，不要为了"显得有用"而制造问题
- 不要捏造不存在的歧义
- 关注大方向，不纠结措辞细节
```

### 步骤 4：处理分析结果

| 结果 | 动作 |
|------|------|
| PASS | 直接进入 Plan 制定 |
| NEEDS_CLARIFICATION | 主 agent 向用户提出澄清问题（基于 sub-agent 建议），等用户回复后重新评估（不需要再 spawn sub-agent） |
| MISUNDERSTANDING | 主 agent 修正理解。偏差严重（目标理解错误）→ 修正后 spawn 新 sub-agent 验证；偏差轻微（范围/约束遗漏）→ 修正后直接进入 Plan |

### 迭代机制

- **最大迭代次数**：2 次（每次 spawn 新 sub-agent）
- 第 1 次：全量分析
- 第 2 次：验证修正后的理解是否正确（仅在第 1 次判定为 MISUNDERSTANDING 时）
- 2 次后仍有 MISUNDERSTANDING → 向用户展示两版理解的差异，请用户明确

## 与其他 SKILL 的关系

```
用户明确调用 $my-requirement-analysis → 需求审查 → Plan 草稿 → 设计审查 → 用户审批 → 编码 → 代码审查 → 验证 → 完成
```

- **前置**：用户明确调用 `$my-requirement-analysis`
- **后续**：Plan 制定
- **互补**：本 Skill 验证“理解对不对”，`$my-review-design` 验证“方案好不好”，`$my-code-review` 验证“实现对不对”
