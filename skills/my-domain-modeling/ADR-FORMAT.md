# ADR 格式

个人 ADR 候选存放在 `.agent/work/<topic>/domain/adr/`，文件名为 `domain-<topic>-<NN>-<slug>.md`。项目已有正式 ADR 目录时先读取它；写回团队目录须遵守项目的确认策略。

只在首次确有 ADR 时创建 `.agent/work/<topic>/domain/adr/`。

## 模板

```md
# {决策的简短标题}

{一到三句话：背景是什么、决定了什么、为什么。}
```

就是这样。ADR 可以只有一个段落；价值在于记录**做过**什么决定和**为什么**，而非填满各种章节。

## 可选章节

只有在确实增加价值时才加入，多数 ADR 不需要：

- **状态** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：适合决定被重新审视时。
- **考虑过的选项**：仅在被否决的替代方案值得记住时使用。
- **后果**：仅在需要指出不明显的下游影响时使用。

## 编号

扫描个人候选目录或项目配置的正式 ADR 目录，取现有最大编号加一。个人候选写回团队前应重新核对团队目录，避免与其他人新增的 ADR 冲突。

## 何时建议 ADR

必须同时满足以下三项：

1. **难以逆转**：以后改变主意的成本很高。
2. **缺少背景会令人意外**：未来读者看见代码会问“他们为什么这样做？”
3. **源于真实权衡**：存在真实替代方案，并因具体原因选择其一。

若决定容易逆转，就跳过——以后自然会改回来；若并不令人意外，没人会追问；若没有真实替代方案，除了“我们做了显而易见的事”就无须记录。

### 符合条件的例子

- **架构形状。** “使用 monorepo。”“写模型采用事件溯源，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “订单与计费通过领域事件通信，而非同步 HTTP。”
- **会造成锁定的技术选择。** 数据库、消息总线、身份认证提供方、部署目标；不是每个库，只记录替换成本高的选择。
- **边界与范围决策。** “客户数据归 Customer 上下文所有；其他上下文只能以 ID 引用。”明确的“不做什么”和“做什么”同样有价值。
- **刻意偏离显然路径。** “因为 X 使用手写 SQL 而非 ORM。”任何合理读者会预期相反选择的事项，都能阻止下一位工程师把有意设计当作错误“修复”。
- **代码中不可见的约束。** “因合规要求不能使用 AWS。”“由于合作方 API 合同，响应时间必须低于 200ms。”
- **不明显的被否决方案。** 若曾考虑 GraphQL 却因微妙原因选择 REST，应记录；否则六个月后又会有人提出 GraphQL。
