# 需求对齐

两阶段闸门：先回述需求并停顿，用户确认后再对照方案。默认只诊断；用户明确说「按最小纠偏改方案」后再改方案。

通常接在 `/my-grill-me` 或 `/my-grill-with-docs` 的方案产出之后。本 skill 只做对齐闸门；写入 docs/ADR 仅在用户要求时。

## 全程规则

每条关键断言旁注依据（原话摘要或对话轮次）。意图用转述；仅真实出现过的表述才加引号并标「用户说过」。不确定写「不确定」。中文输出（用户另有要求除外）。

来源三类分开写：

- **假设**：从未被用户确认
- **漂移**：曾确认过，后来改成别的
- **推断补全**：为自洽补上、用户未提

## 1. 回述需求

只陈述需求。输出结构：

```markdown
# 需求回述

## 1. 真正想要的
- …

## 2. 明确不想要的 / 非目标
- …

## 3. 硬约束
- …

## 4. 成功标准
- …

## 5. 范围边界
- In：…
- Out：…

## 6. Must vs Nice
- Must：…
- Nice：…（对话未区分则写「未区分」）

## 7. 未确认假设与推断补全
- [假设|推断补全] …（依据或「无依据-模型推断」）

## 8. 可能的漂移点
- …（从 A 变成 B；前后依据）

## 9. 不确定项
- …
```

**完成条件**：九节齐全；第 7、8 节每条都有依据标注；已用下面整句提问并停止等待回复：

> 以上需求回述是否符合你的原意？请指出要改的条目；确认后再做方案对照。

用户要改：更新回述，再次满足本步完成条件。用户未明确确认前，不进入第 2 步。

## 2. 对照方案

仅在用户明确确认第 1 步后执行。读取并遵循 [phase-b.md](phase-b.md)。

**完成条件**：已确认需求的每一条都有判定；超出与偏离均已入清单；已给出最小纠偏与一句结论；未改方案，除非用户明确要求按最小纠偏修改。
